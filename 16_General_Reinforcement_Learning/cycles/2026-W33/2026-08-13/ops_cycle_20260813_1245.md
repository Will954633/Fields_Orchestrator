## Mechanism I think is at work

The board is not decaying. It is **blocked on two credentials**, and one of them
(Bright Data) is the sixth credential-expiry outage this business has had — Gmail twice,
GitHub, the Google 7-day OAuth, and a two-month Facebook Ads token blackout. Not one of
these credentials has expiry monitoring. Rule 7 made processes report whether they *ran*;
nothing reports whether the secrets they run on are still *valid*, so every one of these
has been discovered by the downstream job dying rather than by the credential aging out.
That is a class, and it will produce a seventh.

A second, smaller mechanism worth recording. `run_curlffi_suburb_scrape.py` returns 2 on
the total-discovery-zero path at line ~1174, **before** the `listing_discovery_coverage`
heartbeat is written at ~1191. So a hard upstream outage writes *no* heartbeat at all,
and the board renders it `STALE — may not be firing` rather than `ERROR`. The mandate's
warning about `repair_class` held exactly: the hint said `NOT_FIRING`, and the truth is
that the cron fired fine and the fetch died. The primary signal (Step 101 ERROR) was
correct, so this is a nuance rather than a defect, but it means an outage can present as
neglect.

## The open question I'd most like answered next week

**Do we want credential-expiry monitoring as a first-class check, and is Will willing to
tell us where each credential's expiry actually lives?**

Six outages of the same class, every one found by a downstream job dying days later.
The obstacle is not the code — a job that probes each credential weekly and heartbeats
per-credential is small. The obstacle is that some of these (Bright Data, the FB Ads
60-day token) have an expiry only the account owner can see, so the probe has to be
"make the cheapest possible authenticated call and check for 401" rather than reading an
expiry date. I would want Will's agreement before adding recurring authenticated calls
against paid external accounts, which is why this is a question and not a recommendation.
