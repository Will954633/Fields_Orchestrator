### (a) React #418 on the off-market deck — a ~10× step, and a recurrence of our own July fix

Normalised, so this is not a traffic story — `/off-market/*` pageviews are flat across the window:

| week | pageviews | #418 | per 100 pv |
|---|---|---|---|
| 07-26 | 101 | 0 | 0.0 |
| 08-09 | 110 | 0 | 0.0 |
| 08-16 | 74 | 1 | 1.4 |
| **08-23** | 129 | 20 | **15.5** |
| **08-30** | 129 | 21 | **16.3** |
| **09-06** | 105 | 13 | **12.4** |

~1 in 8 pageviews, across ~22 distinct property pages and every major browser.

**I first suspected my own mount.** The step lands exactly the week REC-onsite-003 mounted
`PersonalizationSlot` on the V4 deck (2026-08-23). Reading the component killed that hypothesis: it
returns `null` on SSR *and* on first client render, and only sets content inside an async callback
after mount — which is a normal state update, not a hydration mismatch. It cannot produce #418.
Recording the false lead because the temporal coincidence was strong enough that I would have
believed it without checking.

**The actual cause.** `WhatsChangedSection.tsx` computes dates *during render* in two places:
`selectTimeline()` does `new Date()` and `WhatsChangedAnchor()` does
`new Date().toISOString().slice(0,10)`. Both feed rendered text — one gates a visible count ("2
dated changes"), the other drives two date-boundary expiry rules that decide whether points render
at all. SSR and hydration sample different instants; with the SSR HTML cached, a response generated
before a boundary and hydrated after it renders different text.

**This exact bug has its own fix-history ID from 2026-07-24**, where it was fixed for
`computeGainVerdict` by capturing one instant in the loader (`off-market.$slug.tsx:848`,
`asOfMs: Date.now()`, with a comment naming React #418). `HeroSection.tsx` even carries a ⚠ warning
to use it. `WhatsChangedSection` moved into Part 03 on 2026-08-13 and never adopted it — which is
why the rate steps the following week.

Fixed: both sites now read `new Date(data.asOfMs ?? Date.now())`.

## 5. Address search — the regression harness I owed from last cycle

Last cycle: *"I said last cycle I would make the 400-address regression harness permanent and I did
not get to it. It is the first thing next week."* Built:
**`scripts/address_search_regression.py`** (pushed, `0c46aa55`).

It samples addresses from the **suburb collections, never the index** — an index-drawn probe is
structurally incapable of seeing the 1,843 addresses that were absent from the index in September —
types each the way an owner would, hits the live API, and asserts two floors: `found ≥ 97%` (comes
back at all) and `first ≥ 80%` (ranked first; "3 Cassowary Drive" returning 35/37/39 but never
number 3 is what sends an owner a report on a neighbour's house). Rule 7b assertions on all three
zero-output paths.

**Full sweep, 240 probes across the three core suburbs:**

```
found  240/240  100.0%   (floor 97.0%)
first  239/240   99.6%   (floor 80.0%)
latency  p50 1.59s   p95 1.69s
NOT-FIRST  2/28 Castello Circuit Varsity Lakes  rank 2, top='28/28 Castello Circuit'
```

The single not-first is a genuine ambiguity between two real units in one building, returned at
rank 2. Post-topup the search is healthy, and there is now a baseline to regress against.

**Two things the harness got wrong first, recorded because they are the useful part:**

1. I guessed `UNIT_NO`. The real field is **`UNIT_NUMBER`** (Rule 8; `db_fields.py --grep UNIT`
   shows 98% fill, and no `UNIT_NO` path exists). Unverified, every unit probe would have silently
   tested the *house* at that street number — the harness would have passed while blind to exactly
   the 1,002 unit addresses that were the real September failure.
2. The first live run scored **0/24 against a site answering every probe correctly**: the
   comparator did not normalise punctuation, and we store `complete_address` unpunctuated while the
   API renders it with commas. The failure direction was the lucky one — a *looser* comparator
   would have printed PASS forever and been worth nothing.

**Not scheduled, deliberately.** No domain may edit the crontab. `job_run` self-registers
unconditionally, so it records its real outcome to `job_runs` but sets `stale_hours` absurdly high
until `--scheduled` is passed — otherwise it plants a permanently-STALE row on the Process Registry
for a cadence nobody signed up to. Heartbeat verified:
`success · "100.0% found, 99.6% first, p95 1.69s (n=240)"`. Scheduling ownership is the open ask in
REC-onsite-006.
