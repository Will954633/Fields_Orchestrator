## 3. Friction first — the incident, and the much larger thing under it

`rl_onsite_friction`: **2 incidents / 39 sessions (1 HIGH, 1 LOW)**, plus 3 client errors on
`/find/burleigh-waters`.

The HIGH: `did=01a0663b-ae7`, **38 searches, 0 submits**, converging on
`601/190 Varsity parade  varsity` — arriving from the **Owner-Market carousel ad**
(`/find/varsity-lakes?utm_campaign=owner_market_carousel`). Paid traffic, correct suburb, real
owner behaviour, zero result.

I ran it against the live API before concluding anything. `601/190 Varsity Parade` genuinely is not
in our data — the index holds only `190`, `112/190`, `210/190`, `603/190`, `604/190` at that
building, and `varsity_lakes` holds a different set again. That one visitor's unit we do not have.

**But checking why led somewhere much worse.** Three findings, each verified:

**(a) The index was built once and never rebuilt.** Every original row's `_id` timestamps to
**2026-03-07, between 02:20 and 02:46 UTC** — one 26-minute run of `build-address-index.mjs`.
Nothing schedules it. It has no heartbeat. Six months of new cadastral rows and sold-listing
addresses accumulated outside it:

| suburb | held | absent from index | |
|---|---|---|---|
| varsity_lakes | 7,119 | 961 | 13.5% |
| robina | 11,306 | 419 | 3.7% |
| burleigh_waters | 6,752 | 463 | 6.9% |
| **total** | **25,177** | **1,843** | **7.3%** |

1,002 of the 1,843 are unit addresses.

**(b) What that actually did to a visitor — and it is not simply "slow".** Missing addresses fall
through to `searchCollectionsFallback`. Measured live: `1/18 Thornleigh Crescent` **12.0s**,
`1/49 Heights Drive Robina` **11.2s**, `104/170 Bardon Avenue` **11.8s**, `39 Manhattan Avenue
Robina` **13.5s** — against ~1.6s on the indexed path. On a keystroke-debounced box, that is
indistinguishable from broken.

The worse case is when the fallback never runs, because the deliberately-loose regex found *some*
other row and the handler only falls back on a total zero:

- `159 Varsity Parade` returned **only `159/251 Varsity Parade`** — a different building.
- `3 Cassowary Drive Burleigh` returned 3/2, 35, 37 and 39 Cassowary Drive — **never number 3**.

The owner's own home was absent while a neighbour's was offered. If they click it we generate a
report on someone else's property; if they don't, they leave. Neither is visible to us.

**(c) A zero-result search rendered nothing at all.** `AddressSearch.tsx` did
`setIsOpen(response.results.length > 0)`, so the `noResults` branch in its own JSX was **unreachable
on a fresh search** — no dropdown, no message, no error, just a spinner that stops. This is why the
class of defect keeps reaching production and keeps being found by a visitor rather than by us: the
failure state was, literally, nothing happening. It is also what a 38-search retry loop looks like
from the inside.

### What I did (both under briefing §4 "ship reversible on-site conversion fixes")

1. **`scripts/topup_address_search_index.py`** (new) — additive-only, mirrors the builder's document
   shape from the suburb collections, Cosmos 429 back-off, and a Rule 7b assertion (missing>0 and
   inserted==0 → raise). Ran it: **1,843 inserted, 0 duplicates created**, verified by counting each
   topped-up address across the whole index. All six failing probes now return the correct address
   **first**, `search_mode=indexed`, ~1.6s. No regression on previously-working queries
   (`5 Fulham Place Robina`, `25 H` unchanged).
2. **`AddressSearch.tsx`** — dropdown opens on zero results so the no-match state is reachable,
   suppressed while `isLoading` so it cannot flash under the spinner, and given a next step:
   unit-shaped queries (`^\d+\s*[/-]`) are told to try the street number and street name without the
   unit. `npm run build` clean, **one** commit `431c18a0`, one Netlify build. Verified live headless:
   the exact 38-times query now renders *"No match for "601/190 Varsity Parade Varsity Lakes". Try
   the street number and street name without the unit number."*, **0 console errors**; positive
   control `1/18 Thornleigh Crescent` — one of the topped-up rows — returns correctly.

Fix-history: `[ADDRESS-SEARCH-INDEX-STALE]`, 2026-09-06.

**The honest caveat:** this is the **fifth** visitor-found address-search failure in six weeks
(Gleneagles 07-30, slash/state 08-28, street types 08-30, this). Every one reached production
because nothing tests the matcher or the index against real stored addresses. I said last cycle I
would make the 400-address regression harness permanent and I did not get to it — the index work
took the cycle. It is the first thing next week.

## 4. Experiments — read, not concluded

**Nothing served, nothing retired, nothing scaled this cycle, and that is the rule working.**

Last cycle's hypothesis was that the `no_contact` mechanism — the strongest effect measured anywhere
on this site — would transfer from `/property` to the deck, which carries the traffic. First read:

- `/off-market` `no_contact` **7.3% (10/136)** vs control **4.9% (6/122)** — 1.50×
- `/property` `no_contact` **9.5% (25/263)** vs control **5.1% (13/256)** — 1.87×

**The same framing leads on two independent surfaces.** A mechanism replicating across surfaces is
worth considerably more than one arm winning on one page, and it is the first thing this domain has
measured that does.

My kill/scale rule says SCALE on two consecutive holding reads. `offmarket_2` is at read 1 — kept
running. `property_1` is at read 2 and holding direction (2.35× → 1.87×), so by the letter of the
rule I could promote it. **I did not**, and the reason matters: 25 vs 13 conversions is z≈1.9, the
magnitude has already regressed once, and this domain withdrew a recommendation seven days ago
because an arm inverted inside a week at exactly these counts. Promoting on that evidence is the
14-vs-11 error with better manners. One more read is cheap; being wrong in public is not.

**No new experiment proposed.** All four of my surfaces already carry one, and the honest thing to
say is that adding a fifth arm to fill a quota would compete for the same thin traffic. The
untested question this cycle actually raised is not a content question — it is whether the two
search fixes move `searched_address` off 17. That is a measurement next week, not an arm.
