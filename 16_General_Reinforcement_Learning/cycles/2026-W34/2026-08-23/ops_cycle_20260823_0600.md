## Fixed this cycle (2)

### 1. Step 117 — nightly run failed on a legitimately empty queue

This is the row that had been taking the **entire nightly pipeline** to `status: failed` for
three nights. Its stdout contradicted itself in the space of two seconds:

```
Needing satellite analysis per suburb:
  - robina: 11 / varsity_lakes: 3 / burleigh_waters: 3 / merrimac: 0
  Total: 17
...
shared.ru_guard.EmptyWorkSetError: No properties need satellite analysis.
```

**Root cause, proven:** `count_needing_analysis()` counts the raw Mongo query.
`fetch_candidates()` additionally applies the `_is_house()` gate, which cannot be expressed
in a query. I ran both halves directly against the three target suburbs:

```
robina             matched= 11 houses=  0
varsity_lakes      matched=  3 houses=  0
burleigh_waters    matched=  3 houses=  0
TOTAL matched 17 houses 0
```

All 17 are unit-numbered strata addresses (`31/24 Ron Penhaligon Way`, `2501/42 Laver Drive`,
`163/251 Varsity Parade`). Non-houses are excluded **deliberately** — the `_is_house`
docstring records that a scheme-level `backs_onto` corrupts `precompute_valuations.py:448`'s
primary signal. So the queue was genuinely drained and the step called that a failure.

**Fix** (`scripts/step117_satellite_analysis.py`, non-monitoring pipeline code, brief §4):
a gate-drained queue now exits success with the counts printed; the Rule 7b outcome assertion
**moves** post-loop to `if candidates and stats.successes == 0: raise`, so "found work and did
none of it" still can never report success; and a latent `AttributeError` is fixed alongside
(the gate turns the cursor into a generator and the next line called `cursor.limit()` on it —
any run passing `--batch-size` would have crashed).

I want to be explicit about the risk here, because this is the exact shape of the thing I am
forbidden to do: **I made a red row go green.** The justification is that the row was
factually wrong — there was no work, and the step said there was. I did not touch monitoring
code, I did not delete a heartbeat, and I moved the assertion rather than removing it. If Will
disagrees with that call, the change is one commit and reverts cleanly.

**Verified:** re-ran the step. Exit 0, `✓ Nothing eligible: 17 matched the filter, none are
houses.` Pushed as `ed909676`.

### 2. FB-organic approval poller — a heartbeat failure was double-publishing

`fb_approval_poll` read STALE ("last ran 0.3d ago, expected every 1h"). It was not dead:
`logs/fb_approval.log` has mtime 2026-08-22 22:57 and ends in normal `poll done` lines, while
the job's single `job_runs` document is frozen at 12:57 — ~10 hours of 3-minutely polls with
no heartbeat.

**Root cause:** `main()` wrapped the import, the poll and the heartbeat write in one
`try: … except Exception: poll(a.dry_run)`. A `record_job_result` failure therefore skipped
the heartbeat *and re-ran `poll()`* — and `poll()` publishes to the public Facebook page. So
every heartbeat failure was also a double-publish risk, ~200 times over.

**Fix:** guard only the import, run `poll()` once, let a heartbeat failure raise into the log.
Verified by `py_compile` + `poll --dry-run` (prints once). Pushed as `9efdde94`.

**Honest limit:** I fixed the swallow, not the trigger. `record_job_result` succeeded when I
called it by hand this morning, so the underlying write failure looks transient (Cosmos RU).
The point of the fix is that the next one will be visible instead of silent. I did not re-run
the poller to confirm the heartbeat recovers, because Tier 1 forbids re-running anything that
publishes — it will prove itself at 08:00 when cron next fires.
