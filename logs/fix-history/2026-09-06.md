## [ADDRESS-SEARCH-INDEX-STALE] Search index built once in March; 1,843 core-suburb addresses unfindable — 11:00 AEST
**Symptom:** A visitor from the Owner-Market carousel ad searched `601/190 Varsity Parade Varsity lakes` 38 times on `/find/varsity-lakes` and never submitted (onsite friction sensor, HIGH). Investigating that led to a much wider defect: addresses we hold were either resolving through an ~11-second fallback path or being **silently replaced by a different property**. `159 Varsity Parade` returned only `159/251 Varsity Parade` — a different building. `3 Cassowary Drive Burleigh` returned 3/2, 35, 37 and 39 Cassowary Drive but never number 3. The owner's own home was absent while a neighbour's was offered.
**Root cause:** Two independent faults.
  1. **`Gold_Coast.address_search_index` was built exactly once and never rebuilt.** Every original row's `_id` timestamps to 2026-03-07 between 02:20 and 02:46 UTC — a single 26-minute run of `scripts/build-address-index.mjs`. Nothing schedules it; it has no heartbeat. Six months of new cadastral rows and sold-listing addresses accumulated outside it: **1,843 of 25,177 addresses (7.3%) held in the three core suburbs were absent, 1,002 of them unit addresses** (varsity_lakes 961/7119 = 13.5%, robina 419/11306 = 3.7%, burleigh_waters 463/6752 = 6.9%). Missing addresses fall through to `searchCollectionsFallback`, measured live at **11.2s–13.5s** vs ~1.6s on the indexed path; and where the deliberately-loose regex found *some* other row, the fallback never ran at all and the wrong property was returned instead.
  2. **A zero-result search rendered nothing whatsoever.** `AddressSearch.tsx` did `setIsOpen(response.results.length > 0)`, so the `noResults` branch in its own JSX was unreachable on a fresh search — no dropdown, no message, no error. From the visitor's side an unfound address is indistinguishable from a broken box, which is exactly what a 38-search retry loop looks like from the inside.
**Fix:**
  - Added `scripts/topup_address_search_index.py` — additive-only top-up that mirrors the builder's document shape from the suburb collections, with Cosmos 429 back-off and a Rule 7b assertion (missing>0 and inserted==0 → raise). Ran it for the three core suburbs: **1,843 inserted, 0 duplicates created** (verified by counting each topped-up address across the whole index). Re-probed all six failing queries live: every one now returns the correct address first, `search_mode=indexed`, ~1.6s.
  - `AddressSearch.tsx`: open the dropdown on zero results so the no-match state is reachable, suppressed while `isLoading` so it cannot flash under the spinner, and gave it a next step — unit-shaped queries (`^\d+\s*[/-]`) are told to try the street number and street name without the unit.
  - **Not done, and raised instead as REC-onsite-006:** the other ~49 suburbs are still six months stale and all 52 will re-rot. The rebuild needs a schedule (crontab is globally prohibited to RL domains) and a full 52-suburb rebuild rewrites the collection behind the highest-value action on the site, which is not an unattended operation.
**Files:** `scripts/topup_address_search_index.py` (new), `01_Website/src/components/AddressSearch/AddressSearch.tsx` (commit `431c18a0`, repo `Will954633/Website_Version_Feb_2026`).
**Recurrence:** First for the index staleness. But it is the **fifth** visitor-found address-search failure in six weeks — `[ADDRESS-SEARCH-WHITESPACE]` (Gleneagles, 07-30), `[ADDRESS-SEARCH-SLASH-STATE-ZERO]` (08-28), `[ADDRESS-SEARCH-STREET-TYPE-ZERO]` (08-30), and now this. Every one reached production because nothing tests the matcher or the index against real stored addresses. A fixture suite is overdue.
