
## [ARTICLE-EXCERPT-TRUNCATION] Article subtitles cut mid-word at 300 chars — 15:24 AEST
**Symptom:** The subtitle (dek) on the draft article "Sold in 35 Days: How a Renovated Burleigh Waters Duplex Reached $1,100,000" ended mid-word — "...this home landed above the g". `custom_excerpt` was exactly 300 chars. A sweep of `system_monitor.content_articles` found 13 more articles cut mid-word (8 at 300, 5 at 280) plus 4 carrying raw `**` markdown at the tail — 17 of 92 total, 12 of them published and live.
**Root cause:** Every excerpt write path used a raw character slice with no word-boundary awareness: `scripts/push_to_ghost.py` sliced `stripped[:300]` when deriving the excerpt from the first paragraph and re-sliced `custom_excerpt[:300]` on both the create and update writes to Mongo; `pipeline/run_market_strength.py`, `run_state_of_market.py` and `run_market_insight.py` each did `line[:280]`. The 280-char pipeline cut then hit the 300-char cut downstream, so a long lead paragraph was guaranteed to land mid-word. Bold lead paragraphs also leaked their `**` markers because the excerpt was taken from raw markdown.
**Fix:** Added `scripts/excerpt_utils.py` with `clip_excerpt(text, limit)` — strips markdown emphasis, returns the text unchanged when it fits, otherwise prefers the last complete sentence inside the limit (when it retains ≥60% of the allowance) and falls back to the last whole word plus an ellipsis so a trim is visible rather than silent. Guards a degenerate no-word-boundary input by hard-cutting, and is limit-inclusive of the ellipsis. Wired into all five write sites; `push_to_ghost.py` is the last gate before Mongo, so nothing truncated can reach the DB regardless of which pipeline produced it. Backfilled all 17 damaged excerpts by re-deriving from the article's first HTML paragraph and re-clipping; re-verified zero remaining.
**Files:** fields-automation: `scripts/excerpt_utils.py` (new), `scripts/push_to_ghost.py`, `pipeline/run_market_strength.py`, `pipeline/run_state_of_market.py`, `pipeline/run_market_insight.py`
**Recurrence:** First

## [HEALTH-BOARD-PAUSED-VS-DEAD] Paused jobs buried 3 real failures on the Systems Health board — 09:05 AEST
**Symptom:** Will asked for an audit of every heartbeat watcher on the Fields Systems Health sheet. Process Registry read **67% health, 5 ERROR + 33 STALE** — but almost all of it was noise. Of 32 flagged rows, 29 were jobs switched off ON PURPOSE (the 2026-07-30 `[RL-AGENTS-PAUSE]` and Home Owner funnel pauses, plus the 2026-07-29 weekly-SEO disable). Only 3 were real, and they were invisible inside the noise.
**Root cause:** `collect_self_reported_jobs()` — the generic Rule 7 heartbeat renderer — had no concept of "off on purpose". A paused job keeps its last heartbeat forever, so it ages into STALE (or freezes on a final ERROR) and alarms every day. `collect_process_registry()` already had `_REGISTRY_DISABLED` for exactly this, but the heartbeat path never got the equivalent. Net effect: the board cried wolf 29 times a day and the 3 genuine failures didn't stand out.
**The 3 real failures found underneath:**
1. `seo_dashboard` — dead since 2026-07-28 while cron fired daily (syslog confirms Aug 2/3/4/5). Its crontab line was the ONLY one of 83 using relative paths with no `cd`: `set -a && source .env && ...`. Cron runs from `$HOME` (`/home/projects`), where no `.env` exists → `source` fails → the `&&` chain short-circuits → the script never runs AND nothing is logged, anywhere. Silent by construction. Same class as `[[gh_api_large_file_gotcha]]` (relative paths + cwd reset); almost certainly collateral from the `[OPS-CRONTAB-WIPE]` restore.
2. `offmarket_home_signal` — failing nightly on `WriteError code 28: Cannot create field 'address' in element {offmarket_home: null}`. `crm_sync.py`'s hourly whole-doc REPLACE carries the field forward with a bare `.get()`, storing an explicit **null** for every contact that never had one; Mongo cannot create a dotted path inside a null, so every `$set` raised. 381 contacts affected. `physical_scan` (70) and `home_confirmed` (65) carried the identical unfired landmine — `minisite-visit.mjs:129` dotted-`$set`s into `physical_scan` from live traffic.
3. `ssd_quota_autoresize` — cron line lost in the `[OPS-CRONTAB-WIPE]` restore (absent from `crontab.restored-2026-07-30.bak`). Investigating showed it is also **obsolete**: a separate 750 GB `blobs-hdd` disk was attached and `/data/blobs` moved onto it (`/dev/sdc`, 738 G, 43% used), well past its `TARGET_BLOB=700`. It still targets `DEV=/dev/sdb` (the old 400 GB `fields-blob-storage`), so running it now would grow the wrong disk.
**Also found:** `search_intent_ads` was a FALSE ALARM — it reports `error` on "0 rows", but every Google Ads campaign is PAUSED/REMOVED so the search-terms report correctly returns nothing. And 5 weekly jobs (`fpf_preflight_gmail`, `fpf_friday_batch`, `propradar_ingest`, `fetch_abs_market_signals`, `fetch_macro_indicators`) declared no `cadence_hours` at all — running fine but effectively unmonitored, defaulted to a 24 h cadence they could never meet.
**Fix:**
- `main_site_health_check.py` — new `_PAUSED_JOBS` registry (29 entries, each with reason + pause date), the heartbeat-side twin of `_REGISTRY_DISABLED`; renders KNOWN-GAP (severity 0, `info=True`) instead of an alarm. **Safety valve:** a listed job that reports a run INSIDE its cadence is rendered normally with "LISTED AS PAUSED but ran Nh ago — remove it from `_PAUSED_JOBS`", so the registry can suppress a job only while it is genuinely silent, never while it is running or failing. Verified across 6 cases incl. paused-and-erroring-while-live → still ERROR.
- crontab — `seo_dashboard` line rewritten with `cd /home/fields/Fields_Orchestrator &&` + absolute script/log paths. Reproduced the old failure under a stripped `env -i` cron-like shell, then confirmed the new form runs.
- `crm_sync.py` — `offmarket_home` / `home_confirmed` / `physical_scan` now carry forward as `{}` not `None` (verified nothing anywhere does `is None`/`=== null` on them, so `{}` is behaviour-identical). `offmarket_home_signal.py` — added an idempotent pre-pass unsetting any explicit null. One-time repair cleared all 516 existing nulls across the 3 fields.
- `search-intent-collector.py` — new `_SRC_EMPTY_OK` set: 0 rows AND no source error = success-with-note, for `ads` only. Every real ads failure appends a `google-ads:` error, so an empty error list unambiguously means "API answered, nothing to report". 5/5 logic cases pass; `gsc` empty still ERRORs.
- `fpf_preflight_gmail.py`, `fpf_send.py`, `propradar/run_ingest_cron.py`, `fetch_abs_market_signals.py`, `fetch_macro_indicators.py` — `cadence_hours=168, stale_hours=192` + titles on BOTH success and error paths (8 call sites), so one missed week flags rather than the default 10.5 d.
- `ssd_quota_autoresize.py` — RETIRED banner, cron deliberately not reinstated, heartbeat doc deleted.
**Verified:** Process Registry self-reported rows went **63 → 32 OK / 28 KNOWN-GAP / 3 flagged**, and post-fix only genuine items remain. `offmarket_home_signal` re-run succeeds (229 contacts flagged from 248 sessions) where it previously raised.
**Miss worth recording:** my own first-pass audit under-reported by one. I judged staleness as `cadence × 1.5` and missed that the renderer honours an explicit `stale_hours` override — `samantha_seo_improvement` (cadence 168, stale_hours 180, age 188 h) read OK to me but STALE to the board. Re-audited every job carrying a `stale_hours` override; that was the only one mis-classified. It turned out to be a 29th deliberately-paused job (disabled 2026-07-29 by Will, whole weekly SEO process off — distinct from `run_seo_pilot_review.sh`, which is still live Mondays and ran fine Aug 3).
