## [OFFMARKET-DECK-HYDRATION-418] What's-changed block re-introduced render-path date math on the off-market deck — 11:20 AEST
**Symptom:** PostHog `$exception` on `/off-market/*` — Minified React error #418 (`args[]=text`, server/client text hydration mismatch), unhandled. Not a blip and not a traffic artifact: normalised per pageview the rate steps ~10x and stays there. Weekly, `/off-market/*` pageviews vs #418 — 07-26: 101pv/0; 08-02: 128/0; 08-09: 110/0; 08-16: 74/1 (1.4 per 100pv); **08-23: 129/20 (15.5); 08-30: 129/21 (16.3); 09-06: 105/13 (12.4)**. Pageviews are flat across the whole window, so the denominator did not move — the defect rate did. Spread across ~22 distinct property pages and every major browser (Mobile Safari, Chrome, Samsung Internet, Safari desktop), ~1 in 8 pageviews. When #418 fires React discards the SSR subtree and re-renders client-side, on the highest-traffic organic surface we own (705 `offmarket_page_view` in the reward ledger) and one already measured at p75 LCP 11-22s.
**Root cause:** `WhatsChangedSection.tsx` computes dates DURING render, in two places: `selectTimeline()` does `const now = new Date()` and `WhatsChangedAnchor()` does `const today = new Date().toISOString().slice(0,10)`. Both feed rendered TEXT — `today` gates the `past`/`ahead` split behind a visible count ("2 dated changes"), and `now` drives two date-boundary expiry rules that decide whether timeline points render at all. The deck is SSR'd then hydrated, so both run twice against different instants; with Netlify caching the SSR HTML, a response generated before a date boundary and hydrated after it produces different text. This is **the same root cause as [OFFMARKET-DECK-HYDRATION-418] on 2026-07-24**, which fixed it for `computeGainVerdict` by threading a single loader-captured instant. That fix was correct and is still in place — `off-market.$slug.tsx:848` sets `asOfMs: Date.now()` with a comment naming React #418 explicitly, and `HeroSection.tsx:46-59` carries a ⚠ warning to use it. `WhatsChangedSection` moved into Part 03 on 2026-08-13 and simply never adopted it, which is why the rate steps in the week after.
**Fix:** Both call sites now read `new Date(data.asOfMs ?? Date.now())` — the same instant the server used, threaded through serialized loader data — matching the established pattern in the sibling components. Comments at both sites explain why, and name this recurrence so the next person adding a section to this file sees it.
**Files:** Feilds_Website/01_Website/src/pages/OffMarketPage/v4/WhatsChangedSection.tsx
**Verification:** `npm run build` clean; pushed as ONE commit `08fc6bd5` with the fix below (one Netlify build, deploy state `ready`). Headless mobile-Safari UA load of `/off-market/13-prahran-court-robina` — 0 console errors. ⚠ That is a weak positive and is recorded as one: the fault is intermittent (~1 in 8) and boundary-dependent, so a clean single load is consistent with both "fixed" and "did not happen to trigger". The real check is the per-pageview rate over the coming week, against the 12.4-15.5 per 100pv baseline above.
**Recurrence:** 2nd under this exact ID (2026-07-24), and at least the 6th React #418 in this codebase — see [HOUSE-MINI-SITE-003], [HOUSE-MINI-SITE-006], [V3-HERO-DATE-HYDRATION], [GFONT-HYDRATION-418], and the 2026-09-09 `formatArticleDate` entry. The standing lesson from 07-24 was already written and correct ("ANY non-deterministic value read during render is an SSR hydration hazard"); what failed is that it lived in a fix-history file and a comment on two components, and a NEW component added three weeks later did not inherit it. The class keeps recurring because nothing enforces it — a lint rule banning bare `new Date()`/`Date.now()` in the render path of SSR'd route trees would, and does not exist.

## [WALK-NULL-STYLE-AFTER-TEARDOWN] Walkthrough engine dereferenced removed DOM nodes on /news — 11:20 AEST
**Symptom:** `Cannot read properties of null (reading 'style')` (and its minified twin `null is not an object (evaluating 't.style')`) on `/news`, `/news/robina`, `/news/varsity-lakes`, `/news/burleigh-waters`. **9 occurrences in the week of 2026-09-06 and 0 in any prior week** — new with the `[NEWS-V2-SPLIT-LAYOUT]` deploy of 2026-09-06, which mounts `MarketFlowProto` (and with it the walkthrough runtime) on the /news suburb pages for the first time.
**Root cause:** `endWalk()` removes the whole `#walkLayer` subtree — `#wkAvatar`, `#wkCap`, `#wkDim` all go with it — the instant the reader closes the walkthrough. Several routines look those nodes up and dereference them without a guard, and at least one runs on a timer *after* the close is possible: `wkHeadAtChart()` calls its inner `place()` immediately and again via `setTimeout(place, 780)`, and `place()` re-reads `wkEl("wkCap")` on every call. Close the walkthrough inside that 780ms window and the deferred call dereferences a node that no longer exists. `wkStage`, `wkDock`, `wkAvBox` and three `wkEl("walkLayer").appendChild(...)` sites had the same unguarded shape, reachable from any beat that fires after teardown.
**Fix:** `place()` now re-reads and guards BOTH nodes each call and bails if either is gone. `wkStage`/`wkDock` return early when the avatar/caption are absent and null-check `#wkDim` before `classList`. `wkAvBox()` returns a zero rect instead of throwing, because all five of its callers immediately read `.left`/`.top` off the result. The three `walkLayer.appendChild` sites are guarded. All are bail-outs, not behaviour changes — when the layer is mounted every path is byte-identical to before.
**Files:** Feilds_Website/01_Website/src/components/MarketFlowProto/MarketFlowProto.engine.ts
**Verification:** `npm run build` clean; commit `08fc6bd5` (batched with the fix above — one Netlify build), deploy `ready`. Headless mobile load of `/news/robina`: page renders, title correct, 0 console errors.
**Recurrence:** First for this ID. Same *class* as the walkthrough timing faults of 2026-09-08/11/12 ([WALK-ARC-ZOOM-LENDING-SYNC], [WALK-CTA-FOLLOW-SUBSCRIBE], [WALK-INK-VIEWPORT-DRIFT]): the engine is a large imperative DOM runtime whose teardown races its own animation timers. Worth noting the sensor angle — these errors were surfacing in `onsite_friction_signal.py`'s CLIENT_ERROR channel as untriaged noise on a key funnel page, which is exactly the channel that is supposed to catch a real funnel break. Persistent benign errors there degrade the sensor.

## [ADDRESS-SEARCH-NO-REGRESSION-TEST] Address search had no automated check against addresses we actually hold — 11:45 AEST
**Symptom:** Not a fault report — the absence of one. Five distinct address-search failures in six weeks ([ADDRESS-SEARCH-GLENEAGLES] 07-30, [ADDRESS-SEARCH-SLASH-STATE-ZERO] 08-28, street-type variants 08-30, [ADDRESS-SEARCH-INDEX-STALE] 09-06 and the silent zero-result UI in the same entry) all reached production and all were found by a member of the public. Address search is the highest-value action on the site (`searched_address` P(reward) 0.69 vs a 1.5% base rate), and nothing checked it.
**Fix:** New `scripts/address_search_regression.py`. Samples real addresses from the **suburb collections** (never the index — an index-drawn probe is structurally incapable of seeing the 1,843 addresses that were absent from the index in September), types each the way an owner would, hits the live `/api/v1/address-search`, and asserts two floors: `found_pct >= 97` (the address comes back at all) and `first_pct >= 80` (it is ranked first — "3 Cassowary Drive" returning 35/37/39 but never number 3 is the failure that sends an owner a report on a neighbour's house). Rule 7b assertions on all three zero-output paths: 0 probes sampled, >=50% transport failures, and either floor breached.
**Files:** scripts/address_search_regression.py (new)
**Two things it got wrong first, both recorded because they are the interesting part:**
1. Guessed `UNIT_NO`; the real field is `UNIT_NUMBER` (Rule 8 — verified with `db_fields.py Gold_Coast robina --grep UNIT`, 98% fill on UNIT_NUMBER, no `UNIT_NO` path at all). Unverified, every unit probe would have silently tested the *house* at that street number, and the harness would have passed while blind to exactly the 1,002 unit addresses that were the real September failure.
2. First live run scored **0/24 against a site answering every probe correctly** — the comparator did not normalise punctuation, and we store `complete_address` unpunctuated while the API renders it with commas for display. The failure direction was the lucky one: a looser comparator would have reported PASS forever and been worth nothing.
**Verification:** after both fixes, 24/24 found and first; full sweep results in the onsite cycle doc.
**⚠ NOT scheduled, deliberately:** no domain may edit the crontab. `job_run` self-registers unconditionally, so the job records its real outcome to `job_runs` but sets `stale_hours` absurdly high until `--scheduled` is passed — otherwise it would plant a permanently-STALE row on the Process Registry for a cadence nobody signed up to. The cron line should pass `--scheduled`. Scheduling ownership is the open ask in REC-onsite-006.
