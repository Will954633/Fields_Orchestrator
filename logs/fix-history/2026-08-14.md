## [PREWARM-INVISIBLE-TO-ENDPOINT] Pre-warmed reports were written to a collection nothing reads — 09:25 AEST
**Symptom:** A real visitor (PostHog distinct_id `019ffd0b-03d6-749f-8281-1c1fad90e1b1`)
landed on `/off-market/3-ripponlea-street-robina` from Google, read for 110s across 8
sections, clicked "Get the report" at 07:34:42, and left 12s later. No Telegram, no
tracked open, no report. Investigation found the report **had already been pre-built at
06:59 that morning** — 35 minutes earlier — and the click nevertheless triggered a 29s
rebuild that produced a byte-identical file, finishing 20s AFTER the reader had gone.

**Root cause:** Two collections, never joined. `prewarm_offmarket_covers.py` recorded its
output to `system_monitor.offmarket_report_covers`. `offmarket-report-request.mjs` answers
readers from `system_monitor.offmarket_report_requests` and nothing else — its 7-day cache
check (`CACHE_MAX_AGE_MS`, line 118) only ever saw rows the endpoint itself had inserted.
**2,443 finished reports were invisible to the endpoint that serves them**, so every
visitor to a pre-warmed address paid a full rebuild.

A second latent fault sat behind it: the pre-warm never wrote the durable
`/data/blobs/off-market-reports/<slug>/report.pdf`, which is the path the tracked viewer
renders pages from, and never minted an `email_tracking` record. Had the join been made
naively, pre-warmed addresses would have delivered a raw PDF with **no open / page / dwell
tracking** — regressing the exact instrumentation this investigation started from.

**Fix:** One file, `scripts/prewarm_offmarket_covers.py`. Deliberately NO website change —
having the pre-warm write into the collection the endpoint already reads means the existing
cache logic works unmodified, so there is no deploy and no frontend risk.
1. Writes a `status: "completed"` row to `offmarket_report_requests`, keyed `(slug,
   source: "prewarm")` so re-warming refreshes one row and never touches a reader's. No
   `user_agent`/`country`, which is how a pre-warm stays distinguishable in the funnel.
2. Writes the durable `report.pdf` and mints the tracking record, so a pre-warmed report is
   delivered through the tracked viewer with `viewer_url` — instant AND instrumented.
3. `--max-age-days`: `eligible()` previously skipped anything already on disk and so could
   never refresh. Both the substantiation `valid_until` and the endpoint cache are 7 days,
   so without this the warm cache silently expires and never refills.
4. **Failure memory** (`failed_at` + error, 14-day backoff, cleared on success). Without it
   the job cannot get past its own dead ends: a property that CANNOT build never acquires a
   cover, so it was re-selected every run forever — measured, **32 of the first 60 targets**
   were permanently unbuildable against 3.3% of the remainder, and a 25-property test batch
   spent 23 renders re-failing the same addresses.
5. `job_run("offmarket_report_prewarm", cadence_hours=24)` — the script had no heartbeat,
   no cron and no systemd unit. It had been run by hand once and stopped, and nothing
   reported that. Rule 7 gap on the process the whole feature depends on.

**⚠ Two bugs I introduced writing this, both caught only by running it — Rule 7b in
reverse:**
- The outcome assertion was wrong twice. First "0 warmed and any work due" (tripped on one
  property that legitimately had no resolvable hero image). Then "0 warmed and >=20 due"
  (tripped on a batch of 25 that were ALL the same legitimate refusal — unbuildables
  cluster). **No threshold on the count can separate "we correctly declined 25 properties"
  from "the generator is broken"**, because both look like zero output. It now classifies on
  error type via `_EXPECTED_REFUSALS`; unrecognised failures are what goes red.
- That classification then read the **160-char error tail** returned to the caller, which has
  lost the identifying `RuntimeError:` line — so every legitimate refusal counted as
  "unexplained" and **the heartbeat would have gone red every night on a healthy run.** A
  heartbeat that cries wolf is as useless as one that stays silent. Classification now
  happens inside `warm_one` against the full stderr.

## [SUB40-FLOOR-AREA-CONTRADICTION] The page published a number its own valuation had rejected — 10:05 AEST
**Symptom:** `/off-market/2-14-gammon-drive-varsity-lakes` said "We are not going to put a figure on
this home", then listed **"Floor area 20 m²"** under *What the record does say* — for a 3-bed 2-bath
2-car townhouse — and explained the refusal as a shortage of comparable sales.
**Root cause:** Two independent bugs pointing the same way.
1. The loader read `floor_area_sqm` raw. `_resolve_internal_and_building`
   (`precompute_valuations.py:2544`) discards any internal area below `MIN_FLOOR_AREA = 40`, so the
   engine saw *no* floor area and declined with `missing_floor_area` — while the page printed the
   discarded value as fact. The 20 came from an `onthehouse_backfill` on 2026-08-13. Only 4 of 6,633
   onthehouse-sourced areas are sub-40, so the scrape is sound; the display contract was not.
2. `NoFigureSection` computed `missingFloor = !data.floor_area`, re-deriving a verdict the engine had
   already reached. With a truthy-but-rejected 20 it came out false, so the reader got the
   "not enough comparable sales" branch — the wrong cause — and was never asked for the one number
   that would have fixed it.
**Fix:** Floor the area at 40 m² in the loader (`floorArea()`), so every consumer shares the engine's
definition of "has a floor area" instead of three components each deciding for themselves.
`missingFloor` now reads `decline_reason` — the engine's own verdict — keeping `!data.floor_area`
only as a fallback for pre-`exclusion_reason` documents. **52 homes across the three live V4 suburbs
carry a sub-40 area.**
**Files:** `src/routes/off-market.$slug.tsx`, `src/pages/OffMarketPage/v4/NoFigureSection.tsx`
**Recurrence:** Nth for floor-area resolution — cf. `[VAL-FLOOR-AREA]`, `[REGRESSION-FLOOR-AREA]`,
`[UNIT-NUM-ALIAS-EATS-FLOOR-AREA]`, `[FLOOR-AREA-MISSING]`. Every one is the same shape: a second
reader of floor area that does not share the resolver's rules. The fix this time is placement — at
the loader, where there is one of them.

## [CLAIM-PANEL-LATENCY-160S] The first reader to click paid a 145s cache build — 11:55 AEST
**Symptom:** Will tested the panel on `/off-market/5-glenferrie-drive-robina`, entered a floor area,

**Root cause:** `_caches()` was called **on the claim path**, lazily. Building the shared comparable

## [CLAIM-VERIFY-PUBLISH] Verification flow + Record Corrections ops tab — 12:30 AEST
**Symptom:** Not a defect. A corrected record could be computed privately but there was no way to
review one or ever publish it, so the whole feature dead-ended at the review queue.
**Fix — the publish path** (`attribute_claim_poller.publish_one`, status `approved` → `published`):
writes the corrected attribute onto the property document with `attribute_correction` provenance
(shaped like the existing `property_type_correction`), then **REVALUES through the normal engine path**.
**⚠ It deliberately does NOT copy the private `provisional`.** Re-deriving is what makes the published
figure durable: the nightly `batch_value_offmarket` run reads the same document and reproduces the same
answer. Copying would publish a number the nightly job then recomputes from an *uncorrected* document
and silently reverts — the page would flicker back to "no figure" overnight with nothing to explain it.
**Fix — the ops tab** (`/ops-hub-4417` → *Record Corrections*): lists each claim with its private
range, what changed against what we held, session id and status; Approve/Reject wired to
`attribute-claims` (GET) and `attribute-claim-decision` (POST) on `system-monitor.mjs`. The approve
confirm names the address, the exact fields being written, and the range that will go live — approving
is a publishing action and the dialog says so rather than looking like clearing an inbox.
**⚠ An `assumed` (typical-figures) claim can never be published.** It is a suburb median, so it
describes a shape of home, not that home; publishing one would put an average on a page about a
specific property and lend it our measured error rate. **Refused at three layers** — button absent,
API 400, poller refusal — because the error is invisible once live.
**Also:** stale-claim reclaim now returns a crashed publish to `approved`, not `pending`, or a human
approval would be silently discarded and the claim would re-enter the reader queue.
**Verified in production:** approve on an assumed claim → `{"error":"cannot publish a claim built from
typical figures"}`; reject → `{"ok":true}`; unauthenticated approve → `{"error":"Unauthorised"}`; and a
real end-to-end publish on 68 Dipper Drive applied `internal_living_area_sqm: 185`, wrote provenance and
revalued — returning `directional_only / above_design_ceiling`, i.e. **correctly still no public figure**
because that home values above the $2M envelope. Test document reverted to its exact prior state.

`src/pages/OpsPage/panels/AttributeClaimsPanel.tsx`, `src/pages/OpsPage/OpsPage.tsx`

on how many substitutes get plotted on the competitor map. `TARGET_MAX = 6` in
`scripts/property_reports/competitor_matcher.py:64`, applied a *second* time as a literal
`active[:6]` in `comparable_feed.py:257`. It saturates for any normal suburb.

The real measure was already in the same document and unused:
`slots.competitor_map.ranked_comparison.funnel.close_tier` (`n_close`), computed over the FULL
candidate set within `CLOSE_MATCH_THRESHOLD` and a ±50% price guard. It ranges **0–13** across
the mailable pool. V1's number was wrong in both directions — 26 Ballyliffen's posted mailer
claimed 5 where the real count is **7**; 22 Mapleton and 3 Woodland would have claimed 6 where
the true count is **0**. Six of 25 addresses have nothing that closely competes, which V1 was
structurally incapable of saying.

**Fix:** V2 (`11_House_Mini_Site/_shared/mailer_v2/`, entirely separate from V1) reads
`close_tier` everywhere — headline, hero card and page 2 — and adds an `f_no_competition`
finding for the zero case, which is a far stronger hook than a capped 6. The price guard is
only active once a valuation exists, which is a second reason V2's gate requires one.

**Files:** `11_House_Mini_Site/_shared/mailer_v2/{hooks.py,generate_mailers_v2.py,mailer_v2_template.html,README.md}`
**Recurrence:** First for this field. Nth for the family — a plausible-looking field standing in
for the one that means what you want (see [FIELD-NAME-GUESS-FALSE-ABSENCE] 2026-08-09, Rule 8).
The lesson generalises: `len(x)` of a *display* array is never a measurement.

## [MAILER-V2-SILENT-ARTWORK-CLIPPING] Fixed-height A4 pages crop copy with no error — 15:55 AEST
**Symptom:** Generated V2 mailers looked plausible while missing copy. The closing "We also
found…" paragraph rendered *underneath* the absolutely-positioned CTA band; support-card
sub-lines overflowed their card bounds; two labels clipped entirely.

**Root cause:** `.page` is a fixed 210×297mm box with `overflow:hidden`, so content that no
longer fits is neither paginated nor errored — it is cropped. The CTA is `position:absolute;
bottom:0`, so nothing in the normal flow knows it is there. A single extra line of hook copy
silently deletes the last paragraph from the artwork. Because V2 chooses findings per property,
copy length varies per mailer, so this could not be eyeballed once and trusted.

**Fix:** `verify_pdf()` re-reads every generated PDF with `pdftotext` and rejects it
(`<slug>.REJECTED.pdf`) unless it has exactly 2 pages and every load-bearing line is present.
Plus a `.frontbody` padding reservation for the CTA, a fixed-height findings strip so hook
choice cannot shift page geometry, and the support cards relaid horizontally (they had ~55×22mm
stacked, which cannot hold a numeral + wrapped label + two-line sub).

**Two things worth remembering:**
1. **Text extraction proves copy EXISTS, not that it is VISIBLE.** Overlapping text extracts
   perfectly. Character budgets per field are the only guard against a wrapped label rendering
   on top of the line below — that is why both check types are kept.
2. The verifier's own first three failures were verifier bugs, not artwork bugs:
   `text-transform:uppercase`, `letter-spacing` (pdftotext emits `T E M P L AT E`), and
   `&rsquo;` printing as `’` (U+2019) while `strip()` folded it to ASCII `'`. Comparison now
   folds whitespace, case and typographic variants on both sides.

**Files:** `11_House_Mini_Site/_shared/mailer_v2/{generate_mailers_v2.py,mailer_v2_template.html,hooks.py}`
**Recurrence:** First. Result: 25/25 mailable addresses generate and verify clean, 0 rejected.

## [CLAIM-RESULT-DOUBLE-FIRE] One submission, two result events — 13:20 AEST
**Symptom:** The first genuinely verified run produced `shown=1, submitted=1, **result=2**`.
**Root cause:** `clearInterval` stops future ticks but **cannot cancel a fetch already in flight**. At
`POLL_MS = 1200` a slow response leaves two polls outstanding; both resolve as `computed` and both
captured `offmarket_claim_result`.
**Why it mattered more than a stray event:** it would have inflated the completion rate of the very
funnel the instrumentation exists to measure — and inflated it **more the slower the backend got**, so
a latency regression would have read as improving conversion.
**Fix:** a `settled` ref guarding all four settle paths (computed, engine error, timeout, rejected),
re-armed on resubmission. **Verified by delta across one clean run: shown +1, submitted +1, result +1.**
**Files:** `src/pages/OffMarketPage/v4/AttributeClaim.tsx`
**Recurrence:** First. Found only because the events were checked against PostHog rather than assumed
to work once deployed — the bug is invisible in the UI.

## [VERIFY-CHECKS-THAT-PROVE-NOTHING] Two false-positive deploy checks in one day — 13:20 AEST
**Symptom:** Twice I concluded a deploy was live when it was not, and tested stale code.
**Root cause:** (1) polling for a **401** from `/api/monitor/attribute-claims` — but `isAuthorised`
runs **before** path dispatch, so every unknown path 401s; the route did not exist yet. (2) polling for
`grep -q "settled"` in the minified bundle — matched unrelated existing code, so a pre-fix bundle was
re-tested and the double-fire looked unfixed.
**Fix:** poll for a string only the new code can produce (an authed response body containing `"claims"`;
a genuinely distinctive literal), or measure a **delta** that does not depend on detecting the deploy.
**Recurrence:** Second and third instance today. Same shape as `[SUB40-FLOOR-AREA-CONTRADICTION]`:
a check that cannot fail is not a check. Worth remembering as a habit, not a one-off.
