# Fix History — 2026-08-14 (AEST)

## [PREWARM-INVISIBLE-TO-ENDPOINT] Pre-warmed reports were written to a collection nothing reads — 09:25 AEST
**Symptom:** A real visitor (PostHog distinct_id `019ffd0b-03d6-749f-8281-1c1fad90e1b1`)
landed on `/off-market/3-ripponlea-street-robina` from Google, read for 110s across 8
sections, clicked "Get the report" at 07:34:42, and left 12s later. No Telegram, no
tracked open, no report. Investigation found the report **had already been pre-built at
06:59 that morning** — 35 minutes earlier — and the click nevertheless triggered a 29s
rebuild that produced a byte-identical file, finishing 20s AFTER the reader had gone.

**Root cause:** Two collections, never joined. `prewarm_offmarket_covers.py` recorded its
output to `system_monitor.offmarket_report_covers`. `offmarket-report-request.mjs` answers
readers from `system_monitor.offmarket_report_requests` and nothing else — its 7-day cache
check (`CACHE_MAX_AGE_MS`, line 118) only ever saw rows the endpoint itself had inserted.
**2,443 finished reports were invisible to the endpoint that serves them**, so every
visitor to a pre-warmed address paid a full rebuild.

A second latent fault sat behind it: the pre-warm never wrote the durable
`/data/blobs/off-market-reports/<slug>/report.pdf`, which is the path the tracked viewer
renders pages from, and never minted an `email_tracking` record. Had the join been made
naively, pre-warmed addresses would have delivered a raw PDF with **no open / page / dwell
tracking** — regressing the exact instrumentation this investigation started from.

**Fix:** One file, `scripts/prewarm_offmarket_covers.py`. Deliberately NO website change —
having the pre-warm write into the collection the endpoint already reads means the existing
cache logic works unmodified, so there is no deploy and no frontend risk.
1. Writes a `status: "completed"` row to `offmarket_report_requests`, keyed `(slug,
   source: "prewarm")` so re-warming refreshes one row and never touches a reader's. No
   `user_agent`/`country`, which is how a pre-warm stays distinguishable in the funnel.
2. Writes the durable `report.pdf` and mints the tracking record, so a pre-warmed report is
   delivered through the tracked viewer with `viewer_url` — instant AND instrumented.
3. `--max-age-days`: `eligible()` previously skipped anything already on disk and so could
   never refresh. Both the substantiation `valid_until` and the endpoint cache are 7 days,
   so without this the warm cache silently expires and never refills.
4. **Failure memory** (`failed_at` + error, 14-day backoff, cleared on success). Without it
   the job cannot get past its own dead ends: a property that CANNOT build never acquires a
   cover, so it was re-selected every run forever — measured, **32 of the first 60 targets**
   were permanently unbuildable against 3.3% of the remainder, and a 25-property test batch
   spent 23 renders re-failing the same addresses.
5. `job_run("offmarket_report_prewarm", cadence_hours=24)` — the script had no heartbeat,
   no cron and no systemd unit. It had been run by hand once and stopped, and nothing
   reported that. Rule 7 gap on the process the whole feature depends on.

**⚠ Two bugs I introduced writing this, both caught only by running it — Rule 7b in
reverse:**
- The outcome assertion was wrong twice. First "0 warmed and any work due" (tripped on one
  property that legitimately had no resolvable hero image). Then "0 warmed and >=20 due"
  (tripped on a batch of 25 that were ALL the same legitimate refusal — unbuildables
  cluster). **No threshold on the count can separate "we correctly declined 25 properties"
  from "the generator is broken"**, because both look like zero output. It now classifies on
  error type via `_EXPECTED_REFUSALS`; unrecognised failures are what goes red.
- That classification then read the **160-char error tail** returned to the caller, which has
  lost the identifying `RuntimeError:` line — so every legitimate refusal counted as
  "unexplained" and **the heartbeat would have gone red every night on a healthy run.** A
  heartbeat that cries wolf is as useless as one that stays silent. Classification now
  happens inside `warm_one` against the full stderr.

**Measured (this VM, 2026-08-14):**
- Build profile, 20.7s wall on **8.9s CPU** (42% — I/O and subprocess-startup bound, not
  compute bound): Chrome print-to-PDF **12.4s**, Ghostscript `/printer` shrink **4.9s**, data
  pull + HTML + 2 fit-check passes ~8.3s, publish/cover/tracking ~3s. Chrome launches
  **three times** per build, twice only to MEASURE layout. No AI in the path at all — the one
  Vision call (Google Cloud Vision, not Claude/Gemini) is content-hash cached in
  `cover_photo_verdicts` and skipped entirely when the cover resolves to a boundary aerial.
- 3 workers gives only ~1.3x, not 3x: **21.2s/property** at `--workers 3` vs ~29s serial. The
  4-vCPU box saturates; the documented ceiling of 3 is real.
- ~181 eligible properties have **no coordinates and no boundary aerial**, so every hero tier
  fails and the generator refuses rather than print a different house on the cover. That is
  the guard working, not a bug — but those addresses currently offer a button that can only
  ever fail.

**Verification:** 30-property run — `28 warmed, 2 declined, 0 unexplained`, exit 0,
`job_runs` row green with matching metrics. All 24 prewarm rows carry both `pdf_url` and
`viewer_url`. Live production GET for `283-easthill-drive-robina` returns
`status: completed` in 2.9s (the documented per-request Mongo connect) instead of a 29s
rebuild, with `viewer_url` populated; the tracked viewer returns 200 with the correct
address in `<title>` and renders page 1 as a 619KB PNG. ⚠ That curl recorded a real
`viewer_opened` event and fired a Telegram — the event was cleared and the counter reset.

**⚠ A 20-HOUR STALE RUN WAS MANUFACTURING THE BUG THE WHOLE TIME.** While installing the
cron, found `prewarm_offmarket_covers.py --limit 100000 --workers 3` (PID 3211242) running
for **20h03m**, started by an earlier session and holding code loaded before this fix. Of
2,733 built reports, **only 38 were servable**; the other 2,695 had no queue row, no
`report.pdf` and no tracking record. It had no heartbeat, which is exactly why nobody
noticed — and it also silently contaminated every throughput measurement taken during this
session (3 competing workers, so the box was running 6). Stopped it; the script is
resumable by design so nothing was lost.

Recovery needed NO re-rendering — the blob store IS `/data/blobs`, so all 2,695 PDFs were
already on local disk. New `scripts/backfill_prewarm_queue_rows.py` copies each to
`report.pdf`, mints tracking and writes the queue row at ~0.1s per property instead of
~19s. **Result: 38 -> 2,737 servable in minutes.** ⚠ The backfilled rows carry the ORIGINAL
`built_at`, not `now()` — both the endpoint cache and the substantiation records are 7 days,
and stamping them fresh would serve an owner week-old comparables under a claim of currency.
Builds already past shelf life are left for the prewarm to rebuild.

**Also added:** an `flock` (`_acquire_lock`) — once on cron, a scheduled run landing on a
manual fill is 6 concurrent Chromium sets, which per Will is what takes the VM down. Tested:
second instance exits without running. And `data_pull.get_subject` is now memoized per
process (~20 calls per build, each looping the catchment for the identical doc); HTML output
verified byte-identical across baseline and two memoized runs (md5 `2e1d49ab95d6...`).

**Throughput, measured clean after the stale run was stopped:** single build **18.55s**;
3 workers **276/hour** — only **1.4x** serial. The 4-vCPU box saturates (load 6.6), so
parallelism is not the lever; per-build cost is. Remaining structural targets: two of the
three Chrome launches exist only to MEASURE layout, and `pick_highlight` issues 36-84
`count_documents` that `section_01_right` then partly repeats.

**Open, not actioned — 219 eligible addresses cannot build.** 154 HAVE coordinates but no
parcel polygon; the hero chain has no plain-aerial last resort (listing photos -> street view
-> boundary aerial -> cadastral -> refuse), though the SATELLITE chain already falls back to
`auto_static_maps`. Adding that fallback to the cover would rescue all 154, but the
2026-08-13 fix ranked boundary aerial above raw Static Maps precisely because the latter has
no lot outline — the `local_cadastral` ambiguity. That is an editorial call on what we put
in front of an owner, left for Will. The other 65 have no coordinates and need geocoding.

## [SUB40-FLOOR-AREA-CONTRADICTION] The page published a number its own valuation had rejected — 10:05 AEST
**Symptom:** `/off-market/2-14-gammon-drive-varsity-lakes` said "We are not going to put a figure on
this home", then listed **"Floor area 20 m²"** under *What the record does say* — for a 3-bed 2-bath
2-car townhouse — and explained the refusal as a shortage of comparable sales.
**Root cause:** Two independent bugs pointing the same way.
1. The loader read `floor_area_sqm` raw. `_resolve_internal_and_building`
   (`precompute_valuations.py:2544`) discards any internal area below `MIN_FLOOR_AREA = 40`, so the
   engine saw *no* floor area and declined with `missing_floor_area` — while the page printed the
   discarded value as fact. The 20 came from an `onthehouse_backfill` on 2026-08-13. Only 4 of 6,633
   onthehouse-sourced areas are sub-40, so the scrape is sound; the display contract was not.
2. `NoFigureSection` computed `missingFloor = !data.floor_area`, re-deriving a verdict the engine had
   already reached. With a truthy-but-rejected 20 it came out false, so the reader got the
   "not enough comparable sales" branch — the wrong cause — and was never asked for the one number
   that would have fixed it.
**Fix:** Floor the area at 40 m² in the loader (`floorArea()`), so every consumer shares the engine's
definition of "has a floor area" instead of three components each deciding for themselves.
`missingFloor` now reads `decline_reason` — the engine's own verdict — keeping `!data.floor_area`
only as a fallback for pre-`exclusion_reason` documents. **52 homes across the three live V4 suburbs
carry a sub-40 area.**
**Files:** `src/routes/off-market.$slug.tsx`, `src/pages/OffMarketPage/v4/NoFigureSection.tsx`
**Recurrence:** Nth for floor-area resolution — cf. `[VAL-FLOOR-AREA]`, `[REGRESSION-FLOOR-AREA]`,
`[UNIT-NUM-ALIAS-EATS-FLOOR-AREA]`, `[FLOOR-AREA-MISSING]`. Every one is the same shape: a second
reader of floor area that does not share the resolver's rules. The fix this time is placement — at
the loader, where there is one of them.

## [OFFMARKET-BOOK-UNSCHEDULED] A job with a heartbeat, a cadence, and no scheduler — 10:05 AEST
**Symptom:** `batch_value_offmarket.py` — the only writer of `valuation_data` for the off-market book
— last ran 2026-08-08 and had **no crontab entry**. It self-registered `cadence_hours=168`, so the
health board would have shown STALE from ~2026-08-18 onward, permanently.
**Root cause:** Rule 7's heartbeat was added; the scheduling was not. Declaring a cadence is a claim
that something fires the job on that cadence, and nothing did — the book was revalued only when a
human remembered. Its heartbeat also reported `metrics: {}` and the static string "adjusted-comparables
valuations recomputed", so a run that valued nothing was indistinguishable from one that worked (7b).
**Fix:** Nightly at 02:10 AEST (after the 20:30 pipeline and the 00:20 discovery build, so it overlaps
neither). `cadence_hours` 168 → 24. `main()` now returns real counters, and the wrapper **raises when
work was queued and nothing was written** rather than reporting success. Seeded run: 300/300 written,
0 errors, 1.2 min.
**Files:** `scripts/batch_value_offmarket.py`, crontab (02:10 daily)
**Recurrence:** Nth for the 7b pattern — cf. `[BUILDER-ENV-EXPORT-GAP]`, `[INDEXING-SILENT-ZERO]`,
`[PREWARM-COVERS-JOIN]` earlier today. **First** for this variant: not a silent-zero but a silent-
*never*, where the heartbeat was correct and the scheduler was absent. Worth a check across every
`self_registered` job that no other job has the same gap.

## [ATTRIBUTE-CLAIM-PANEL] Readers can now supply the input the method is missing — 10:05 AEST
**Symptom:** Not a defect — the feature the two fixes above made necessary. `missing_floor_area` is
**2,316 of 3,367** valuation declines across the three live suburbs, against 57 for thin comparables.
Those homes are not failures of the method; they are homes we lack inputs for, and the owner has them.
The existing corrections block wrote four booleans to `localStorage` while `NoFigureSection` told the
reader it was "the fastest way to tell us" — so the page was already making a promise it did not keep.
**Fix:** `AttributeClaim` panel shows the record, marks the inputs the engine cannot run without, and
accepts corrections with **no name, email or phone**. `offmarket-attribute-claim.mjs` queues them;
`attribute_claim_poller.py` injects them into the subject document **in memory** at the top of each
resolver chain (`internal_living_area_sqm`, `lot_size_sqm`) and returns a **private range**.
**⚠ The corrected figure is written to `system_monitor.attribute_claims`, never to the property
document.** There is no code path from that collection to the SSR loader, so an unverified figure
cannot reach a public indexed page by someone forgetting a flag. This matters because the page states
a *measured* error rate, and that rate was measured against our inputs — it does not transfer to a
number a visitor typed. Publishing stays manual (`verified: true`).
**Scope guard:** shown only where the record is short by ≤2 required inputs. 2,262 of the 2,316 are
also missing land size; a five-field form on a page reached from search is a form nobody finishes.
**Verified in production:** valid submit → queued; `floor_area_sqm: 20` → rejected at the bound;
Googlebot → well-formed response, no work queued; owner token → range; wrong token → `{"status":"none"}`;
2/14 Gammon still renders "not going to put a figure" with no figure in the HTML and an untouched
document. 5 Glenferrie Drive, Robina — previously unvaluable — returned $1,105,223–$1,412,370 from 43
comparables on one supplied number.
**Files:** `netlify/functions/offmarket-attribute-claim.mjs`, `scripts/attribute_claim_poller.py`,
`src/pages/OffMarketPage/v4/AttributeClaim.tsx` + `.module.css`,
`src/pages/OffMarketPage/v4/NoFigureSection.tsx`, `/etc/systemd/system/fields-attribute-claim-poller.service`
**Recurrence:** First.

## [LOADER-LAND-SIZE-CHAIN] Loader ignored `land_size_sqm`, claiming no land on 6,579 docs — 10:35 AEST
**Symptom:** The new AttributeClaim panel asked readers to supply a land size we already held. The
off-market page reported no land size for **6,579 of 25,217** off-market documents that have one.
**Root cause:** The loader read `lot_size_sqm ?? land_size ?? lot_size`. `land_size_sqm` — **second**
in the engine's own `resolve_land_size` (`precompute_valuations.py:2621`) — was absent, so the engine
saw a land size and the page did not.
**Fix:** Added `land_size_sqm` in the engine's priority position.
**Files:** `src/routes/off-market.$slug.tsx`
**Recurrence:** Second today, same shape as `[SUB40-FLOOR-AREA-CONTRADICTION]` — the page and the
engine each resolving an attribute by their own rules. Found only because building the claim panel
forced a direct comparison of "what we hold" against "what the engine uses". **Worth auditing the
remaining loader fields against their resolvers** — these two were not looked for, they fell out.
