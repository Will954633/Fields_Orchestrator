## [YOURHOME-UNIT-HOUSE-COMPS] Units valued against house comparables — 21:15 AEST
**Symptom:** A unit submitted to `/your-home` received a valuation built from HOUSE sales.
**Root cause:** No dwelling-class gate anywhere in the mini-site build. An attached dwelling
fell through the house tiers to `SlotResolver.valuation_model_range()`, whose query filtered
`listing_status` + `bedrooms` + `sale_price` and **not** property type. Measured on sold
stock, 3-bed house median vs 3-bed unit median: **Robina +27%, Burleigh Waters +26%,
Varsity Lakes +21%**. The tell was three unrelated units sharing one range — the suburb's
house median band.
**Fix:** Three layers.
  1. `_is_attached_dwelling()` using the shared `classify_dwelling` (not a local regex — the
     off-market TS route has its own and they disagree at the edges).
  2. Tier 0 in `working_valuation_range()`: attached dwellings read the unit engine
     (`Gold_Coast.unit_valuations`, written daily 04:30) and **never** fall through to the
     house tiers. Honours the engine's own `publishable` flag, so Burleigh Waters units —
     1,302 of which carry a point estimate — correctly render no figure.
  3. Defence in depth: `valuation_model_range()` now filters comparables to the subject's
     own dwelling class, so the defect cannot return via a new caller.
  Also: the resolver now writes `valuation.model_range = None` + `valuation.no_figure` when
  refusing, because the writer only `$set`s — without it a stale wrong range survives.
**Remediation:** `scripts/property_reports/remediate_unit_valuations.py` (dry-run/apply).
16 attached reports found: **14 repaired** onto the unit engine, **2 cleared** (both
`comparables_too_old`). Verified 0 house-tier figures remain on attached dwellings.
**Files:** `scripts/property_reports/slot_resolver.py`,
`scripts/property_reports/remediate_unit_valuations.py`
**Recurrence:** First on /your-home. The same defect is documented off-market as
`[OFFMARKET-UNIT-THIN-RANGE-HOUSE-COMPS]` — so 2nd for the business.

  - the Process tab's **"For your home"** pane named 13 Terrace Court and quoted a

Relabelled to "Median growth (YoY)", sourced to the suburb's rolling 12-month median.
**Verified live** on 3 reports: zero occurrences of "13 Terrace Court", "Merrimac",
"of 142" or "46-sale". 0 console errors.
**Files:** `YourHomePage.tsx`, `data/homeFixture.ts`, `components/FearSection.tsx`,

## [YOURHOME-VALUATION-STALE] Reports never picked up a later valuation — 2026-08-15 11:20 AEST
**Symptom:** 44 of 106 live reports (42%) showed no working range. Framed initially as a
data gap; it was mostly staleness.
**Root cause:** A report is resolved once at build time, and the nightly job re-runs ONLY
competitor slots (`refresh_property_reports.py:1043` → `refresh_competitor_slots()`). The
valuation engines keep running behind it — `batch_value_offmarket.py` (02:10) writes
`valuation_data`, the unit engine (04:30) writes `unit_valuations`. A property valued AFTER
its report was built never got the result. `25-ballyliffen-court-robina` was built 14 June
against a valuation computed 8 August.
**Diagnosis of the 44:** 25 stale (range already on the property doc) · 16 genuinely unvalued
· 3 subject not findable · **0 genuine "range existed but was ignored"**. An earlier
hypothesis that `27-protea-court-robina` was such a case was WRONG — it is one of 5 reports
with `property_id: None`, so the subject was never loaded.
**Fix:** (1) `refresh_stale_valuations.py` repaired the 25 — coverage **58% → 82%**, verified
live. (2) `SlotResolver.refresh_valuation_slot()` added and wired into the nightly, so
staleness cannot reaccumulate. Tier 0/1 ONLY — never runs the on-demand engine and never
falls back to exterior-evidence or suburb-median, because a nightly job must not quietly
synthesise a figure for a report that legitimately has none. Idempotent; returns {} on no
change. Verified it does NOT synthesise for a report with nothing computed.
**Files:** `scripts/property_reports/refresh_stale_valuations.py`, `slot_resolver.py`,
`scripts/refresh_property_reports.py`
**Recurrence:** First

## [GREP-FALSE-ABSENCE] "Not referenced anywhere" was a bad search — 2026-08-17 14:50 AEST
**Symptom:** I reported that `aerial_boundary_url` was "never referenced in the report
pipeline". It appears five times in `slot_resolver.py`, and the no_llm satellite path
already fell back to it.
**Root cause:** shell `grep` on this VM is ugrep. `grep -rn "aerial_boundary_url" <dir>`
returned NOTHING and exited 0; the same search with `-F` returns five matches. The memory
`ugrep-regex-blowup-vm-lockup` already says to use `-F`/`-P`.
**Why it matters:** this is CLAUDE.md Rule 8 applied to CODE rather than data — an empty
result was read as evidence of absence rather than as a fact about the search. It led to a
claimed finding ("completely unused") that was false, and nearly to duplicating work that
already existed.
**Fix:** use `grep -F` (or `-P`) for literal searches on this VM, and treat a zero-match
result on a string you expect to exist as a failed search until proven otherwise.
