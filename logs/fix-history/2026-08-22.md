# Fix History — 2026-08-22

## [GALLERY-SRCSET-STALE-FOLDER-404] Property galleries blank — srcset derivatives 404 → ORB — 18:15 AEST
**Symptom:** `/property/92-3-robina-town-centre-drive-robina` showed broken-image icons for every one of its 84 photos (and the hero). Will flagged it and asked whether it was isolated or widespread. Curl of the blob originals returned HTTP 200 real JPEGs, so the images existed — but the browser showed nothing.
**Root cause:** The gallery `<img>` uses a `srcSet` of pre-generated WebP derivatives (`NN.480.webp` / `NN.960.webp`) built by `buildPhotoSrcSet` whenever the listing carries `image_derivative_widths`. A 404 inside a `srcset` fails the image and does **not** fall back to `src`, and nginx returns the 404 body as `text/html`, which Chrome ORB-blocks (`net::ERR_BLOCKED_BY_ORB`).
The derivatives were missing because `backfill_image_derivatives.py::collect()` enumerated **`property_images` only**, while the public API (`property.mjs`) builds the gallery from **`photo_tour_order` FIRST**, then `property_images`. When a listing's photos are re-uploaded to a new date-folder, `property_images` moves to the new folder (which gets derivatives + the widths tag) but `photo_tour_order` keeps pointing at the OLD folder, whose derivatives were never generated. For 92/3: gallery served `.../photos/2026-06-18/*` (58 jpgs, 0 webp on disk) while derivatives lived only in `.../2026-08-20/` (64 jpgs, 186 webp). The listing-level `[480,960]` tag then made the browser request 06-18 `.webp` files that 404.
This is a Rule 7b defect: the widths flag *asserts* "derivatives exist for this listing's photos" but only verified one of the two arrays the gallery reads. Recurrence of the srcset system's blind spot (see `[PROPERTY-SRCSET]`, `[LISTING-IMAGE-DERIVATIVES]`).
**Scope:** Confined to listings carrying the widths flag — the 3 target suburbs (Robina, Burleigh Waters, Varsity Lakes), 214 listings, 209 with non-empty flag. Non-flagged listings (all other suburbs) serve originals with no srcset and were never affected. Within the flagged set, only listings re-uploaded to a new folder (folder drift) broke.
**Fix:** Added `_blob_names_served(doc)` to `backfill_image_derivatives.py` and pointed `collect()` at it — it now enumerates the union of `photo_tour_order` + `property_images` (deduped, order-stable), i.e. every folder the API can serve, so a re-upload self-heals on the next nightly run (03:30 cron). Re-ran the backfill for all target suburbs: 214 listings tagged, 255 derivatives written, 0 missing/corrupt. Verified 92/3: all 168 srcset candidates (84×2) now HTTP 200; headless render shows the ORB error gone and the hero + gallery rendering.
**Files:** `scripts/backfill_image_derivatives.py`
**Recurrence:** First for this exact folder-drift cause; the broader srcset/derivative area has prior entries (`[PROPERTY-SRCSET]`, `[LISTING-IMAGE-DERIVATIVES]`, `[DERIVATIVES-JOB-SCHEDULED]`).
**Follow-up (not yet done):** `photo_tour_order` itself is stale on re-uploaded listings (points at deleted-content folders / different photo counts, e.g. 84 vs 64). The derivative fix makes that cosmetically harmless, but the pipeline should refresh `photo_tour_order` to the current folder when photos are re-uploaded. Flagged to Will.

## [AERIAL-HERO-SRCSET-404] Boundary-aerial hero broken on 48 for-sale property pages — 20:40 AEST
**Symptom:** The V2 property page (`?v2=1`, e.g. /property/92-3-robina-town-centre-drive-robina) showed a broken-image icon where the boundary aerial hero should be. `boundary.png` served 200, but `boundary.480.webp`/`boundary.960.webp` returned 404.
**Root cause:** `PropertyHeroV2.tsx` builds a `.480.webp`/`.960.webp` `srcSet` unconditionally for any `.png` aerial URL, and a 404 candidate inside `srcSet` fails the `<img>` outright — it does NOT fall back to `src`. `scripts/batch_render_aerials.py` writes `boundary.png` but never generated the WebP renditions; the derivatives that most listings carried were made by a one-off backfill that was never wired into anything. Every aerial rendered after that one-off (48 live for-sale listings across the 3 target suburbs) therefore shipped a broken hero. Same failure class as [GALLERY-SRCSET-STALE-FOLDER-404] earlier today, different image.
**Fix:** (1) Added `ensure_derivatives()` to `batch_render_aerials.py` calling `shared/image_derivatives.make_derivatives_from_disk` after every render AND on the skip path, so a previously-rendered aerial self-heals its missing renditions; surfaced a `derivatives_written` metric on the `job_run` heartbeat. Source is ~1280px and derivatives never upscale, so it emits exactly the 480+960 the hero advertises. (2) Ran a no-cost backfill over the 3 target suburbs' for-sale aerials: 48 newly fixed, 79 already OK, 0 errors. Verified `boundary.480/960.webp` now serve 200 `image/webp` via the CDN and the V2 hero renders the aerial (headless screenshot).
**Files:** `scripts/batch_render_aerials.py`
**Recurrence:** First
