### [NEWS-MOBILE-SCROLL] — a duplicate CSS rule inside one media block

**I blamed the Data Insights Strip.** Wrong — it clips correctly
(`overflow: hidden`, `scrollWidth 390 == clientWidth`). Then I blamed a grid
blowout, then flex `min-width: auto`. Each candidate was applied to the live page
and measured: 591 → 469 → 469. Neither reached the viewport, so neither was the
cause.

**Actual root cause:** `@media (max-width: 768px)` contains **two** rules for
`.imageSection`. The first (grouped with `.heroSection`, `.featuredSection`) sets
`grid-template-columns: 1fr`. A second rule ~20 lines later in the SAME block
sets `repeat(2, 1fr)` and, being later, wins — silently undoing the intended
single-column phone layout. Slot content has a ~267px min-content width, and
`1fr` is `minmax(auto, 1fr)` whose `auto` minimum will not shrink below that, so
two tracks forced the document to **591px inside a 390px viewport**.

**Fix:** the later rule becomes `minmax(0, 1fr)` — single column, and able to
shrink below min-content if the content ever grows. Two-up still applies at
`max-width: 1024px`, where there is room.

**Verified:** document scrollWidth exactly equals viewport at **360 / 390 /
414px**; desktop unchanged at 4 columns.

### [GFONT-HYDRATION-418] — an attribute mismatch, not a text one

**I told Will this was the Data Insights Strip's SSR placeholder
("Loading market data…" vs real data). Wrong, and wrong because of a bad
instrument:** I had diffed server HTML against a *settled* client DOM, which
surfaces every async change, not just hydration faults. An async fetch replacing
a placeholder is expected and is NOT a mismatch.

**Correct instrument — a React dev build**, which names the mismatch:

```
<link id="gfont" rel="stylesheet"
+     media="print"     <- what React rendered
-     media="all"       <- what was actually in the DOM
```

`root.tsx:143` runs an inline async-CSS script that flips `media` to `all` once
the stylesheet loads. It executes during head parse, so on a slow page it mutates
the DOM **before React hydrates** — hence intermittent, and only on heavier pages.

**Fix:** `suppressHydrationWarning` on the `<link>` — the element is
intentionally mutated outside React's control.

**Prediction I got wrong, in the good direction.** The dev warning also showed a
`<script>` diff, which I attributed to PostHog's loader inserting a node into
`<head>` before hydration. I told Will #418 would likely survive the gfont fix
and need an analytics refactor. It did not — **#418 is gone on all four
viewports**. The script diff was part of the same cascade (React prints the tree
around the first mismatch), not an independent fault. No analytics change needed.

**Deliberately NOT done:** loading PostHog as an npm module. `posthog-js` is not
installed and `src/utils/posthog.ts` documents why the script tag was chosen —
"the npm module import creates a dead reference on the server that persists
through hydration". Reversing that would risk business-critical analytics that
fail silently. Moot now that #418 is fixed.

## [V3-HERO-DATE-HYDRATION] I introduced React #418 while fixing the above — 17:05 AEST

## [ADDRSEARCH-NO-RANKING] Address autocomplete returned Mudgeeraba for almost everything — 14:05 AEST

**Symptom:** Will reported the unlock dropdown "is only showing addresses for
Mudgereebah". Reproduced and it was broader than that — the endpoint had no
relevance ordering at all:

| Query | Old result |
|---|---|
| `25 H` | 3× Mudgeeraba + 3× Worongary — **none contain a street starting with H** (they matched the "h" inside "LeviatHan") |
| `1 Ma` | `11/20 Douma Drive` — the "ma" buried inside "Douma" |
| `Smith` | Same address listed twice ("Smith Street, Arundel", "183 Smith Road") |
| `Robina` | "Robina Parkway, **Merrimac**" ranked above every actual Robina address |

**Root cause:** three separate things, one dominant.

1. **No sort.** `searchIndex()` did `.find(mongoQuery).limit(6)` with no `.sort()`.
   Mongo returned *natural (insertion) order*, and `address_search_index` was
   built suburb-by-suburb with **Mudgeeraba inserted first**. So the first six
   loose matches were Mudgeeraba on essentially any broad query. This is the
   whole of the reported symptom.
2. **The matcher regex is deliberately loose** and must stay that way — it joins
   tokens with `.*` and characters with `\s*` so "Gleneagles" finds the stored
   "GLEN EAGLES". (A seller at 120 Glen Eagles Drive searched that ~40 times on
   2026-07-30, got nothing, and never reached their mini-site.) Looseness is
   fine *provided tight matches are ranked to the top* — which nothing did.
3. **1,774 addresses are duplicated in the index**, up to **151×** for
   "106 SURF PARADE BROADBEACH" — one row per apartment with the unit number
   stripped. Indistinguishable in a dropdown.

Note `is_target_market` could not be used as the ranking signal: it is `true` on
**39,639 of 86,223** rows — most of the Gold Coast, Mudgeeraba included.

**Fix:** kept the loose regex as the *matcher*, added a *ranker*.
- Over-fetch `limit * 25` (capped 150–400) candidates, then score and sort.
- Scoring: exact street-number match (+120) > unit form `25/21` (+90) >
  number prefix (+30); whole-word token (+70) > word-start, `\s*`-aware so
  "Gleneagles" still scores against "GLEN EAGLES" (+50) > buried mid-word (+4);
  core suburb Robina/Varsity Lakes/Burleigh Waters (+40); street-level rows with
  no house number (−25), since someone entering *their home* needs a property.
- Dedupe by normalised address, keeping the best-scoring row.
- Added a projection to the 12 fields the mapper actually reads.

**Cost, measured rather than assumed.** The over-fetch tripled latency
(206ms → 825ms on "25 H"). I expected the projection to recover it; it did not
(825 → 628ms). The cost is the **scan**, not the payload — the collection has
only an `_id_` index, so the regex scans, and latency tracks candidates
*requested*, not returned. I had scaled the pool off `limit`, which meant
`/analyse-your-home` (limit=50) silently paid a 400-candidate scan: 412 → 848ms.
Changed to a **flat 150** so every caller shares one ceiling (~630ms worst case).

**Known limitation, stated rather than hidden:** 150 is not a converged pool. On
broad queries ("Robina", "1 Ma") the top 6 still shift between a 110- and a
150-candidate pool, because candidates arrive in natural order and are a biased
sample. Broad queries have thousands of equally valid matches so any six are
arbitrary; narrow queries are fully converged and exact ("5 Chantilly" = 2
matches, "12 Park" = 22, "Smith" = 18). Making broad queries deterministic needs
a real text index or a prefix-anchored search field — a separate piece of work,
not a bigger scan.

**Net:** ~410ms slower, in exchange for results that are correct instead of
wrong. Worth flagging to Will rather than deciding silently.

**Verified live** on the branch preview — every case above now correct, and
"Gleneagles" returns Glen Eagles Drive, Robina.

**Recurrence:** First for ranking. Second time this endpoint has cost real
seller leads (the 2026-07-30 Glen Eagles case was the first).

## [V3-NEON-BALLAST-CONTINUOUS] Neon hum audible in situ — 20:05 AEST
**Symptom:** Sign silent on Android, audible on laptop. Two wrong guesses first (harmonics, page
weight), then a wrong-but-reasonable one (context born outside a gesture).

every dropout and only reached full gain on the brightest frames. Over a take that is mostly dark

## [V3-NEON-TOUCHSTART-NOT-ACTIVATION] Neon sign silent on Android — touchstart grants no user activation — 12:10 AEST
**Symptom:** On Will's Android phone the card-11 neon sign lit and pulsated on
arrival (visual take correct) but produced no sound at any point — before,
during or after. The glass-shatter sequence and voice-over, triggered by
*clicking* the same sign, played perfectly. All seven isolated tones in
`audio/neon-sound-test.html` were audible on the same handset, so neither the
recipe, the level nor the speaker was at fault.

**Root cause:** `neon_cta.js` armed its AudioContext from
`["pointerdown","touchstart","keydown"]` and treated "an input event fired" as
"a user activation exists". On Android these are not the same thing: a finger
going down may be the start of a scroll, so Chrome withholds activation until
the gesture resolves as a tap — activation lands on `touchend` / `pointerup` /
`click`, none of which were being listened for. So the first scroll fired
`touchstart`, `arm(true)` rebuilt the context with no activation to honour it,
and `bornInGesture` latched **true on a lie**. From that moment the rebuild path
was dead: every later gesture — including real taps on the chapter cues — found
`bornInGesture === true` and rebuilt nothing, leaving a context that was
suspended (or "running" and mute) for the rest of the session with no way to
recover. The glass audio was unaffected because its context is created inside a
genuine `click` handler.

**Fix:** Ask the browser instead of inferring. `arm()` now tests
`navigator.userActivation.isActive` (falling back to the caller's flag on
Safari < 16.4) and only sets `bornInGesture` when activation is genuinely live;
it also rebuilds when a context it believed in is not actually `running`. The
listener list gained the events that really do grant activation on a handset —
`pointerup`, `touchend`, `click`, `keyup`. Verified headless: a trusted
`touchscreen.tap` now produces `rebuilds 1`, `ctx running`, `born true`, and the
take runs with `humGain 0.059 → 0.090` over 309 frames.
