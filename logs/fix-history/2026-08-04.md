## [V3-HERO-DATE-HYDRATION] I introduced React #418 while fixing the above — 17:05 AEST

**Symptom:** after the change, `/for-sale-v3` threw `Minified React error #418`
(hydration text mismatch) on **every** visitor path. Production threw none.
**This was my regression, caught only because I diffed server HTML against the
hydrated DOM instead of trusting that the fix worked.**

**Root cause:** `HeroV3` rendered
`new Date().toLocaleDateString('en-AU', {...})` with **no `timeZone`**. Netlify
functions run in **UTC**, visitors are in **AEST**. The diff was exact:

```
line 12  SERVER: "3 August 2026 · Updated daily"
         CLIENT: "4 August 2026 · Updated daily"
```

A latent bug, not a new one — production never rendered `HeroV3` server-side
(it rendered the loading branch), so nothing ever compared the two.

**Fix:** pinning the timezone alone is NOT sufficient — the route is CDN-cached
with `stale-while-revalidate`, so HTML rendered before midnight is served after
it and a client recomputing the date would disagree again (a ~10-minute window
every night). The date is now computed **once in the loader** and passed down as
`renderedDate`; `brisbaneDateStr()` (timezone-pinned) remains the fallback for
non-SSR use. Server and client cannot diverge by construction.

## [ADDRSEARCH-NO-RANKING] Address autocomplete returned Mudgeeraba for almost everything — 14:05 AEST

**Symptom:** Will reported the unlock dropdown "is only showing addresses for
Mudgereebah". Reproduced and it was broader than that — the endpoint had no
relevance ordering at all:

| Query | Old result |
|---|---|
| `25 H` | 3× Mudgeeraba + 3× Worongary — **none contain a street starting with H** (they matched the "h" inside "LeviatHan") |
| `1 Ma` | `11/20 Douma Drive` — the "ma" buried inside "Douma" |
| `Smith` | Same address listed twice ("Smith Street, Arundel", "183 Smith Road") |
| `Robina` | "Robina Parkway, **Merrimac**" ranked above every actual Robina address |

**Root cause:** three separate things, one dominant.

1. **No sort.** `searchIndex()` did `.find(mongoQuery).limit(6)` with no `.sort()`.
   Mongo returned *natural (insertion) order*, and `address_search_index` was
   built suburb-by-suburb with **Mudgeeraba inserted first**. So the first six
   loose matches were Mudgeeraba on essentially any broad query. This is the
   whole of the reported symptom.
2. **The matcher regex is deliberately loose** and must stay that way — it joins
   tokens with `.*` and characters with `\s*` so "Gleneagles" finds the stored
   "GLEN EAGLES". (A seller at 120 Glen Eagles Drive searched that ~40 times on
   2026-07-30, got nothing, and never reached their mini-site.) Looseness is
   fine *provided tight matches are ranked to the top* — which nothing did.
3. **1,774 addresses are duplicated in the index**, up to **151×** for
   "106 SURF PARADE BROADBEACH" — one row per apartment with the unit number
   stripped. Indistinguishable in a dropdown.

Note `is_target_market` could not be used as the ranking signal: it is `true` on
**39,639 of 86,223** rows — most of the Gold Coast, Mudgeeraba included.

**Fix:** kept the loose regex as the *matcher*, added a *ranker*.
- Over-fetch `limit * 25` (capped 150–400) candidates, then score and sort.
- Scoring: exact street-number match (+120) > unit form `25/21` (+90) >
  number prefix (+30); whole-word token (+70) > word-start, `\s*`-aware so
  "Gleneagles" still scores against "GLEN EAGLES" (+50) > buried mid-word (+4);
  core suburb Robina/Varsity Lakes/Burleigh Waters (+40); street-level rows with
  no house number (−25), since someone entering *their home* needs a property.
- Dedupe by normalised address, keeping the best-scoring row.
- Added a projection to the 12 fields the mapper actually reads.

**Cost, measured rather than assumed.** The over-fetch tripled latency
(206ms → 825ms on "25 H"). I expected the projection to recover it; it did not
(825 → 628ms). The cost is the **scan**, not the payload — the collection has
only an `_id_` index, so the regex scans, and latency tracks candidates
*requested*, not returned. I had scaled the pool off `limit`, which meant
`/analyse-your-home` (limit=50) silently paid a 400-candidate scan: 412 → 848ms.
Changed to a **flat 150** so every caller shares one ceiling (~630ms worst case).

**Known limitation, stated rather than hidden:** 150 is not a converged pool. On
broad queries ("Robina", "1 Ma") the top 6 still shift between a 110- and a
150-candidate pool, because candidates arrive in natural order and are a biased
sample. Broad queries have thousands of equally valid matches so any six are
arbitrary; narrow queries are fully converged and exact ("5 Chantilly" = 2
matches, "12 Park" = 22, "Smith" = 18). Making broad queries deterministic needs
a real text index or a prefix-anchored search field — a separate piece of work,
not a bigger scan.

**Net:** ~410ms slower, in exchange for results that are correct instead of
wrong. Worth flagging to Will rather than deciding silently.

**Verified live** on the branch preview — every case above now correct, and
"Gleneagles" returns Glen Eagles Drive, Robina.

**Files:**
- `01_Website/netlify/functions/address-search.mjs`

**Recurrence:** First for ranking. Second time this endpoint has cost real
seller leads (the 2026-07-30 Glen Eagles case was the first).

**Note — this is a production bug, not a rebuild bug.** The same endpoint backs
`/analyse-your-home`, the front door of the seller funnel. The fix currently
sits on `august-2026-rebuild` only; it is worth cherry-picking to `main`
independently of the rebuild merge.

### Process note: my md5 verification was wrong, not the push

Post-push verification reported MISMATCH. The push was byte-correct — chaining
`gh api --jq .content | tr -d '\n' | base64 -d | md5sum` in one pipeline gave a
bad digest. Writing the decoded bytes to a file and using `cmp` matched exactly.
**Decode to a file, then `cmp`** — do not chain into `md5sum`. This is the
second time this session the *instrument* was wrong rather than the code
(cf. `[TEST-SYNTHETIC-CLICK]` on 2026-08-03).

## [V3-FRUIT-MOBILE] Fruit roll did not animate on phones — 09:55 AEST
**Symptom:** Will: "perfect on my laptop. tried it on my phone and it doesn't animate."
**Root cause:** I disabled it below 900px on purpose — `.colFruit` was `display:none` there, so
there was no target to roll to. But the original beach-card concept HAD handled phones (mobile
rest at 30% across / 82% down card 04, plus bottom padding so the copy clears it); I disabled
rather than ported, again.
**Fix, and three real bugs it exposed:**
1. `.colFruit` now renders on mobile as an in-flow box with `order:2`, so it drops below the
   copy — which is also the reading order: told why the distance matters, then the thing that
   fell out of the tree arrives underneath it. One code path for both breakpoints.
2. **The fall was anchored in DOCUMENT space**, so the fruit hit its final y at p=0.44 and then
   sat there while the viewport spent the other 56% catching up. On a phone that put it 1220px
   down an 844px screen — it vanished mid-flight and reappeared at the end. (Desktop hid this:
   span 890 vs viewport 900, so the geometry was gentle enough to look fine.) The ground is now
   SCREEN space, `scrollY + innerHeight/2`. Not arbitrary: `s1` is defined as the scroll at
   which the target is centred, so at p=1 that expression IS `to.y` exactly — it arrives with
   no correction term.
3. **Aimed at the column, not at the fruit.** On mobile the column is full-width and the fruit
   is left-biased inside it, so target and resting place were 16% of the viewport apart and it
   jumped sideways on landing. Now measures the resting `<img>`, which is in the layout from
   the start with its final width already set.
Also: mobile rest is left-biased (~34%) not centred, because the fruit starts at 54% and a
centred rest gives 4% of travel — and rotation is distance/radius, so 4% is a drop, not a roll.
Spin now derives from actual displacement rather than `px` x span, so any future lateral kick
follows for free. Rest box is sized at measure time, not on landing, so it cannot shift the copy.
**Verified** (iPhone 390x844 + laptop 1440x900): phone travels 54%->35% with 104° of rotation,
laptop 73%->32% with 438°; both land in view, patch on, canvas removed, no horizontal scroll,
no page errors.
**Known, flagged to Will:** mobile rolls about a quarter turn vs desktop's 1.2 turns — the
viewport is simply narrower. A lateral kick (bounce right, then roll back left) would roughly
double it. And mid-flight the fruit passes over the body copy on mobile, since a single column

## [V3-FRUIT-KICK] Lateral kick to double the mobile roll — 10:30 AEST
**Symptom:** Follow-up to [V3-FRUIT-MOBILE]. Mobile turned ~104° against desktop's ~440°
because a narrow viewport leaves almost no horizontal distance, and rotation is distance/radius.
**Fix:** Phones only — on first ground contact the fruit is kicked right, then rolls back left
to its resting place. `kickPx = min(innerWidth * 0.13, 70)`, shaped `sin(pi * u^0.65)` over
first-contact -> settled. `u^0.65` puts the peak at ~1/3 rather than halfway, so it squirts out
on impact and spends the rest of the journey rolling back, which is the part worth watching.
Zero at both ends, so the landing stays exact with no correction term. Desktop gets none: it
already turns 1.2 times and the only room it could kick into is the copy.
No new spin code — rotation was already derived from actual displacement rather than progress
x span, so the kick (and its reversal) followed for free.
**Measurement error worth recording:** I first reported the kick as a failure — "104° -> 107°,
barely moved". I was measuring angular RANGE (max minus min), but what a reader perceives is
ACCUMULATED turn, and the leftward base travel partly cancels the rightward kick in a range
metric. Summing |delta| per frame: **104° -> 191°**, which is the doubling asked for. The
motion was right the first time; the instrument was wrong. Range is only equal to accumulated
turn when the path is monotonic — which it was before the kick, and is not after.
**Verified:** iPhone 390x844 and a 360x740 Android — path bulges 54% -> 60% -> 35%, sprite
x-extent 68..284 of 390 and 64..264 of 360 so it never clips, lands centred at 34-35%, patch
on, canvas removed, no horizontal scroll, no page errors. Laptop unchanged at 440°.
**Files:** `15_Off-Market/Page_Redesign_V3/preview/fruit_roll.js`
**Recurrence:** First.
