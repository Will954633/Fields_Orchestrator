## [COMPS-DISPLAY-ORDER] /property comparable cards now shown most-comparable first — 07:56 AEST
**Symptom:** On `/property/:id` the 8 comparable cards under the valuation range were NOT ordered by comparability — top-left was not the closest match. Order was effectively arbitrary to the reader (current-listing comps first, then sold, each in DB/query order), so the grid layout carried no meaning and a viewer couldn't read rank from position.
**Root cause:** `select_quality_comps` ranks candidates by quality to pick WHICH 8 to show, but the display array is built from `included_points = [p for p in all_enriched_points if included_in_valuation]` (precompute_valuations.py:4045), which preserves the enriched-pool order, not the ranking. The whole chain downstream preserves array order (properties-for-sale.mjs:520 passthrough → comparables.ts normaliseComparables no sort → PropertyComparablesV2.tsx comps.map).
**Fix:** After `normalize_weights(included_points)`, sort `included_points` in place by `weight.raw_weight` descending (raw_weight is invariant to the later re-normalisation of shared point objects and ranks by the same 6-factor composite). Display-only: the range/reconciled figure is computed from the whole pool via `calculate_confidence(_estimate_points, …)`, never from `included_points`, so the valuation is provably unchanged. Verified by running the real engine on 4 live Robina listings — all now DESCENDING BY WEIGHT: True, ranges healthy/non-directional.
**Files:** 07_Valuation_Comps/precompute_valuations.py (pushed to Will954633/Fields_Orchestrator @ b6b2a993). NOTE: the copy in Will954633/Website_Version_Feb_2026 is stale (~200 lines behind, pre-Aug-2026 hardening) and was deliberately NOT updated — it is not the live source and a one-line patch there would misrepresent it as current.
**Deploy:** Takes effect on the next nightly valuation recompute (20:30 AEST) or a manual `precompute_valuations.py` run; not yet live on `/property` at time of writing.
