## [RENTAL-AS-SALE-PARSERS] Closed the deferred half of the rental-as-sale class — 7 parsers hardened — 07:37 AEST
**Symptom:** None visible. This is the item `[RENTAL-AS-SALE-DEEP]` (2026-08-10) deliberately left

**Root cause:** Every price parser in the estate was written independently. There was no shared price
helper and **no rent guard anywhere in the codebase** (`grep` over `shared/` and

   reaches the comparable feed and the nightly report refresher, not just the valuation engine.
3. `assemble.num` was **miscounted as a parser**. It is a *formatter* — it returns the string

## [DR-OUT-OF-TREE-BLINDSPOT] The valuation engine ran from a directory no backup check scanned — 08:05 AEST
**Symptom:** GitHub's copy of the house valuation engine was **254 lines divergent** from the file
that actually runs (4,356 vs 4,480 lines) — and nothing anywhere reported it.

**What the divergence actually was:** the 2026-08-12 `[VALUATION-UNKNOWN-ASYMMETRY]` fix (unknown
attributes silently marking subjects down, worth up to $120k on water views). It edited the live file
and never reached GitHub. Confirmed by diffing the hunks against that entry — the `_LEGACY_UNKNOWN`
guards are exactly it. **Shipped behind `VALUATION_UNKNOWN_HARDENING=1`, default OFF**, so syncing it
changes no production behaviour; that entry verified the default path unchanged (MAE 9.1% both sides).

**Root cause — three failures stacked, none of which alone would have done it:**
1. **The live engine lives outside every repo `check_unpushed_code.py` scans.** `REPOS` covers
   `/home/fields/Fields_Orchestrator` and `/home/fields/Property_Data_Scraping`.
   `/home/fields/Feilds_Website/` — where the engine actually runs, per CLAUDE.md — is scanned by
   **nothing**, and has no local `.git` at all.
2. **Someone worked around (1) by hand-copying the file into the orchestrator repo** at a mirror path
   and pushing it. A copy is a thing that can drift, and it did.
3. **That mirror was later deleted from the working tree, and the deletion was silent.**
   `code_files()` filters with `os.path.isfile()`, so a tracked-but-missing file is skipped with no
   output. GitHub's copy then looked authoritative while the file that ran lived somewhere else.
   Rule 8 applied to backups: an empty result asserted nothing.

**Fix (`scripts/check_unpushed_code.py`):**
- **`EXTRA_FILES`** — a first-class concept of an out-of-tree live file that claims a path inside a
  repo. It points at the **LIVE path, not a copy**, which is the whole point: there is no second file
  to drift. `classify_extra()` compares by content hash; `push_repo()` takes a `localmap` so the
  bytes come from the live file while the commit lands at the repo path.
- **`ghost_files()`** — tracked paths with no file on disk are now printed instead of silently
  dropped. Reported, not alerted (most ghosts are ordinary uncommitted deletions), but a stale mirror
  can no longer hide in the gap.
- **`secret_hits()` refactored to take an absolute path** rather than `(repo, rel)`, so out-of-tree
  files go through the same credential gate. A bypass route must not also bypass the secret scan.

**Verified — the guard fires, rather than just happening to read clean once:**

|---|---|
| unchanged live file | IN SYNC |
| drifted copy | **MOD** (caught) |
| live file vanished | **MISSING** (caught — not silently skipped) |
| path absent on GitHub | **NEW** |
| secret in an out-of-tree file | **BLOCKS** |

Then synced: commit `025d5dc8`, byte-verified, and the checker now reports the engine in sync.

**Follow-up (08:40, actioned on Will's go-ahead) — one live file now has exactly one backup path.**
Deleted the superseded root-level mirror `precompute_valuations.py` from the DR repo

**Two flaws found in my OWN fix while verifying the deletion** — both the same class of error this
entry is about, caught only because I re-read the output instead of trusting one clean run:
1. **`ghost_files()` read the LOCAL index** (`git ls-files -d`). That is the exact source this
   file's own docstring calls untrustworthy — nothing commits locally and `git push` hangs, so the
   index has drifted. Now reads `origin/main`, which is what actually holds the backup. The switch

2. **A path covered by `EXTRA_FILES` was listed as a ghost too**, so the valuation engine printed

**How the second mirror was found:** the new ghost report surfaced it on its first run — a

last touched 2026-08-05, vs 198,984B at the `07_Valuation_Comps/` path). Two backup copies of one
live file, both stale, is how the "which copy is real?" trap gets rebuilt. Deleted — see the
follow-up above. The check paid for itself on the run that introduced it.

## [V4-DEPTH-MISLABELLED] `deepest_section` measured where readers LEFT, not how far they got — 10:35 AEST
**Symptom:** Analysing the first 3 days of V4 reading telemetry (13 exit events on detached
houses), the three deepest reads on the site — 100% scroll, 94-193s engaged, 9-11 sections —
all reported `deepest_section: "hero"`, `deepest_index: 0`. The three shallowest sessions
reported the same thing. The field could not distinguish a complete read from a bounce.
**Root cause:** `sendExit()` assigned `deepest_section: s.lastSection`. `lastSection` is
reassigned on EVERY section change (`settle()`), so it tracks the current section and moves
backwards. Readers who reached the bottom and scrolled back up to re-read the hero — which is
what all three deep readers did — recorded `hero`. Depth is a high-water mark and was never
tracked as one. The same wrong value was sent to the `offmarket-intent-alert` Telegram beacon,
so Will's deep-read alerts have been reporting the exit point as the depth reached.
**Fix:** Track `deepestSection`/`deepestIndex` as an explicit max in `settle()`. Exit event now
carries `deepest_*` (furthest reached), `exit_*` (where they left — the drop-off answer, which
is what the old field actually held) and `scrolled_back` (deep then back up; a re-read signal
worth having on its own). Alert payload carries both.
**Files:** `01_Website/src/pages/OffMarketPage/v4/useReportAnalytics.ts`
**Recurrence:** First. Related: [WHATS-CHANGED-SHIPPED] 2026-08-10 shipped this telemetry.

   visitors, so a change that makes MORE people bounce instantly makes the average look BETTER.
   ⚠ My own earlier power calculation (mean 43.9s, sd 46.5) was computed over these ladder markers,
   not durations, and was therefore invalid. Corrected before it was acted on.
2. **`property_view` double-fired.** The effect depended on `[id, property?.suburb]` and `suburb` is
   undefined until the client fetch resolves, so it ran twice — 199 of 253 session+property pairs had
   exactly 2 events, ~2-4s apart, the first with no suburb. Every count built on it was ~2x inflated
   and any suburb filter dropped half the data. The same dependency also tore down and rebuilt the
   scroll/time instruments mid-visit, restarting the clock from fetch-resolve and allowing duplicate
   scroll milestones.
3. **Variant assignment races the early events.** `$feature/*` is present on 99% of `time_on_page`
   but only **66% of `property_view` and 38% of `$pageview`** — they fire before flags load.
**Fix:** New `phTrackPageEngagement()` in `src/utils/posthog.ts` — continuous `max_depth_pct` and
`engaged_seconds` (gated on document visibility, so a hidden tab is not counted as reading), emitted
via the existing `phCaptureOnExit`/sendBeacon on `visibilitychange`, `pagehide` AND SPA unmount. Both
tracking effects on `PropertyPage.tsx` now depend on `[id]` only, with suburb read through a ref so a
late fetch enriches events without re-running the effect; `property_view` waits on `phOnFlagsReady`
with a 2s fallback so a blocked SDK loses the variant rather than the event.
⚠ `page_engagement` may emit more than once per visit (tab hidden then restored). **Take the MAX per
session+page+property_id — never sum, never average raw rows.** Documented on the helper.
**Also created:** PostHog flag `property_page_v2` (id 817007), control/v2 50/50 at 100% rollout. No
code branches on it yet, so it is inert — deliberately, so an **A/A period can validate balance and
instrumentation before any traffic is spent on the real comparison.**

the touched files — the 10 errors in `PropertyPage.tsx` are all pre-existing (lines 637+, none at the
edited sites), none in `posthog.ts`. ⚠ Not yet verified in a browser — `page_engagement` has not been
observed arriving in PostHog. That is the next gate before trusting it.

## [COVER-PHOTO-AGENCY-WATERMARK] Competing agency's watermark on report covers — 11:45 AEST
**Symptom:** An audit of 43 pre-warmed covers found `1 Highgate Lane` carrying
**"PRD nationwide Robina"** across the photo, directly beneath the Fields logo. Scraped Domain
listing photos belong to the listing agency and frequently carry its watermark. A second issue
in the same audit: listing photo #1 is often a kitchen, lounge or deck rather than the home.
**Root cause:** The hero chain prefers `auto_apr01` / `auto_scraped` (Domain CDN photos) and had
no notion of whether a photo was fit to publish — only whether it downloaded and exceeded 2 KB.
**Scale (measured over 149 real hero images):** 11% are unfit; **4.0% carry competing-agency
branding** — roughly 310 covers across the 7,730 eligible properties.
**Fix:** New `scripts/appraisal_template/cover_photo_gate.py` — one Google Vision call
(LOGO_DETECTION + TEXT_DETECTION + LABEL_DETECTION) per photo, reusing the service-account auth
already built for `floor_plan_debrand.py`. Rejects agency logos, agency names from the existing
`floor_plan_agencies.txt`, marketing text, phone numbers, and interiors. Rejected photos fall
through to the **boundary aerial**, which is ours, never watermarked, and always the subject lot.
Deliberately does NOT inpaint: `floor_plan_debrand` can, because a floor plan is a line drawing
with margins; content-aware removal on photography is far riskier and a smudged patch is worse
than no photo.
**Two calibration errors of mine, both found by looking at the rejected images:**
1. `pool > exterior` rejected four GOOD covers — pool in front of a clearly visible two-storey
   block — because Vision labels those frames "resort"/"leisure"/"condominium", none of which
   were in the exterior vocabulary. The vocabulary was the bug, not the photos. Rule removed;
   a frame with no building at all is still caught by `no_exterior_signal`.
2. `logo:Android` was rejecting every Street View hero. That is Google's own required
   attribution, not a competitor's watermark. Added `ALLOWED_LOGOS`.
   Recalibration moved publishable from 63.1% -> 89.3% over the same 149 images. **The first
   measurement (37% unfit) was mostly my own over-rejection, not a defect in the data.**
**Cost control:** branding is a property of the LISTING, not the frame — every photo in a PRD
listing carries PRD's mark. Testing all 8 candidates cost 16 Vision calls to reach the same
answer (~$550 across the catchment). Now short-circuits to the aerial on the first branding
rejection: **16 calls -> 1**, ~$60 for the full catchment. Composition rejections (interior)
still try the next photo, since that is per-frame. Verdicts cached on (subject_id, image hash)
in `system_monitor.cover_photo_verdicts`.
**Fails OPEN.** An unreachable Vision API accepts the photo and records
`reason: vision_unavailable`, rather than silently demoting every cover in the catchment to an
aerial the moment a key expires.
**Verified:** 6/6 on hand-labelled cases (PRD watermark, two interiors, two facades, one pool
photo I had mislabelled myself — the gate was right and I was wrong). `1 Highgate Lane`
re-renders to `cover_hero=boundary_aerial`.

`scripts/prewarm_offmarket_covers.py`
