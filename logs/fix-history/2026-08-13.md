## [RENTAL-AS-SALE-PARSERS] Closed the deferred half of the rental-as-sale class — 7 parsers hardened — 07:37 AEST
**Symptom:** None visible. This is the item `[RENTAL-AS-SALE-DEEP]` (2026-08-10) deliberately left
undone: the price parsers that accept a weekly rent as a sale price. Latent, not active.

**Root cause:** Every price parser in the estate was written independently. There was no shared price
helper and **no rent guard anywhere in the codebase** (`grep` over `shared/` and
`scripts/property_reports/` returns only occupancy-classifier rent *estimates*). Each parser strips
`$`, `,` and text and converts what remains, so `"$750 per week"` reduces to `750`.

**What the earlier record got wrong.** I re-tested all 13 parsers by executing them rather than
reading them, and the 2026-08-10 entry understates the exposure in two ways:
1. It says **"two accept the literal string `$750 per week`"**. **Five do** — `slot_resolver`,
   `cohort_premiums`, `appraisal_data_pull`, `comparable_feed`, `refresh_property_reports`.
2. Two of its named parsers were **tested at the wrong function**. In `comparable_feed` and
   `refresh_property_reports`, `parse_price` is string-only *by design*; the real entry point is
   `coerce_price`, which is permissive on **both** the numeric and the string form. So the exposure
   reaches the comparable feed and the nightly report refresher, not just the valuation engine.
3. `assemble.num` was **miscounted as a parser**. It is a *formatter* — it returns the string
   `"950,000"` — and does not belong in this class at all.

Net: 7 real entry points, not 6.

**The floor is measured, not guessed.** I did not inherit the price floor from the previous entry.
Across every Sale-category timeline event in the three target suburbs:

| band | n | median year |
|---|---|---|
| < $1,000 | **0** | — |
| $1,000–$5,000 | **0** | — |
| $5,000–$20,000 | 56 | 1978 |
| $20,000–$100,000 | 4,246 | 1990 |

There is not one genuine sale below $5,000 in our history, so the $1,000 floor carries 5x headroom
and cannot touch the 56 real 1970s sales — the trap the previous entry correctly flagged. Note the
floor is **not** the primary defence and cannot be: luxury Gold Coast weekly rents reach $3k–$5k and
would clear any floor set low enough to preserve 1970s sales. The **string markers** do the
discriminating work; the floor only catches bare numerics with no plausible sale reading.

**Fix:** new `shared/price.py` — `looks_like_rent()` (string markers: `per week`, `pw`, `p/w`,
`p.w.`, `/wk`, `weekly`, `fortnightly`, `per month`) and `sale_price_or_none(raw, parsed)`, which
takes the **untouched** raw value so the markers are still visible (every parser strips them before
converting). Wired into all 7 entry points.

## [DR-OUT-OF-TREE-BLINDSPOT] The valuation engine ran from a directory no backup check scanned — 08:05 AEST
**Symptom:** GitHub's copy of the house valuation engine was **254 lines divergent** from the file
that actually runs (4,356 vs 4,480 lines) — and nothing anywhere reported it.

**What the divergence actually was:** the 2026-08-12 `[VALUATION-UNKNOWN-ASYMMETRY]` fix (unknown
attributes silently marking subjects down, worth up to $120k on water views). It edited the live file
and never reached GitHub. Confirmed by diffing the hunks against that entry — the `_LEGACY_UNKNOWN`
guards are exactly it. **Shipped behind `VALUATION_UNKNOWN_HARDENING=1`, default OFF**, so syncing it
changes no production behaviour; that entry verified the default path unchanged (MAE 9.1% both sides).

**Root cause — three failures stacked, none of which alone would have done it:**
1. **The live engine lives outside every repo `check_unpushed_code.py` scans.** `REPOS` covers
   `/home/fields/Fields_Orchestrator` and `/home/fields/Property_Data_Scraping`.
   `/home/fields/Feilds_Website/` — where the engine actually runs, per CLAUDE.md — is scanned by
   **nothing**, and has no local `.git` at all.
2. **Someone worked around (1) by hand-copying the file into the orchestrator repo** at a mirror path
   and pushing it. A copy is a thing that can drift, and it did.
3. **That mirror was later deleted from the working tree, and the deletion was silent.**
   `code_files()` filters with `os.path.isfile()`, so a tracked-but-missing file is skipped with no
   output. GitHub's copy then looked authoritative while the file that ran lived somewhere else.
   Rule 8 applied to backups: an empty result asserted nothing.

**Fix (`scripts/check_unpushed_code.py`):**
- **`EXTRA_FILES`** — a first-class concept of an out-of-tree live file that claims a path inside a
  repo. It points at the **LIVE path, not a copy**, which is the whole point: there is no second file
  to drift. `classify_extra()` compares by content hash; `push_repo()` takes a `localmap` so the
  bytes come from the live file while the commit lands at the repo path.
- **`ghost_files()`** — tracked paths with no file on disk are now printed instead of silently
  dropped. Reported, not alerted (most ghosts are ordinary uncommitted deletions), but a stale mirror
  can no longer hide in the gap.
- **`secret_hits()` refactored to take an absolute path** rather than `(repo, rel)`, so out-of-tree
  files go through the same credential gate. A bypass route must not also bypass the secret scan.

**Verified — the guard fires, rather than just happening to read clean once:**
| case | result |
|---|---|
| unchanged live file | IN SYNC |
| drifted copy | **MOD** (caught) |
| live file vanished | **MISSING** (caught — not silently skipped) |
| path absent on GitHub | **NEW** |
| secret in an out-of-tree file | **BLOCKS** |

Then synced: commit `025d5dc8`, byte-verified, and the checker now reports the engine in sync.

**Found while fixing, NOT actioned — needs a decision:** the ghost report immediately surfaced a
**second, older mirror** of the same engine at the repo ROOT, `precompute_valuations.py` (171,651B,
last touched 2026-08-05, vs 198,984B at the `07_Valuation_Comps/` path). Two backup copies of one
live file, both stale, is how the "which copy is real?" trap gets rebuilt. I did not delete it —

## [V4-DEPTH-MISLABELLED] `deepest_section` measured where readers LEFT, not how far they got — 10:35 AEST
**Symptom:** Analysing the first 3 days of V4 reading telemetry (13 exit events on detached
houses), the three deepest reads on the site — 100% scroll, 94-193s engaged, 9-11 sections —
all reported `deepest_section: "hero"`, `deepest_index: 0`. The three shallowest sessions
reported the same thing. The field could not distinguish a complete read from a bounce.
**Root cause:** `sendExit()` assigned `deepest_section: s.lastSection`. `lastSection` is
reassigned on EVERY section change (`settle()`), so it tracks the current section and moves
backwards. Readers who reached the bottom and scrolled back up to re-read the hero — which is
what all three deep readers did — recorded `hero`. Depth is a high-water mark and was never
tracked as one. The same wrong value was sent to the `offmarket-intent-alert` Telegram beacon,
so Will's deep-read alerts have been reporting the exit point as the depth reached.
**Fix:** Track `deepestSection`/`deepestIndex` as an explicit max in `settle()`. Exit event now
carries `deepest_*` (furthest reached), `exit_*` (where they left — the drop-off answer, which
is what the old field actually held) and `scrolled_back` (deep then back up; a re-read signal
worth having on its own). Alert payload carries both.
**Files:** `01_Website/src/pages/OffMarketPage/v4/useReportAnalytics.ts`
**Recurrence:** First. Related: [WHATS-CHANGED-SHIPPED] 2026-08-10 shipped this telemetry.

## [WHATS-CHANGED-WATCH-UNPUBLISHED] Resolving a watch published nothing; RBA decision went stale on ~21,800 pages — 10:50 AEST
**Symptom:** Every V4 page still read "**Coming up — 11 August 2026 (tomorrow)** — The Reserve
Bank hands down its next cash rate decision" on 13 August, two days after the decision. It is
the second-most-reached section in the reading data (8/13 house sessions, 11.3% of reading time).
**Root cause:** Three separate faults, each masking the next.
  1. The generated `whatsChangedData.ts` had not been re-emitted since 2026-08-10. The
     expired-watch guard in `watch_points()` drops a stale watch at GENERATION time, not at
     render time, so an un-regenerated file keeps serving the stale line indefinitely.
  2. `events.yaml` documents that writing `outcome:` "converts it into a normal dated event and
     it moves into the timeline". That is not implemented — `watch_points()` simply `continue`s
     on a resolved watch and nothing else reads it. Resolving the watch alone would have removed
     the stale line and published nothing, silently breaking the promise the watch made
     ("we will re-read the numbers against it and update this page").
  3. Adding the outcome as a second cash-rate event ALSO published nothing. Both it and the
     existing 1 May `cash_rate_rises` pair with `days_on_market`, so `_dedupe_readings` saw the
     same "34 days" figure twice and kept the earlier bullet. Every local metric is already
     spoken for, so a second cash-rate event can never carry a reading of its own.
  Then, once re-anchored to 11 August, it was dropped a THIRD time — by the synthetic
  `**Now** — homes are taking 34 days to sell` suburb point, dated `now - 30d`, a value that
  exists only for sorting. "Earlier wins" is sound between two macro events; against a point
  with no real date it ranked a bare restatement above a dated fact carrying the same figure.
**Fix:** Verified the actual outcome against RBA primary sources first (MR 2026-19: held at
4.35%; next decision 29 September; our Feb/Mar/May-to-4.35% record confirmed correct). Collapsed
to ONE cash-rate event re-anchored to 2026-08-11 stating the hold; resolved the `rba_2026_08_11`
watch and queued `rba_2026_09_29`; gave `_dedupe_readings` a kind-rank so a `macro` event
outranks a `suburb` restatement regardless of date. Documented in both files that resolving a
watch and publishing its result are two separate writes that must happen together.
**Files:** `15_Off-Market/Whats_Changed/events.yaml`,
`15_Off-Market/Whats_Changed/whats_changed.py`,
`01_Website/src/pages/OffMarketPage/v4/whatsChangedData.ts` (regenerated)
**Recurrence:** First for the publish path. The stale-timeline risk was anticipated in
[WHATS-CHANGED-SHIPPED] 2026-08-10 ("REGENERATE MONTHLY"); nothing enforces it — see note below.
