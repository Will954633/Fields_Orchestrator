## [STEP117-HOUSE-GATE-FALSE-RED] Step 117 failed the nightly run on a legitimately empty queue — 06:10 AEST
**Symptom:** Step 117 (Satellite Image Analysis) has failed every nightly run since 2026-08-20,
taking the whole run to `status: failed`, with an empty error message on the board. Its own
stdout contradicted itself: it printed `Total: 17` needing analysis and then, seconds later,
`EmptyWorkSetError: No properties need satellite analysis.` The watchdog escalated it three
nights running ([WATCHDOG] entries 2026-08-21/22/23) and could not classify it.
**Root cause:** `count_needing_analysis()` counts the raw Mongo query; `fetch_candidates()`
additionally applies the `_is_house()` gate, which cannot be expressed in a query. The two
therefore disagree whenever every unanalysed listing is an apartment. Proven by running both
halves directly: 17 documents match the filter across the three target suburbs (robina 11,
varsity_lakes 3, burleigh_waters 3) and `_is_house()` returns False for all 17 — they are
unit-numbered strata addresses (`31/24 Ron Penhaligon Way`, `2501/42 Laver Drive`,
`163/251 Varsity Parade`, …). Non-houses are excluded deliberately (see the `_is_house`
docstring: scheme-level adjacency corrupts `backs_onto`, which `precompute_valuations.py:448`
uses as a primary signal). So the queue was genuinely drained and the step called it a failure.
**Fix:** Three changes in `scripts/step117_satellite_analysis.py`, none to monitoring code.
(1) The empty-candidates branch now distinguishes CLAUDE.md Rule 7b's two cases: a queue
drained by the deliberate house gate exits success with the counts printed, rather than
raising. (2) Because that relaxes an assertion, the outcome assertion moves to where it is
unambiguous — post-loop, `if candidates and stats.successes == 0: raise` — so "found work and
did none of it" can still never report success. (3) Fixed a latent `AttributeError` alongside
it: the house gate turns the cursor into a generator and the next line called `cursor.limit()`
on it, so any run passing `--batch-size` would have crashed; the limit is now applied inside
the loop. The count's print label now says "before the houses-only gate" so the number can
never again be read as the work set.
**Verification:** re-ran `python3 scripts/step117_satellite_analysis.py --status for_sale` —
exit 0, output `✓ Nothing eligible: 17 matched the filter, none are houses.`
**Files:** scripts/step117_satellite_analysis.py
**Recurrence:** First for this step. Nth for the class — same shape as
[YT-7B-COUNTS-UNAVAILABLE-AS-FAILURE] (2026-08-16), where a Rule 7b assertion cried wolf on
input it could not legitimately process.

## [FB-APPROVAL-DOUBLE-POLL-ON-HEARTBEAT-FAIL] Heartbeat failure silently double-published FB posts — 06:06 AEST
**Symptom:** `fb_approval_poll` shows STALE on the Process Registry — "last ran 0.3d ago
(expected every 1h)" — while the poller was in fact still running: `logs/fb_approval.log` has
an mtime of 2026-08-22 22:57 and ends in normal `poll done — acted on 0 post(s)` lines, but the
single `job_runs` document for the job is frozen at 2026-08-22 12:57. Roughly ten hours of
3-minutely polls left no heartbeat at all.
**Root cause:** `main()` wrapped the import, the poll AND the heartbeat write in one
`try: … except Exception: poll(a.dry_run)`. Any failure in `record_job_result` therefore did
two things, both invisible: it skipped the heartbeat, and it re-ran `poll()` from scratch.
`poll()` PUBLISHES to the public Facebook page on an approved token, so the fallback path was a
double-publish risk on every heartbeat failure. The write itself is not permanently broken —
`record_job_result` succeeded when called by hand this morning — so the trigger looks transient
(Cosmos RU), but the swallow is what made ten hours of it undiagnosable.
**Fix:** guard only the import; run `poll()` exactly once; let a heartbeat failure raise so it
lands in `logs/fb_approval.log` instead of vanishing.
**Verification:** `python3 -m py_compile` clean; `fb_approval.py poll --dry-run` runs and
prints `poll done` once, not twice.
**Files:** scripts/fb_approval.py
**Recurrence:** First for this script. 2nd for the class this month — same swallow-the-error
shape as [INDEXING-SILENT-ZERO] (2026-08-07).

**Symptom:** Six meta descriptions served on every suburb's market-intelligence tabs asserted
"Updated March 2026" — five months stale. One of them, crash-risk, sits at avg position 8.4 on
«is the gold coast property market going to crash» (27 impressions, **0 clicks**, 28d to
2026-08-22). Separately the `direction` tab's `<title>` promised a "[2026 Forecast]" and its
description promised "price projections" / "Price forecast models" on every suburb page.
**Root cause:** `src/config/marketMetricsSeo.ts` hardcodes both. The dates were written in
March and nothing re-reads them, so they were correct exactly once. The forecast wording
predates the current reading of CLAUDE.md Rule 5, which forbids predictions outright — the
pages themselves are compliant (they present indicators), but the tags promised the thing the
rule prohibits, on public URLs, which is where a rule breach actually bites.

file always goes stale again, and the pages already state the period of each figure inline,
which is the durable form. Reworded `direction` title/description to indicators and their
limits. Same commit also rewrote the `overview` title to the measured query set (see
[SEO-OVERVIEW-TITLE-QUERY-MISMATCH] below) and aligned its H1 and JSON-LD headline.
**Verification:** `npm run build` passed; fetched all three page types live as Googlebot after
deploy — new titles and descriptions present, no residual "March 2026" anywhere.

## [SEO-ABOUT-STATIC-SHADOW-ENTITY-DRIFT] Three organization names claimed one URL, on shadowed /about pages — 10:20 AEST
**Symptom:** `/about/will-simpson` kept serving `<title>… | Fields Estate</title>` after a
deploy that had already corrected that string in `src/routes/about.$authorSlug.tsx`. Local
source and live page disagreed with no cache involved.
**Root cause:** `netlify.toml` (lines 126-145) rewrites four URLs — `/about`, `/about/will`,
`/about/will-simpson`, `/about/fields-editorial` — to three hand-written static HTML files at
`status = 200`. The React routes for all of them are inert. Underneath that, the static files
carried a worse problem than the wrong title: `about/will-simpson.html` declared
`worksFor: {Organization, name: "Fields Research", url: "https://fieldsestate.com.au"}` and
`about/fields-editorial.html` declared the same as `parentOrganization` — so **three different
names were asserting the same root URL** (`Fields Real Estate` from root.tsx, `Fields Estate`
from the static titles, `Fields Research` from the author schema). `/about` had no structured
data at all. This is the entity fragmentation that lets a competing agent rank on our brand.
**Why it stayed invisible:** `brand_serp_signal.py` sampled four pages and none was an /about
page, so on 2026-08-22 it reported "names in use: Fields Real Estate" — accurate about its
sample, wrong about the site.
**Fix:** widened the sensor to nine pages (every template that emits its own brand suffix
rather than inheriting root's); it caught all of the above on the first re-run. Then corrected
the files that are actually served: canonical name throughout, employer/parent entity set to
"Fields Real Estate", and a full AboutPage + RealEstateAgent JSON-LD node added to `/about`
kept byte-identical to root.tsx. Left the LinkedIn profile as the Person's `sameAs` rather than
promoting it to the Organization's — a personal profile is not corroboration for the company,
and LinkedIn answers bots with HTTP 999, so I could not verify it resolves.
**Verification:** JSON-LD parsed with `json.loads` on all three files before push;
`npm run build` passed; live fetch as Googlebot after each deploy; `brand_serp_signal.py`
re-run against the widened sample.
