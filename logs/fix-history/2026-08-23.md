## [STEP117-HOUSE-GATE-FALSE-RED] Step 117 failed the nightly run on a legitimately empty queue — 06:10 AEST
**Symptom:** Step 117 (Satellite Image Analysis) has failed every nightly run since 2026-08-20,
taking the whole run to `status: failed`, with an empty error message on the board. Its own
stdout contradicted itself: it printed `Total: 17` needing analysis and then, seconds later,
`EmptyWorkSetError: No properties need satellite analysis.` The watchdog escalated it three
nights running ([WATCHDOG] entries 2026-08-21/22/23) and could not classify it.
**Root cause:** `count_needing_analysis()` counts the raw Mongo query; `fetch_candidates()`
additionally applies the `_is_house()` gate, which cannot be expressed in a query. The two
therefore disagree whenever every unanalysed listing is an apartment. Proven by running both
halves directly: 17 documents match the filter across the three target suburbs (robina 11,
varsity_lakes 3, burleigh_waters 3) and `_is_house()` returns False for all 17 — they are
unit-numbered strata addresses (`31/24 Ron Penhaligon Way`, `2501/42 Laver Drive`,
`163/251 Varsity Parade`, …). Non-houses are excluded deliberately (see the `_is_house`
docstring: scheme-level adjacency corrupts `backs_onto`, which `precompute_valuations.py:448`
uses as a primary signal). So the queue was genuinely drained and the step called it a failure.
**Fix:** Three changes in `scripts/step117_satellite_analysis.py`, none to monitoring code.
(1) The empty-candidates branch now distinguishes CLAUDE.md Rule 7b's two cases: a queue
drained by the deliberate house gate exits success with the counts printed, rather than
raising. (2) Because that relaxes an assertion, the outcome assertion moves to where it is
unambiguous — post-loop, `if candidates and stats.successes == 0: raise` — so "found work and
did none of it" can still never report success. (3) Fixed a latent `AttributeError` alongside
it: the house gate turns the cursor into a generator and the next line called `cursor.limit()`
on it, so any run passing `--batch-size` would have crashed; the limit is now applied inside
the loop. The count's print label now says "before the houses-only gate" so the number can
never again be read as the work set.
**Verification:** re-ran `python3 scripts/step117_satellite_analysis.py --status for_sale` —
exit 0, output `✓ Nothing eligible: 17 matched the filter, none are houses.`
**Files:** scripts/step117_satellite_analysis.py

**Fix:** guard only the import; run `poll()` exactly once; let a heartbeat failure raise so it
lands in `logs/fb_approval.log` instead of vanishing.
**Verification:** `python3 -m py_compile` clean; `fb_approval.py poll --dry-run` runs and

## [GEO-BLOCK-403-TO-200] Overseas IPs no longer get 403+noindex where crawlers get 200 — 12:05 AEST
**Symptom:** On the same URL, an ordinary browser from a US IP received HTTP 403 and a page
carrying `<meta name="robots" content="noindex">`, while a bingbot user-agent from the same IP
received a normal 200 and the real page (measured 2026-08-16 from a Bright Data US residential
IP). Serving crawlers different content from humans is what cloaking is, and Bing polices it
harder than Google. The divergence went live 2026-07-21, two days before Bing impressions fell
to zero for 22 consecutive days.
**Root cause:** `netlify/edge-functions/geo-block.js` refused every non-AU/NZ visitor outright —
`return new Response(BLOCKED_HTML, {status: 403})` — while exempting a long allowlist of crawler
user-agents. The block was doing two jobs at once: keeping overseas lead/analytics spam out, and
(unintentionally) presenting a crawler-only view of the site. Only the first was wanted.
**Fix:** Non-AU/NZ requests now fall through to `context.next()` and are *annotated* rather than
refused — response header `x-fields-region: outside-service-area` and cookie
`fields_region=outside`, so the original concern can be handled by filtering leads/analytics
instead of by refusing the page. Nothing consumes those yet; they are the hook. The crawler
allowlist and exempt paths are retained deliberately (now belt-and-braces) because they are the
documented contract with `public/robots.txt`, and because deleting them would make any future
re-introduction of a block silently unsafe — that exact omission has bitten twice already
(`[GEO-BLOCK-INSPECTIONTOOL]` 2026-07-31, `[GEO-BLOCK-AI-CRAWLERS-403]` 2026-08-16). Dead
`BLOCKED_HTML` constant removed.
**Not done:** the visible region notice Will's decision also mentions. `src/entry.client.tsx`
calls `hydrateRoot(document, …)`, so React owns the entire document and any HTML injected at the
edge into head or body is a hydration mismatch that React 19 would discard while client-rendering
the whole page. A visible notice needs a component in `src/root.tsx` reading the cookie above —
a render-path change, which is perf-gated and not this domain's lever. The substantive half of
the decision (no more 403 + noindex divergence) is delivered.
**Authorisation:** Will, 2026-08-18, approving REC-geo-002 — *"serve overseas IPs a normal 200 +
region notice instead of 403+noindex. Removing the cloaking-shaped pattern is the point — NOT a
bet that this restores Bing… Overseas humans were never buyers, so the 403 was buying us
nothing."* Brief §5 reserves this file to Will; this shipped on his explicit approval, not
unilaterally.
**Verification:** `npm run build` passed (15.03s) · ONE commit `4e1ca6cb`, md5-verified against
the pushed blob · Netlify deploy `6a8a1d7ec4b1d20008b743cd` ready. Re-probed from the same US
residential IP after deploy: ordinary US Chrome **200 / 214,959 bytes / no noindex / no block
page**, byte-identical to what bingbot, Googlebot, GPTBot, OAI-SearchBot, ClaudeBot and
PerplexityBot each receive. AU control unchanged (200, no header, no cookie).
**⚠ Do not read this as the Bing fix.** Bing recovered on its own on **2026-08-14** — 0
impressions for 22 days, then 13, 18, 59, 62, 68, 57, 55 — which is two days *before* the crawler
