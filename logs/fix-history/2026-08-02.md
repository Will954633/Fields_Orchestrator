## [PULSE-FIVE-YEAR-INDEX-MISLABEL] Suburb-compare ranked on index levels, not five-year growth — 07:00 AEST

**Symptom:** The August suburb-compare summaries on `/market-intelligence/:suburb/suburb-compare`
rank the three suburbs on a "five-year index" that is not a five-year growth rate. Live text says
Burleigh Waters' "index gain of 61.5 exceeds Robina's 52.41"; on actual five-year median growth
Burleigh Waters is **last** of the three, not ahead of Robina. The published ranking is inverted.

**Root cause:** `build_data_snapshot()` in `generate_market_pulse.py` emitted a field named
`five_year_index` holding `indexed_series[-20].index_value` — the index *level* as at ~5 years ago,
where the index is cumulative % growth since a Q3 2016 baseline. Two problems:
1. **Mislabel.** The name reads as a five-year growth rate, so summaries compared
   `latest_index - five_year_index` and reported the result as five-year growth. That difference is
   a percentage-*point* gap on a 2016 base, which ranks suburbs differently from actual growth.
   Index deltas put Burleigh Waters top (96.6pp); true 5yr median growth puts it last.
2. **Off-by-one.** `[-20]` is 19 quarters back from the latest, not 20 — Q3 2021 against a Q2 2026
   latest, i.e. 4.75 years, and it landed on a thin quarter where Burleigh Waters swings from
   76.71 (Q2 2021) to 61.50 (Q3 2021).

**Fix:** Replaced the single ambiguous field with two explicitly-named measures —
`index_since_baseline` (+ `index_baseline_period`) for the level, and `five_year_growth_pct`
(+ `five_year_from_period`, `five_year_from_median`, `five_year_basis`) for the rate. Growth is now
computed off `rolling_12m_median_series` with `is_in_progress` entries excluded, so a single thin
quarter can't swing it, falling back to raw quarters only if the rolling series is missing. Indexing
corrected to `[-(20+1)]`. Added the same corrected block to `manual_market_pulse.py --show-data` so a
human writing summaries sees the real number, and amended the suburb-compare prompt to state that the
two measures are different and must not be mixed. Corrected ranking on 12m-rolling medians:
Varsity Lakes +93.9%, Robina +90.4%, Burleigh Waters +73.2%.

**Files:** `scripts/generate_market_pulse.py`, `scripts/manual_market_pulse.py`

**Recurrence:** First. Same failure *class* as [PROPRADAR-MEDIAN-ANCHOR-WRONG] and the March-2026
crash-risk phantom surge — a field whose name implies a different statistic than it holds.

## [UNION-MEDIANS-REVERTED-NIGHTLY] Nightly pipeline wiped the union medians every night — 07:40 AEST

**Symptom:** The Domain ∪ onthehouse union medians and 90% CIs promoted by the 1st-of-month chain
disappear from `Gold_Coast.precomputed_indexed_prices` within hours. Live docs had no
`median_source`, `union_from`, `method`, `coverage` or `rolling_12m_ci_*` fields at all, and
Burleigh Waters' rolling 12-month median was back to the known-inflated **$2,115,000** instead of
the union's **$1,925,000**. `/market-intelligence/burleigh-waters/overview` renders the same stat
four different ways: **$1,790,000** (hero + FAQ), **$1,710,000** (verdict block + chart caption),
**$1,877,775** (Market Pulse prose). The correct union figure appears nowhere on the page.

**Root cause:** Orchestrator step 17 "Market Narrative Pre-computation"
(`config/process_commands.yaml:314-324`) runs `RUN_PRECOMPUTE.sh` on **every** nightly pipeline run,
which invoked `precompute_indexed_price_data.py` — the same script the monthly chain runs at 05:00.
It ends in a blind full-document `replace_one({'_id': ...}, data, upsert=True)`
(`precompute_indexed_price_data.py:1044-1048`), so it clobbers rather than merges, deleting every
union-owned field. `precompute_market_charts.py` on the next line did the same to
`precomputed_market_charts`. Confirmed by the step's own log: `logs/runs/2026-08-01T20-30-44_completed/
21_step_17_market_narrative_pre_computation/stdout.log:245` reports `growth=135.2%` for Robina at
23:44-23:49 AEST, exactly the value now live, ~6 hours after the 17:57 union promote.

Disguised by a timezone mismatch: `last_updated` is written as naive **UTC**
(`precompute_indexed_price_data.py:794,952` use `datetime.utcnow()`) while the same file uses
`datetime.now()` elsewhere and `market_pulse.generated_at` is naive local. The revert timestamp
therefore reads as `13:46` — an innocuous afternoon write — when it is 23:46 AEST.

Guard existed but was incomplete: the crontab comments (lines 173, 239-241) and the docstring in
`precompute_union_prices.py:499-503` both name only the `0 5 1 * *` cron as the thing that must not
run after the promote. Neither accounts for the pipeline invoking the identical script nightly. The
earlier `[UNION-MEDIANS-NOT-DURABLE]` entry (2026-08-01 17:58) diagnosed this class but concluded the
revert would next land "on 1 September" — it missed the nightly path, so the data was already reverted
that same night.

**Fix:** Removed both precomputes from `RUN_PRECOMPUTE.sh`, leaving a comment block explaining why
they must not be re-added. They are fully redundant with the monthly crons — `0 5 1 * *` for the
indexed prices and `8/16 5 1 * *` covering all four chart types (`dom cycle` + `volume turnover`) —
the data is quarterly so it cannot change between nights, nothing in `process_commands.yaml` depends
on step 17, and the crontab states the intent outright ("1st of month only — aligns charts with
monthly commentary"), as does the live page footer ("Updated monthly on the 1st").

**Files:** `/home/fields/Feilds_Website/08_Market_Narrative_Engine/RUN_PRECOMPUTE.sh` (backup at
`.bak-2026-08-02`; was untracked — now pushed to `Website_Version_Feb_2026`)

**Recurrence:** 2nd of the same class as `[PROPRADAR-MEDIAN-ANCHOR-WRONG]` / `[UNION-MEDIANS-NOT-DURABLE]`
— a blind `replace_one` reverting a deliberately-corrected document.

`ERROR Carrara (missing 4 properties)` every night. Neither suburb is scraped by step 101,

Verified: 6 suburbs checked, 0 gaps.

## [COVERAGE-DOMAIN-VARIANT] Burleigh Waters silently reported DOMAIN_UNAVAILABLE — 07:10 AEST

**Symptom:** 2026-08-01 run: `WARN Burleigh Waters Domain=None DB=54 (DOMAIN_UNAVAILABLE)`.
The one suburb that was also short on discovery (51/54 in step 101) was the one with no
independent count to verify against, and nothing was retained to diagnose why.

**Root cause:** The fetch succeeded but the returned page matched neither count regex. Domain serves
at least two page variants for the same URL — a ~500KB one carrying only the
`<h1 data-testid="summary">` heading, and a ~2MB one that also embeds `"totalResults"`. Extraction
failure was terminal (no retry, since only the *fetch* was retried) and discarded the body.

**Fix:** Replaced the two ad-hoc regexes with a `COUNT_PATTERNS` list covering all four known shapes
(summary heading, bare `<strong>`, `"totalResults"` JSON, generic `>N Properties<`), moved the retry
loop to wrap *extraction* rather than just the fetch, and on total failure the last body is written to
`logs/coverage_unparseable_<slug>.html` so the next occurrence is diagnosable. Re-ran: Burleigh Waters
now `OK Domain=54 DB=54`.

**Files:** scripts/coverage_check.py
**Recurrence:** First

against `fieldspropertyimages.blob.core.windows.net`, failing floor-plan vision for those properties.
Step exited 0, so the run reported 26/26 success and the loss was invisible.

**Root cause:** The Azure `fieldspropertyimages` account was retired 2026-05-28 and the pipeline moved
to `BLOB_BACKEND=local` (nginx over /data/blobs at `blobs.fieldsestate.com.au`, identical paths), but

`toLiveBlobUrl()` in `netlify/functions/shared-utils.mjs` rewrites the host. The Python pipeline had
no equivalent, so vision steps fetched the dead host directly.

**Fix:** Added `to_live_url()` to `shared/blob_storage.py` (Python mirror of the website's
`toLiveBlobUrl`, rewriting known-dead hosts to `BLOB_PUBLIC_BASE_URL` on the same path) and applied it
in `_download_and_encode_image()` in the floor-plan vision client. Verified end-to-end: a URL that
403'd last night now downloads and encodes (452KB PNG).
