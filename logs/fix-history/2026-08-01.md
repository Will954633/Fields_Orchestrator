**Symptom:** Not a failure — a scope decision (Will). Nerang had 3,399 decks built against a released sitemap slice of 1,000, and the release widener was set to keep growing it.
**Root cause:** n/a. The builder deliberately derives its suburb list from the KEYS of the `offmarket_sitemap_release` config doc and builds the WHOLE suburb ahead of release, so simply removing the key would have stopped builds AND dropped the 1,000 already-indexed URLs out of the sitemap, orphaning pages Google already holds.
**Fix:** Added a `frozen: [...]` concept to the release config, distinct from `limits`. A frozen suburb is no longer built and its release can never widen, but `limits` is left in place on purpose so the already-released slice stays in the sitemap and keeps resolving to a real deck. Because the builder no longer covers the whole suburb, "builder ⊇ sitemap" would stop holding by construction — so the coverage assertion now watches `build set ∪ frozen released slice` via a new `frozen_released_slugs()` that mirrors the sitemap's `sort({_id:1}).limit(N)` exactly. Freezing must never become blindness: a frozen suburb losing a deck is the [OFFMARKET-DECK-EXPANSION-DRIFT] failure from earlier today. `offmarket_sitemap_release.py` now refuses to widen a frozen suburb even if its (currently paused) cron is re-enabled. Reversible: drop the name from `frozen`.
**Verification:** build set = core 3 only (14,260); frozen watch = nerang 1,000; watch ⊇ build = True; 0 missing decks; widener run returns "nerang is FROZEN — release held at 1000" and leaves `limits` untouched.

## [ONTHEHOUSE-PARALLEL-INGEST] Second data source live — Domain alone saw 71-75% of the market — 17:10 AEST
**Symptom:** Not a crash — a measured blind spot. Domain is our only live listings/sold source and it is incomplete. Six finished seller reports sat in `under_review` for homes listed with other agents (41 Olympus Dr Robina — Harcourts; 157 Christine Ave; 4/44 Frascott Ave; 46 Mornington Tce; 819 Legend Trail; 70 Burleigh St), and 20 addresses in `offmarket_discovery` were actively for sale with none of our sources knowing.
**Root cause:** Single-source coverage. Measured 2026-08-01, core three suburbs, houses only, like-for-like: for-sale Domain 111 / onthehouse 120 / matched 74 (Domain = 71% of union); sold 12-month Domain 508 / onthehouse 619 / matched 449 (Domain = 75% of union). Where they overlap they agree almost perfectly — 539/554 sale prices identical to the dollar, property type 769/769 — so the ~25-29% each misses is genuine coverage, not a join artefact. onthehouse carries Valuer General (`saleSource: "VG"`) settlement records, which is why it reaches sales Domain never had.
**Fix:** New `scripts/onthehouse/` package (client/matching/suburbs) plus three jobs, all houses-only, core three suburbs, direct from this VM with no Bright Data. `onthehouse_listings_sync.py` (nightly 23:35, 17 pages/~50s) → `system_monitor.onthehouse_listings`. `onthehouse_sold_sync.py` (shallow Mon-Sat 23:40, deep Sunday) → `onthehouse_sold`, a 12-MONTH OVERLAY that never overwrites our deeper history. `onthehouse_reconcile.py` (23:55) → coverage board + `onthehouse_conflicts`, which QUARANTINES price disagreements rather than merging (the 3% is the signal; auto-merge would destroy it — 2 caught, both ~1% with contract-vs-settlement date differences). Guard wired in three places: `market_status.verdict()` takes onthehouse as a third sale signal, `engagement_activity_to_sheet` populates it, and `build_property_report.resolve_one` now asks onthehouse before spending a build. Nothing is written to Gold_Coast — Domain stays the system of record for enrichment (floor plans, images, descriptions, withdrawn state, price history, none of which onthehouse has).
**Design invariants:** (1) A fetch failure returns None, never [] — we only expire listings in suburbs we actually fetched, and reconciliation is deferred because an index also returns neighbouring suburbs. (2) ABSENCE IS NOT EVIDENCE — 28% of live Domain listings are missing from onthehouse, so a miss is never proof a home is unlisted; only a hit is decisive. (3) 403/429 raises `Blocked` and aborts with an error heartbeat rather than degrading to "no results". (4) `salePrice: 0` means withheld (24% of sold houses) and is stored as None with `price_withheld`, never as $0. (5) Sold `_id` is address+sale-date so a home selling twice in the window doesn't overwrite itself.
**Address key:** the whole integration risk, isolated in `onthehouse/matching.py`. Two bugs found and fixed during validation — `\b4\d{3}\b` was stripping high-rise UNIT numbers as postcodes (4204/12-14 Executive Dr keyed as 12|14; 4103/61, 4507/61 and 4708/61 Investigator Dr all collapsed onto one key), and a blanket `&.*` cut ate the street name. Also: `suburb=` must be passed from the collection, because many for-sale docs store `street_address` with no suburb — omitting it silently cut a core-suburb join from 111 matches to 4. Both sides of every join now use one function; the fixed key found 9 MORE sold matches than the ad-hoc one used during measurement.
**AVM:** their `guesstimate` is stored from day one but consumed by nothing. Scoring it against past sales gives 4.7% median error, but `calculationDate` post-dates most of those sales so the test is contaminated, and their own confidence labels don't rank (High n=11 at 5.6% is worse than Medium-High at 3.2%). A clean test needs values captured before sale — possible in ~3 months at zero extra cost.
**Verification:** listings sync 140 active houses (120 in-suburb + 20 free spillover), 0 failures; sold deep backfill 647 houses, 126 price-withheld; reconcile reproduces the measured coverage exactly; all six previously-exposed addresses now BLOCKED with correct agency and listing date; control address correctly returns no listing; all four new jobs registering `job_run` heartbeats.
**Scope:** core three only (Will). A 40-suburb southern+central sweep was measured first — 683 requests / 1.08 GB / 16.9 min / zero blocks — and deliberately pulled back; expansion is a later decision.
