## [OFFMARKET-LISTED-DISCOVERY-GAP] Listed home shown as off-market — Domain search schema migration silently broke discovery — 04:50 AEST
**Symptom:** A buyer googled 6 Joy Avenue, Burleigh Waters (listed the day before) and landed on our `/off-market/6-joy-avenue-burleigh-waters` page, which presented a currently-listed home as an off-market opportunity. Root investigation showed the listing existed nowhere in our DB (no `for_sale` doc) — only a bare cadastral off-market record.
**Root cause:** Domain migrated its sale-search page OFF `__NEXT_DATA__`. The scraper's primary listing extractor keyed on a `"listingUrl":"…"` regex inside `__NEXT_DATA__` — now matches ZERO. Discovery silently fell back to anchor-href scraping, which under-renders (4→23 listings per identical fetch). Combined with an early `if not new: break`, this under-discovered ~20-32% of core-suburb listings every night (Burleigh Waters 38/56, Robina 69/95). Undiscovered listings are never scraped → never categorised → their cadastral off-market page keeps serving. The shortfall was logged (`38 (expected 56)`) but the step still passed and no one saw WHICH addresses were missing.
**Fix:** (#3) Rewrote extraction to use the current authoritative source — the search page's `application/ld+json` array (`@type=Residence` = the complete per-page address list, always = pageSize; `@type=Event` + anchors = URLs). `discover()` now RE-FETCHES each page (up to PAGE_REFETCH_MAX) and unions URLs until they cover the Residence count, and only stops on 2 consecutive genuinely-empty pages or reaching Domain's expected count. Result: Burleigh Waters 38→54/54 (100%); 6 Joy Avenue now discovered (listing id 2021035855). (#1) Added `record_coverage()` → `system_monitor.listing_coverage` (per-suburb expected/discovered/in-DB + the SPECIFIC missing addresses) + a self-registered `listing_discovery_coverage` heartbeat, and a `collect_listing_coverage` collector so the Systems Health sheet names the missing addresses (6 Joy Avenue verified surfacing) instead of a silent red cell.
**Files:** `Property_Data_Scraping/03_Gold_Coast/Gold_Coast_Wide_Currently_For_Sale_AND_Recently_Sold/run_curlffi_suburb_scrape.py`, `Fields_Orchestrator/scripts/main_site_health_check.py`. (#2 real-time PropRadar fallback + interim page still pending.)

## [QUARTERLY-COVER-ISSUE-QR] Tracked per-issue QR on The Fields Quarterly cover — 08:11 AEST
**Symptom:** The Fields Quarterly cover carried no QR. There was no way to measure whether anyone engaged with a given issue of the report — printed copies and PDF downloads were both analytics-dark.
**Root cause:** Not a bug — missing capability. The existing QR tracking (`/track/scan/<tracking_id>`) is one-code-per-homeowner, which does not fit a mass-produced publication where every copy is identical. The identity that matters there is the ASSET + ISSUE, not the reader, and no endpoint modelled that.
**Fix:**
- New `/a/<asset_code>` route on the tracking server. Resolves the code against a new `system_monitor.print_assets` registry, INSERTS ONE DOC PER SCAN into new `system_monitor.asset_scans`, increments `print_assets.scan_count`, fires PostHog `print_asset_qr_scan` + a Telegram ping, then 302s to the asset's destination with UTM params. Unregistered codes still log and still redirect to the homepage — a printed code can never dead-end.
- `?m=` distinguishes the surface one issue was scanned from (print vs pdf); it lands in `asset_scans.medium` and `utm_content`. This closes the "no per-QR differentiation" gap noted against the appraisal QRs.
- New `pipeline/generate_issue_qr.py` does both halves of the contract in one command — registers the asset AND writes the vector QR — so a QR can never be printed against a code the server cannot resolve. Re-runs are idempotent (`scan_count` is not reset).
- Cover QR placed top-right under the logotype, right-aligned to the same 12.5mm margin. 22mm, untiled: light modules are printed birch (#e9e1d7), not white, so nothing boxes the cover. Grass-on-birch clears ~10:1 contrast against the ~3:1 scanners need.
- `--verify-pdf` decodes the cover out of the rendered PDF at 150/300/600 dpi. This is the check that catches a cover pointing at a stale issue's code — the symbol can be flawless and the attribution still wrong.
**Verified:** endpoint 302s correctly via localhost AND the public `vm.fieldsestate.com.au/track/a/...`; destination page returns 200; `print_assets` + `asset_scans` docs confirmed written then test rows cleared so real data starts clean; QR decodes to the exact scan URL from the final PDF at all three dpi.
**Issue:** `quarterly-q2-2026` → `https://fieldsestate.com.au/market-intelligence/Robina`
**Files:** tracking-server/server.py, 10_Market_Report/pipeline/generate_issue_qr.py (new), 10_Market_Report/pipeline/quarterly/index.html, 10_Market_Report/pipeline/quarterly/assets/img/qr_quarterly-q2-2026.svg (new), 10_Market_Report/pipeline/quarterly/INTEGRATION.md
**Recurrence:** First (for asset/issue-level QR tracking; per-recipient QR tracking is [APPR-V4-BACKCOVER-QR])
**Known risk:** `vm.fieldsestate.com.au` is a single point of failure hard-coded into every printed copy — if the VM or nginx goes down, printed QRs dead-end permanently and cannot be re-pointed. Same exposure as the appraisal QRs; worth moving both behind a Netlify redirect before any large print run.

## [OFFMARKET-DECK-EXPANSION-DRIFT] Nerang off-market URLs indexed but served the OLD deck — 12:55 AEST
**Symptom:** A visitor on `/off-market/141-dugandan-street-nerang` was served the old ladder deck (8 cards, "See what it may be worth") instead of the Discovery deck that went live 2026-07-31. Not a one-off: **985 Nerang off-market URLs were in sitemap.xml with 0 Discovery docs** — every one of them served the old design to organic Google traffic.
**Root cause:** Two systems with independently-maintained suburb lists drifted. `generate-sitemap.mjs getOffMarketUrls()` publishes core suburbs **plus release-gated `EXPANSION_SUBURBS = ['nerang']`** (gate opened 2026-07-29, limit 1000). The deck builder `offmarket_discovery_nightly.py` had its own `CORE = [robina, varsity_lakes, burleigh_waters]` and never saw Nerang. The loader's `if (ld?.discovery)` fallthrough to the classic page is deliberate and silent — no error, no log, so the gap was invisible. The builder's docstring claimed coverage was "EXACTLY the sitemap's criteria… indexed → deck guaranteed", but the sitemap gained Nerang two days *before* that claim was written, so the invariant was already false when it was declared. A **third** copy of the list (`offmarket_intel_poller.TARGET_SUBURBS`, 9 suburbs, no Nerang) meant that even a forced build failed with `subject_not_found`.
**Fix:** (1) Builder now derives expansion suburbs from the KEYS of the `Gold_Coast.offmarket_sitemap_release` config doc — the same doc that gates the sitemap, and a strict superset of what the sitemap can emit (a suburb absent from the config contributes 0 URLs). Builder ⊇ sitemap now holds regardless of which side is edited. (2) Builds the WHOLE expansion suburb, not the released slice, so decks are ready *before* URLs are submitted and we never have to mirror the sitemap's `sort({_id:1}).limit(N)`. (3) `indexed_homes()` now yields the source collection and threads it into `build_one(slug, suburb)` instead of relying on the poller's fallback scan; `nerang` added to that scan too for on-demand paths. (4) **Coverage assertion:** after each run the job diffs the indexed slug SET against built docs (sets, not counts — a count can match while a whole suburb is missing and stale docs fill the hole) and raises if the gap exceeds 25, surfacing as ERROR on the Systems Health Process Registry with the missing count and sample slugs.
**Verified:** dry-run went `indexed=14653` → `indexed=18052 to_build=3399` once the config-derived list took effect. Test-built the reported home (8.7s) and confirmed the LIVE page now returns the Discovery deck ("We found your home" + `build-strategy` CTA); the old "See what it may be worth" marker is gone. Full 3,399-home backfill running in 6 shards.
**Gotcha:** `gc or _gc()` raised `Database objects do not implement truth value testing` inside the config read, whose `except` silently fell back to core-only — the fix looked applied but changed nothing. Caught only because the dry-run count didn't move. pymongo `Database`/`Collection` have no `__bool__`; always `is None`.
