# Fix History — 2026-08-10

## [ADS-NO-LEAD-CONVERSION] AYH address submit never reached Google Ads — 09:40 AEST

**Symptom:** Google Ads reported 33 "conversions" across the March/April 2026 campaigns while producing
zero real leads. `Contact Form Click` — the only lead-shaped conversion action — had fired **0 times
lifetime**. Smart Bidding had no seller-lead signal to optimise toward, so any new campaign would repeat
the March result.

**Root cause:** Two independent faults.

1. **The one converting action on the site was invisible to Google Ads.** `AnalyseYourHomePage.tsx` and
   `AnalyseYourHomeV2Page.tsx` never imported `trackGoogleConversion`. Both called a local
   `fireGtag('analyse_home_lead_submit')` helper, which emits `gtag('event', name, {...})` with **no
   `send_to`** — a GA4 custom event that lands in property `G-5C5VS27X42` and never reaches
   `AW-17993173310`. The AYH address submit is the only interaction on the site that yields a real
   seller lead (PostHog, Jul 2026: 316 `/analyse-your-home` pageviews → 15 leads, 4.7%), and Google
   could not see a single one.
2. **The conversion actions that *were* firing were all page views, and all Primary.** `Page view`
   (31 lifetime), `Property Search Click` and `Article Read (30s+)` are `PAGE_VIEW` category yet were
   marked `primary_for_goal=True`, so bidding optimised toward page loads. `page_view` still fires on
   every property page load (`PropertyPage.tsx:514`).

**⚠ This second fault is a recurrence.** `[LAUNCH-BOT-TRAFFIC]` (2026-03-17) found *"a page-view
conversion tag fired on every landing page load (`send_to: AW-17993173310/Rg0OCIGsqIQcEL6S6IND`, value
$1.00), causing Google to report 32 'conversions' that were just bot pageviews. This taught Google's
algorithm to optimise for bot traffic rather than real users."* That fix removed the tag from
`public/launch/{a,b,c}/index.html` **but left the same label wired into the React app and left the
conversion action Primary** — so the identical failure mode stayed live for five months. It is the
documented "feedback loop of doom": all 111 tracked sessions in that campaign came from 11 AWS IPs.

**Fix:**
- Added `ayh_address_submit` to `CONVERSION_LABELS`/`CONVERSION_VALUES` in `gtagConversions.ts` and fire
  `trackGoogleConversion('ayh_address_submit')` at submit-success on **both** AYH pages, alongside the
  existing `phCapture` / `trackMetaEvent` calls.
- Google Ads account `997-572-4211`: created conversion action **AYH Address Submit**
  (`SUBMIT_LEAD_FORM`, `ONE_PER_CLICK`, 90-day click window — the max, because the seller cycle is long),
  `primary_for_goal=True`, resource `customers/9975724211/conversionActions/7715062001`,
  label `AW-17993173310/OW0zCPGB6t4cEL6S6IND`.
- **Demoted `Page view`, `Property Search Click` and `Article Read (30s+)` to
  `primary_for_goal=False`.** Chosen over deleting the tags so we keep the measurement but remove the
  bidding influence. Only the two `SUBMIT_LEAD_FORM` actions are Primary now.

**Verification:** `npx tsc -p tsconfig.app.json --noEmit` clean for the three touched files (repo carries
~210 pre-existing errors, so filtered); `npx vite build` succeeded in 41.6s; label present in
`build/client/assets/gtagConversions-*.js` and both `analyse-your-home*` chunks import it. All campaigns
are PAUSED, so the account change has no live spend impact.

**Files:** `src/utils/gtagConversions.ts`, `src/pages/AnalyseYourHomePage/AnalyseYourHomePage.tsx`,
`src/pages/AnalyseYourHomeV2Page/AnalyseYourHomeV2Page.tsx` (commit `f31b0a18`); Google Ads account
config (no file).

**Recurrence:** Second — page-view-as-primary-conversion previously fixed only on the static launch pages
by `[LAUNCH-BOT-TRAFFIC]` 2026-03-17; the React app and the account-level `primary_for_goal` flag were
missed. Fixed at the account level this time, which covers every surface rather than one page set.

**Context:** Part of the Google Ads viability assessment —
`04_Google_Ads/00-VIABILITY-ASSESSMENT-2026-08-10.md`.

## [BRAIN1-VERIFY-CORPUS-GAP] brain1_verify.py reported an entire library as fabricated — 09:30 AEST
**Symptom:** The mandatory Brain 1 publish gate returned **64.0% fidelity with 41 NOT_FOUND**
("fabricated") on a 129-quote brief, against the ~96.8% this tool has historically reported. Every
one of the 41 was a quote from a `u9#####` unit (eXp Realty US / BLAC SALT AU).

**Root cause:** `brain1_verify.py`'s `ANN_FILES` list held **4 annotation sources while the graph is
built from 6**. Missing: `/home/fields/brain1_yt/annotations.jsonl` (2,292 units — the whole video
corpus) and `/home/fields/brain_drive/annotations_b1.jsonl`. A quote whose unit is absent from the
index cannot be located anywhere, so the verifier reports `NOT_FOUND`, which its own contract
defines as *fabricated*. This is the identical class of defect the memory already records for
`brain1_graph.py` ("the graph is built from four sources, not one") — the corpus grew, the
consumer's hardcoded source list did not. The file's own comment predicted exactly this outcome for
the KB files, which had been added for the same reason earlier.

**Fix:** added both files to `ANN_FILES`, with a comment tying the list to the `--merge` list in
`brain1_graph.py` / `brain_drive_nightly.py` so the next corpus addition updates both. Unit index
9,525 → 12,662. Re-ran all four briefs: brief 01 went **64.0% → 96.1%** (41 NOT_FOUND → 4); all 7
sampled "fabrications" re-located at coverage **1.00** in exactly the cited unit.

**Why it matters beyond one sweep:** this is a publish gate. A gate that cries wolf is worse than no
gate — the next reader sees 64%, concludes the tool is noisy, and stops believing it. It also
silently *masked* a real defect: the genuine `u9####`→`u####` id-truncation bug in map-reduce
output (38 instances in one brief) was buried under 41 false alarms.

**Files:** `scripts/samantha/brain1_verify.py`,
`17_Direct_Letterbox/Withdrawn_Expired_Listings/02_Research/01_Brain1/00-SYNTHESIS.md`

**Recurrence:** First for this file; **Nth for the pattern** — a hardcoded corpus-source list
drifting behind the graph has now bitten `brain1_graph.py` (2026-08-08, silent 6,400→4,593 shrink),
`brain_drive_nightly.py` (2026-08-08, nightly delete of an unlisted corpus), and now
`brain1_verify.py`. **Any script naming Brain 1 sources should derive them from one shared list.**
## [BACKTEST-PRODUCTION-DRIFT] The valuation backtest measured a method we do not ship — 18:40 AEST
**Symptom:** Investigating whether the V4 report's point figure uses adjusted comparables, the
backtest could not reproduce our own published accuracy. Run on Robina it returned **MAE 9.4%,
median 7.0%, within-10% 62% (n=253)** against the documented **8.2% / 6.6% / 67% (n=251)** — and
those documented per-suburb bands are what the live page publishes.
**Root cause:** `scripts/valuation_backtest.py` diverged from `precompute_property_valuation()` in
THREE ways at once, all silent:
  1. it reconciled `calculate_confidence` over `included_points` — the 8 DISPLAYED comparables —
     where production reconciles over the whole candidate pool (`valuation_points`), the change
     credited with taking "homes selling above every comparable" from 42% to 4%;
  2. it never applied `apply_adjustment_reliability`, so it measured adjustment strength 1.0 while
     production ships 0.80;
  3. it passed no `suburb_key`, so every range used the DEFAULT ±14.0% band instead of the suburb's
     own, and no suburb calibration factor was applied at all.
**Why it mattered beyond the tool:** an earlier measurement this session concluded "adjusting
comparables does not improve accuracy" — reconciled over the 8, adjusting looks harmful (improved
48.3% of homes, a coin flip). Reconciled over the pool as production does, adjusting is a clear win:
80% band ±13.72% unadjusted → ±12.44% shipped. The wrong harness produced a wrong finding that was
briefly written into memory and the valuation folder, and had to be retracted.
**Fix:** All three aligned to production, with the old block quoted in a comment so the divergence
cannot silently return. After the fix Robina gives **MAE 9.2%, median 6.7%, within-10% 66%** — median
and within-10% now match the documented figures.
**⚠ Found by the fix — the suburb calibration is stale.** Bias flipped from −1.0% (undervalues) to
**+2.0% (overvalues)**. `_SUBURB_CALIBRATION` was derived 2026-08-07, BEFORE the full-pool and
shrinkage changes of 2026-08-08 improved the method; it is still correcting a −1.9% low bias that no
longer exists, so it now overshoots. The constant's own comment says "RE-MEASURE THESE… re-derive
after any method change" — a method change happened and they were not re-derived. Robina's implied
factor is now ≈1.00, i.e. no correction. Not changed here: re-deriving three shipped constants
deserves its own run on held-out data.
**Files:** `scripts/valuation_backtest.py`, `16_Valuation/experiments/lambda_production.py`
**Recurrence:** First for this drift; the class (backtest not matching production) is the standing
trap in `valuation_backtest_validity_traps`.
