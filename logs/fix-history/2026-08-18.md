## [BRIEF-QUESTIONS-NOT-TAPPABLE] Will's 9 taps answered 1 of 5 briefed questions — two unlinked ask-Will channels — 14:20 AEST
**Symptom:** Samantha's 2026-08-16 weekly brief opened "You didn't answer last week's 5 questions
(you tapped 9 buttons though)". Will had tapped every button he was sent and reasonably believed he
had answered. The same 5 questions were re-asked a week later.

**Root cause — NOT a lost tap.** All 9 taps were received, stored and consumed correctly
(`ceo_chat_messages` seq 2-10; the 6 `RV YES` taps recorded `will_verdict` within 2 min). The defect
is that there were **two ask-Will channels that did not know about each other**:
1. The weekly brief — sent via `telegram_notify.py "<msg>"`, which **had no way to attach a keyboard**:
   `reply_markup` was a Python-only kwarg, never exposed as a CLI argument. So the brief's 5 questions
   were *structurally unanswerable by tapping*.
2. `recommendation_approval.py` — the only tokenised channel, selecting on a bare `{"status": "open"}`
   with no knowledge of the brief, i.e. bypassing Samantha's triage entirely.
Overlap on 2026-08-13 was **exactly 1 of 5** (REC-seo-001). The other 5 buttons were items Samantha
had deliberately *filtered out* of the brief.

Secondary: Step 1 of `samantha_weekly_prompt.md` reads verdicts out of `ceo_chat_messages` text only
and never cross-checks `rl_recommendations.will_verdict`, so a verdict arriving by token read as
unanswered — hence "0 of 5" when the truth was 1 of 5.

**Fix:**
1. `telegram_notify.py` — added `--reply-markup-json`, so the existing `reply_markup` kwarg is reachable
   from the CLI. Rejects non-JSON and non-object input, and refuses `--queue` combination (the digest
   re-renders the text; buttons would be silently lost — that silent drop would recreate this exact bug).
2. `recommendation_approval.py` — new `mint` (token without sending, for the brief to embed) and
   `keyboard` (token list -> inline-keyboard JSON) commands. `mint` reuses a live token rather than
   issuing a second one for the same question, since two valid tokens means a tap on the older message
   records against a stale ask.
3. `recommendation_approval.py cmd_send` — now skips any rec whose `briefed_in` contains the current
   ISO week, so the mid-week channel cannot out-shout the brief on a question the brief already owns.
4. `samantha_weekly_prompt.md` — Step 6 rewritten to mint-then-attach (tokens printed beside each
   numbered question, so tap and typed reply are interchangeable); Step 1 now requires counting answers
   from `will_verdict` regardless of channel.
5. Corrected a **stale docstring** in `telegram_notify.py` that stated the bridge never receives
   `callback_query` and inline buttons "fire into a void". Untrue since 2026-08-13
   (`ceo-telegram-bridge.py:1389` requests it, `extract_message_text` :1355-1375 translates it). Left
   alone it would have kept steering maintainers toward the reply keyboard that already failed.

**Verification:** faked `requests.post` and asserted the real payload — `reply_markup` present,
`callback_data` `RV YES 436F`, token present in body text; then fed that exact `callback_data` and the
typed form `RV YES 436F` through the live `VERDICT_RE`, both yielding `('YES','436F','')`. So a tap and
a typed reply are provably the same record. CLI guards confirmed rejecting bad JSON, JSON arrays, and
`--queue` combination. `mint` confirmed refusing a non-open rec and a non-existent id.

**⚠ One reported defect was NOT real and was dropped.** The investigation claimed the 4/day drip cap is
"computed once per process, so three invocations sent 6". It is a *database query*
(`count_documents({"sent_at": {"$gt": since}})`) re-evaluated per invocation, so it does hold across
processes; the 6 sends at 09:44:09/35/38 got through via `--force`. Changing it as proposed would have
fixed nothing. Verified before writing code, not after.

**Files:** scripts/telegram_notify.py, 16_General_Reinforcement_Learning/recommendation_approval.py,
16_General_Reinforcement_Learning/samantha_weekly_prompt.md
**Recurrence:** First for this defect. But it is the same *class* as [APPRAISAL-AERIAL-SCRATCH-LEAK] and
the valuation-sensor bug approved the same day: **a reader silently pointed at a different source than
the writer.** The durable lesson is that two channels asking the same person the same kind of question
must share one selection, not be kept in sync by discipline.

## [RUNNER-OOM-NO-RESTART] GitHub Actions runner dead 1.5 days — stock unit has no Restart= — 21:00 AEST
**Symptom:** Background-process audit found `actions.runner.Will954633-fields-automation.fields-vm-runner`
in `failed (Result: oom-kill)` since 2026-08-17 08:17 AEST. All 12 `fields-automation` workflows —
including auto-article generation — had not run for 1 day 12h. Nothing reported it.
**Root cause:** Two faults compounding. (1) The stock GitHub runner unit ships with **no `Restart=`
directive**, so a single OOM is permanent until someone notices. (2) The OOM itself came from root-disk
/memory pressure: `/` was at 90% (88G/97G).
**Fix:** Drop-in at `…fields-vm-runner.service.d/restart.conf` with `Restart=on-failure`,
`RestartSec=30`, `StartLimitBurst=5`, `StartLimitIntervalSec=600`. Deliberately **on-failure, not
always** — the runner exits 0 on purpose after a self-update ("stop the service, no retry needed") and
`always` would fight that; systemd did record the OOM as a failure, so `on-failure` catches it.
⚠ Gotcha: `StartLimit*` belong in `[Unit]`. Placed in `[Service]` systemd logs
`Unknown key name … ignoring` and silently leaves the 10s default window. Caught and corrected.
**Files:** `/etc/systemd/system/actions.runner.Will954633-fields-automation.fields-vm-runner.service.d/restart.conf` (new).
**Recurrence:** First for this unit; OOM on this VM is Nth (`[OOM-CHROME-KILL]`, `[OOM-CHANGE-DETECTOR]`).
