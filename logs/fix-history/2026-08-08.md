
## [VALUATION-WATER-COHORT-FIXED] Water geometry backfilled; cohort now geometry-led — 07:27 AEST
**Symptom:** `classify_water_relationship()` could not be the cohort authority because 53% of homes
had no OSM `water_features` block, so it fell back to the photo signal it was written to replace.
**Root cause:** The original enricher issued one Overpass query PER PROPERTY, so ~24,000 properties
were never enriched. Separately, the whole overpass-api.de family (incl. lz4./z.) returns 406 to this
VM regardless of User-Agent; kumi.systems and private.coffee work.
**Fix:** `scripts/backfill_osm_water_features.py` fetches every water element in the region ONCE
(537 elements, 78s) and computes distances locally against a 250m grid of 16,072 segments — one
request replaced ~24,000. Coverage 53%→100% (23,748 written, 0 failures). Wired
`classify_water_relationship()` into `in_cohort()`; `is_waterfront()` still drives the
publish/suppress gate and stays broad.
⚠ Validation caught a real bug: the first regional query omitted `drain`/`ditch` (which WATER_TYPES
handles) and computed distances up to 200m too large across Burleigh Waters' drainage canals — 15/18
agreement. After widening: 29/30, median delta 0.0m.
⚠ Added `lakefront` — the original set waterfront_type for canal/coastline/river only, so a home ON
a lake scored 'none'. 1,817 properties (7.7%) are lakefront, previously undetectable. The 30m
threshold was then VALIDATED against 807 sold houses: premium is +13.6% at 10-20m, +12.4% at 20-30m,
and -9.0% at 30-50m — it stops exactly there.
**Result:** 9 Laura Place (worst outlier, +87%) is genuinely lakefront and now returns no figure
rather than a wrong one. 20 Washington Court reclassified dry, +46% → +30%. Homes falling back to
photos for want of geometry: 332 → 2.

## [SITEMAP-UNDERCONTRACT-GAP] under_contract listings indexable but in no sitemap — 08:40 AEST
**Symptom:** Audit of URLs earning impressions but absent from `sitemap.xml` found 11 `/property/` pages that render fully indexable — **no robots meta at all** — yet appear in no sitemap. Several already earn organic traffic (17 Pitta Place 33 impr/2 clicks, 180 Christine Avenue 38 impr).
**Root cause:** A hole between two queries neither of which claimed `under_contract`. `getPropertyUrls()` matched `listing_status: 'for_sale'` exactly; `getOffMarketUrls()` excludes `{$nin: ['for_sale','under_contract']}`. Meanwhile `property.$id.tsx`'s noindex gate (`p.is_waterfront || (!p.is_sold && !p.has_ai_analysis)`) never tests `listing_status`, so those pages served as indexable. No comment in either file addressed `under_contract` — it was an omission, not a policy.
**Fix:** `getPropertyUrls()` now matches `{$in: ['for_sale','under_contract']}`, keeping the editorial gate and waterfront exclusion. A home under contract is still a real listing whose address people search, and its editorial has already passed the gate.
**Verification:** Ran `node scripts/generate-sitemap.mjs` locally (backing up and restoring `public/sitemap.xml`, which the VM cron owns): property URLs 1493 → **1504 = exactly +11**, and all four spot-checked slugs present.

## [MI-CASING-DUPLICATES] /market-intelligence/:suburb served every casing variant as a distinct indexable page — 08:40 AEST
**Symptom:** `/market-intelligence/Burleigh_Waters` was `Submitted and indexed` with a SELF-referencing canonical, alongside `/market-intelligence/Burleigh-Waters` — one page's signals split across several URLs. Also `Varsity_Lakes`, `burleigh_waters`.
**Root cause:** The route accepted the `:suburb` param verbatim, returned 200 for any casing, and self-canonicalised to whatever was requested. Its sibling `houses-for-sale.$suburb.tsx` has always 301'd variants to a canonical Title-Case-hyphen slug; this route never did. The legacy `/market-metrics/*` → `/market-intelligence/:splat` redirect then propagated the pre-existing variants into the new namespace by forwarding the raw token.
**Fix:** Added `canonicalSuburbSegment()` to `src/utils/suburbNormalize.ts` (composes the existing `normalizeSuburbForDb` + `suburbToUrlSegment`) and applied it in the market-intelligence loader, guarded against an empty segment and inherently loop-free. Verified live: all four variants 301 to canonical in one hop; `Burleigh-Waters`, `Varsity-Lakes/overview`, `Robina`, `Gold-Coast` all still 200.
**Caveat found during verification:** the same normalisation was added to `market-metrics.$suburb.tsx` intending a single hop for legacy URLs, but **that loader does not run** — `netlify.toml` line ~143 has an edge redirect that fires ahead of SSR and forwards the raw token. Legacy URLs therefore resolve in TWO hops (correct and loop-free, just not the single hop intended). The route comment was corrected to say so rather than leave code that appears to do something it cannot.
**Files:** src/utils/suburbNormalize.ts, src/routes/market-intelligence.$suburb.tsx, src/routes/market-metrics.$suburb.tsx (commit 5a65cfb1; comment correction pending next push)
**Recurrence:** First.

## [BACKTEST-COHORT-DRIFT] Backtest kept its own cohort + no retirement — 07:48 AEST
**Symptom:** After wiring geometry-led cohorts and retiring 3 adjustments into production, the
backtest returned figures IDENTICAL to the pre-change run (9.17% MAE, ±14.5%) — neither change moved
the number.
**Root cause:** `valuation_backtest.py` maintains its OWN `in_cohort()` (still keyed to
`is_waterfront`) and calls `calculate_adjustments` directly without `apply_retired_adjustments`.
The same class of divergence already documented as [BACKTEST-PROXIMITY-FEATURES-MISSING] — the
backtest re-implements production instead of reusing it.
**Fix:** Imported `classify_water_relationship`/`WATERFRONT`/`apply_retired_adjustments`; replaced
the cohort water filter; applied retirement after `calculate_adjustments`. Re-running.
**Files:** scripts/valuation_backtest.py
