Three bugs found and fixed during the work, all of which would have produced confident but wrong output:
1. **Silent data loss under rate limiting.** The first Reddit run treated HTTP 429 as an empty result: 127 requests were dropped and it would have written a plausible-looking file missing most of the corpus while reporting success. Now retries with exponential backoff and records `incomplete_queries` in the output.
2. **Every PropertyChat post stamped with the harvest date.** A whole-page date scan matched the forum's "recent activity" sidebar rather than the posts, dating a 2007 thread as 2026-08-05. Dates are now read from within each `<li id="post-N">` block. This would have destroyed the document's staleness convention.
3. **Quoted text attributed to the wrong member.** XenForo renders inline quotes as `<div>`, not nested `<blockquote>`, so tag-stripping left one member's words inside another's post — a misattribution in a quotation-based evidence document.

**Substantive research outcome:** the addendum revises §4.6 (the "is this priced fairly?" need is *articulated*, not merely inferred) and reframes §3.1 (the portal appears to *hold* a numeric price for "Contact Agent" listings and withhold it — five independent posters plus a named broker). ## [UGREP-REGEX-VM-LOCKUP] Runaway ugrep wedged the VM twice (Aug 1, Aug 6) — 08:10 AEST

**Symptom:** `vm.fieldsestate.com.au` stopped loading. code-server stayed `active` in systemd, nginx/TLS/DNS all healthy, but the workbench never loaded. Load average 27–41 on 4 vCPUs, iowait 60–80%, root disk pinned at its ~240 MB/s ceiling. SSH eventually unreachable; only a GCP stop/start recovered it. Twice: 2026-08-01 and 2026-08-06.

**Root cause:** A runaway `ugrep`. Three layers, all needed to explain it:

1. **Where ugrep comes from.** Claude Code installs a bash *function* named `grep` that rewrites every shell `grep` into `exec -a ugrep <claude-binary> -G --ignore-files --hidden -I --exclude-dir=…`. ugrep 7.5.0 is statically linked into the `claude` binary — there is no standalone `ugrep` on this box, and `/usr/bin/grep` is still genuine GNU grep. So this was **not** Claude Code's `Grep` tool; every offending call was an ordinary `grep` typed into the **Bash** tool, which silently became ugrep.
2. **What blows up.** Bounded BRE repeats on *both* sides of a literal, plus `-o -i`, over a file with very long lines. Confirmed by reproduction:
   - `grep -o -i "price[^<]\{0,120\}auction[^<]\{0,120\}\|auction[^<]\{0,120\}price[^<]\{0,120\}"` on `poa.html` → 6.3 GB RSS, ran **9h20m**.
   - `grep -o -i "[^<>]\{0,150\}price[^<>]\{0,150\}"` on the same file → 5.9 GB in 8 min.
   - `grep -n -i -o ".\{0,200\}qr.\{0,300\}"` on an appraisal HTML full of base64 `data:` URIs (Aug 1) → 3.2 GB RSS + 5.7 GB swap.
   Measured locally: **0.87 GB in 12 s (~72 MB/s)**, unbounded. The trigger is **long lines**, not file size — a 157 KB file did it. `-P` (PCRE2 JIT) returns instantly on the same patterns; only ugrep's own RE/flex matcher explodes.
3. **Why it took the whole box down.** ugrep runs inside `code-server.service`'s cgroup, shared by every Claude session. It consumed the allowance as anonymous memory, driving that cgroup's page cache to zero (anon 8.78 GB / file 0.00 GB). Every subsequent file read then missed cache and hit disk, saturating the root disk. Everything went to D-state, including code-server's main process, the ptyHost, and the extension host. **No OOM killer ever fired** — the box thrashed rather than being killed, which is why there is nothing in the kernel log.

Aggravating factor: the Bash tool's 120 s timeout **detaches** the process instead of killing it. Both runaways were orphaned and kept allocating. (This reproduced on me three times during the investigation.)

**Why `resource_guard.py` never caught it** — three independent blind spots, all fixed:
- `reap_orphans()` skips anything with `PPID != 1`. These had a live Claude session as parent, so they were skipped through ~370 guard passes over 9 hours.
- The guard only acted above `MEM_CRIT_PCT = 94.0`. The cgroup cap confined the damage, so *system* memory sat near 71% while code-server suffocated. The guard had no per-cgroup visibility at all.
- `ORPHAN_REAP_PATTERNS` didn't include ugrep.

**Fix:**
- `reap_runaway_search()` — new, runs on **every** pass, **regardless of PPID and regardless of system memory**. Kills grep-family processes at RSS > 2 GB / age > 60 s, or age > 15 min with > 5 min CPU (catches a slow burn before it reaches the ceiling). At the 90 s timer cadence this bounds exposure to ~2 min instead of 9 h. Thresholds are env-overridable (`GUARD_RUNAWAY_*`) for tuning and drills.
  - **Critical detail:** `/proc/<pid>/comm` is `claude` (comm follows the executable), while `argv[0]` is `ugrep` (set by `exec -a`). The matcher keys on **`argv[0]`**. Matching on process *name* would have missed every runaway — or matched every legitimate Claude session.
- `cgroup_pressure()` — reads the code-server slice's `memory.stat` and alerts on the thrash signature (anon high, `file` collapsed to ~0, rising `workingset_refault_file`) even when system-wide memory looks fine.
- `workbench_healthy()` — probes `/healthz` with `curl -sL`. **Verification trap:** a bare `curl http://127.0.0.1:8080/` returns 302 in ~27 ms even when the workbench is completely wedged (that handler never touches the extension host), and `systemctl is-active` stays `active` throughout. Both produced a false all-clear on Aug 6.
- Guard now heartbeats itself via `job_run`/`record_job_result` (Rule 7). It previously had **no** heartbeat — the box's last line of defence could have died unnoticed. Throttled to ~10 min (≈144 Cosmos upserts/day).
- Consolidated the two code-server cgroup drop-ins into one `zz-fields-caps.conf`. The old `zz-resource-caps.conf` had dead 4G/5G values silently overridden by `zz-swap-cap.conf`'s 9G/11G, while its `OOMScoreAdjust=500` was still live. Effective values verified **unchanged** before/after; code-server not restarted.

**Rejected: `ulimit -v` in the Samantha/cron wrappers** (suggested in the brief). Tested and it misfires: a live `claude` agent process shows **VmPeak 9.55 GB / VmSize 5.87 GB against just 329 MB RSS**, so a 2 GB virtual cap would kill healthy agents almost immediately. Virtual address space is a bad proxy for the thing we care about. RSS-based reaping is the correct lever. (`ulimit -v` *would* work on the ugrep shim alone, which peaks ~6 MB VA — but the shim is generated by Claude Code and overriding it is fragile.)

**Source corrected:** the brief attributed this to automated Samantha sessions (`ops_cycle.sh`, cron 07:15). **That is wrong** — no cron job is implicated in either incident. Both trace to Will's *interactive* sessions: session `e7da9ade` (started 21:41 AEST Aug 5, the deep-research run for Page_Redesign_V4) whose subagent `a3c3198d` fired the 9-hour grep at 21:55:14, and session `83848579` on Aug 1 (the QR-code market-report work). The 07:15 ops cycle was a victim, not a cause. Consequence: hardening only the cron wrappers would have fixed nothing.

**Files:** `scripts/resource_guard.py`, `config/systemd/code-server.service.d/zz-fields-caps.conf` (new, mirrored to `/etc/systemd/system/code-server.service.d/`, replacing `zz-resource-caps.conf` + `zz-swap-cap.conf`)

**Recurrence:** Third VM-lockup-class incident — after `[VM-OOM-HARDENING]` and `[VM-WEDGE-PREVENTION]` (both 2026-07-27). Those two addressed accumulated-session memory; neither covered a single runaway child inside the slice, which is the gap this closes.
