## [UGREP-REGEX-VM-LOCKUP] Runaway ugrep wedged the VM twice (Aug 1, Aug 6) — 08:10 AEST

**Symptom:** `vm.fieldsestate.com.au` stopped loading. code-server stayed `active` in systemd, nginx/TLS/DNS all healthy, but the workbench never loaded. Load average 27–41 on 4 vCPUs, iowait 60–80%, root disk pinned at its ~240 MB/s ceiling. SSH eventually unreachable; only a GCP stop/start recovered it. Twice: 2026-08-01 and 2026-08-06.

**Root cause:** A runaway `ugrep`. Three layers, all needed to explain it:

1. **Where ugrep comes from.** Claude Code installs a bash *function* named `grep` that rewrites every shell `grep` into `exec -a ugrep <claude-binary> -G --ignore-files --hidden -I --exclude-dir=…`. ugrep 7.5.0 is statically linked into the `claude` binary — there is no standalone `ugrep` on this box, and `/usr/bin/grep` is still genuine GNU grep. So this was **not** Claude Code's `Grep` tool; every offending call was an ordinary `grep` typed into the **Bash** tool, which silently became ugrep.
2. **What blows up.** Bounded BRE repeats on *both* sides of a literal, plus `-o -i`, over a file with very long lines. Confirmed by reproduction:
   - `grep -o -i "price[^<]\{0,120\}auction[^<]\{0,120\}\|auction[^<]\{0,120\}price[^<]\{0,120\}"` on `poa.html` → 6.3 GB RSS, ran **9h20m**.
   - `grep -o -i "[^<>]\{0,150\}price[^<>]\{0,150\}"` on the same file → 5.9 GB in 8 min.
   - `grep -n -i -o ".\{0,200\}qr.\{0,300\}"` on an appraisal HTML full of base64 `data:` URIs (Aug 1) → 3.2 GB RSS + 5.7 GB swap.
   Measured locally: **0.87 GB in 12 s (~72 MB/s)**, unbounded. The trigger is **long lines**, not file size — a 157 KB file did it. `-P` (PCRE2 JIT) returns instantly on the same patterns; only ugrep's own RE/flex matcher explodes.
3. **Why it took the whole box down.** ugrep runs inside `code-server.service`'s cgroup, shared by every Claude session. It consumed the allowance as anonymous memory, driving that cgroup's page cache to zero (anon 8.78 GB / file 0.00 GB). Every subsequent file read then missed cache and hit disk, saturating the root disk. Everything went to D-state, including code-server's main process, the ptyHost, and the extension host. **No OOM killer ever fired** — the box thrashed rather than being killed, which is why there is nothing in the kernel log.

Aggravating factor: the Bash tool's 120 s timeout **detaches** the process instead of killing it. Both runaways were orphaned and kept allocating. (This reproduced on me three times during the investigation.)

**Why `resource_guard.py` never caught it** — three independent blind spots, all fixed:
- `reap_orphans()` skips anything with `PPID != 1`. These had a live Claude session as parent, so they were skipped through ~370 guard passes over 9 hours.
- The guard only acted above `MEM_CRIT_PCT = 94.0`. The cgroup cap confined the damage, so *system* memory sat near 71% while code-server suffocated. The guard had no per-cgroup visibility at all.
- `ORPHAN_REAP_PATTERNS` didn't include ugrep.

**Fix:**
- `reap_runaway_search()` — new, runs on **every** pass, **regardless of PPID and regardless of system memory**. Kills grep-family processes at RSS > 2 GB / age > 60 s, or age > 15 min with > 5 min CPU (catches a slow burn before it reaches the ceiling). At the 90 s timer cadence this bounds exposure to ~2 min instead of 9 h. Thresholds are env-overridable (`GUARD_RUNAWAY_*`) for tuning and drills.
  - **Critical detail:** `/proc/<pid>/comm` is `claude` (comm follows the executable), while `argv[0]` is `ugrep` (set by `exec -a`). The matcher keys on **`argv[0]`**. Matching on process *name* would have missed every runaway — or matched every legitimate Claude session.
- `cgroup_pressure()` — reads the code-server slice's `memory.stat` and alerts on the thrash signature (anon high, `file` collapsed to ~0, rising `workingset_refault_file`) even when system-wide memory looks fine.
- `workbench_healthy()` — probes `/healthz` with `curl -sL`. **Verification trap:** a bare `curl http://127.0.0.1:8080/` returns 302 in ~27 ms even when the workbench is completely wedged (that handler never touches the extension host), and `systemctl is-active` stays `active` throughout. Both produced a false all-clear on Aug 6.
- Guard now heartbeats itself via `job_run`/`record_job_result` (Rule 7). It previously had **no** heartbeat — the box's last line of defence could have died unnoticed. Throttled to ~10 min (≈144 Cosmos upserts/day).
- Consolidated the two code-server cgroup drop-ins into one `zz-fields-caps.conf`. The old `zz-resource-caps.conf` had dead 4G/5G values silently overridden by `zz-swap-cap.conf`'s 9G/11G, while its `OOMScoreAdjust=500` was still live. Effective values verified **unchanged** before/after; code-server not restarted.

**Rejected: `ulimit -v` in the Samantha/cron wrappers** (suggested in the brief). Tested and it misfires: a live `claude` agent process shows **VmPeak 9.55 GB / VmSize 5.87 GB against just 329 MB RSS**, so a 2 GB virtual cap would kill healthy agents almost immediately. Virtual address space is a bad proxy for the thing we care about. RSS-based reaping is the correct lever. (`ulimit -v` *would* work on the ugrep shim alone, which peaks ~6 MB VA — but the shim is generated by Claude Code and overriding it is fragile.)

**Source corrected:** the brief attributed this to automated Samantha sessions (`ops_cycle.sh`, cron 07:15). **That is wrong** — no cron job is implicated in either incident. Both trace to Will's *interactive* sessions: session `e7da9ade` (started 21:41 AEST Aug 5, the deep-research run for Page_Redesign_V4) whose subagent `a3c3198d` fired the 9-hour grep at 21:55:14, and session `83848579` on Aug 1 (the QR-code market-report work). The 07:15 ops cycle was a victim, not a cause. Consequence: hardening only the cron wrappers would have fixed nothing.

## [VALUATION-MISSING-BEDS-AS-ZERO] Unknown bedroom count valued as ZERO bedrooms — 15:10 AEST

**Symptom:** Found while rendering the V4 prototype for 28 Wedgebill Parade, Burleigh Waters
(off-market, no bedroom/bathroom count on the doc). Every comparable carried
`bedrooms: -$255,000` and `bathrooms: -$120,000` adjustments. The reconciled range came back
**$1,393,218 – $1,773,186**.

**Root cause:** `precompute_valuations.py:3296-3298`

```python
'bedrooms':  subject_doc.get('bedrooms', 0),      # ← the bug
'bathrooms': subject_doc.get('bathrooms', 0),
'car_spaces': subject_doc.get('car_spaces') or subject_doc.get('carspaces') or 0,
```

`calculate_adjustments()` already guards this — `if s_val is None: … skipped: True` — with the
comment *"Missing != zero — a missing value means we don't know the feature, not that it's
absent."* **The `, 0` default defeats its own guard**: the value arrives as `0`, not `None`, so
the skip never fires and the engine subtracts the full per-bedroom rate against every
comparable. A home with an unknown bedroom count was valued as a home with **no bedrooms**.

Same family as the trap already documented in `fact_bundle._obvious_comp` — `.get(k, default)`
returning a default only for an absent key — but here the default itself is the fault.

**Blast radius — measured:**

| Suburb | Off-market houses missing beds/baths | |
|---|---|---|
| Robina | 2,626 / 5,402 | 48.6% |
| Varsity Lakes | 1,066 / 2,903 | 36.7% |
| Burleigh Waters | 1,459 / 3,973 | 36.7% |
| **Total** | **5,151 / 12,278** | **42.0%** |

**For-sale listings are unaffected — 0 of 210 are missing beds/baths**, so no public
`/property/:id` valuation moves. The exposure is off-market subjects and homeowner-submitted
appraisal leads, i.e. exactly the V4 surface and the mini-site.

**Fix:** drop the `0` defaults so `None` propagates and the existing guard fires.

**Verified on 28 Wedgebill:**

| | Range | Confidence |
|---|---|---|
| Before | $1,393,218 – $1,773,186 | medium |
| **After** | **$1,702,859 – $2,167,275** | **high** |

**+$310k on the low, +$394k on the high — roughly 22% — and confidence rose** because removing

## [CANONICAL-CONFIG-DRIFT] canonical_attributes.yaml had drifted from the data and from the engine — 18:20 AEST

**How it surfaced.** A 30-property batch render reported §2 (the adjusted comparables — the
whole traceability argument) at 40% coverage. Digging in, the cause was **my batch harness**, not
the product: the engine resolves its comparable pool from `subject_doc['_collection']` or
`subject_doc['suburb']`, and **`suburb` is NULL on every off-market document**. Without
`_collection` the pool is empty and every valuation returns a confident `insufficient_data`.
`run_subject_valuation.py` sets it; the batch did not. Corrected: **§2 coverage is 77%, not 40%.**

That prompted the real question — how many other consumers are guessing where a fact lives?

**Root cause:** `config/canonical_attributes.yaml` declares an ordered `source_priority` per
attribute and `canonical_resolver.py` walks it. Nothing had ever verified the declared paths
against the data. Three classes of drift, all found by measurement:

**1. Chains too short.** `bathrooms` declared ONE path; 56% of the 5,148 missing values sat in
undeclared paths. `bedrooms` the same — 72% of 4,941 recoverable, undeclared. Both extended.

**2. Dead paths — declared but never present in 1,200 sampled docs:** `parking`,
`property_valuation_data.layout.land_size_sqm`, `enriched_data.beach_distance_km`. Removed.

**3. ⚠ `floor_area_sqm` was INVERTED against the engine.** `resolve_floor_area()` states:
*"Building area — Domain `total_floor_area` then `house_plan.floor_area_sqm` (internal + garage
+ sometimes covered patio) — is a DIFFERENT metric, used for 'internal' ONLY as a last resort."*
The config listed **`house_plan.floor_area_sqm` FIRST**. On 38 docs holding both, the building
figure runs ~1.5× the internal one (median ratio 0.67; −96 m², −106 m², −97 m² on individual
homes). Anything resolving through the config got a materially larger number than the valuation
used — and the engine's own warning is that mixing the two metrics across a subject and its
cohort *"invalidates the premium maths"*. Chain reordered to mirror `resolve_floor_area()`.

**Also measured — the facts themselves are consistent.** The scatter is scraper generations
layered over time, not conflicting systems:

| | |
|---|---|
| `lot_size_sqm` vs `lot_size_calc_sqm` | median difference **0.1%**, max 5% — a rounding variant |
| `bedrooms` — where sources conflict (17.8%) | 91 of 107 are **one room** apart |
| `scraped_data_v2.bedrooms` vs the top-level field | agree **99.1%** (n=551) — retro-validates the morning's backfill of 3,568 homes |

**Fix:** config → **schema_version 3**. New `scripts/audit_canonical_paths.py` checks coverage,
agreement (with a 2% numeric tolerance so rounding variants don't drown the real conflicts),
dead paths and undeclared paths. **Declared issues: 12 → 6.**

**Left open deliberately, needing a definition call rather than a guess:**
- `property_valuation_data.layout.number_of_bedrooms` disagrees with the listed count on 42% (vision vs agent-listed). Last in the chain, so rarely reached.
- `satellite_analysis…pool_visible` disagrees with the vision read on 31%.
- `floor_plan.stated_internal_area_sqm` and `floor_plan_analysis.internal_floor_area` are declared by the engine but never present in the sample — either the enrichment never ran or the paths are wrong.

## [DECK-STALE-AFTER-VALUATION] A valuation landing never rebuilt the deck — 19:40 AEST

**Symptom:** the `comparable` card — *"that sale up the road isn't your comparison"*, the
sharpest device in the deck — renders on **22 of 400 live decks (5.5%)**. Reproduced in a
seeded 30-property sample: **0 of 29 cached bundles carried an `obvious_comp`, while 23 of
those 29 documents already held the `valuation_data.recent_sales` it is built from.**

**Root cause:** `offmarket_discovery_nightly._needs_build()` decided staleness on
`enriched_data.last_enriched > generated_at` alone. **Writing `valuation_data` does not touch
`enriched_data.last_enriched`**, so a home that gained a valuation never qualified for a
rebuild. `fact_bundle._obvious_comp` reads `valuation_data.recent_sales`, so the card could
never appear for any home valued after its deck was first built. The bundle is the expensive
harvest and is cached, so the staleness test is the only thing that can refresh it.

**Fix:** `_needs_build` now takes `valued_at` and rebuilds when **any** input is newer than the
deck — `max(last_enriched, valuation_data.computed_at) > generated_at`. Added `_stamp()` to
normalise the three formats involved (ISO string, datetime, isoformat+Z); comparing them raw
was fragile. Both home generators now project and yield `valuation_data.computed_at`.

**Verified** on 28 Wedgebill Parade — deck generated 2026-08-05T08:45, valued 2026-08-06T05:04:

| | needs rebuild |
|---|---|
| old logic (enrichment only) | **False** ← the bug |
| new logic (+ valuation) | **True** |

**⚠ Honest scope: the immediate effect is small — dry run says 31 homes.** Not because the fix
is weak, but because **off-market valuations barely exist yet**: they are built on demand and
the service has served ~40 requests in its lifetime. So the real sequence is (1) valuations get
computed for off-market homes at volume, (2) decks rebuild — now possible, (3) the comparable
card appears. This fix removes step 2 as a blocker; step 1 is the actual constraint and is
unresolved.

## [POOL-UNKNOWN-AS-NO-POOL] Unknown pool valued as NO pool — ~894 homes penalised ~$75k — 20:15 AEST

**Question that surfaced it (Will):** does the adjusted-comparables valuation need a vision model
per property? If it does, valuations must stay on demand; if not, the whole off-market book can
be computed on an interval.

**Answer: it makes no AI call.** `precompute_valuations.py` imports only
`os/sys/time/math/datetime/dotenv/pymongo/statistics/re/numpy` — no model client, no HTTP.
Measured runtime ~100ms/property. Vision runs SEPARATELY (pipeline steps 105/106/108/117) and
writes `property_valuation_data`; the valuation only READS it. **84% of off-market houses
already have that analysis** (Burleigh Waters 96.9%, Varsity Lakes 89.9%, Robina 71.3%).

So the cost profile is the inverse of what on-demand assumes: the expensive part is the SHARED
caches (~25-130s), built once; per property is ~100ms. On-demand rebuilds those caches per
request — which is why one valuation took 30-90s while 200 in a batch took 42 seconds.

**But tracing it exposed a defect.** For the 1,967 homes with no vision, the engine applied
silent defaults:

| default | verdict |
|---|---|
| `condition_score -> 5`, `renovation_level -> 3`, `cladding_level -> 2` | defensible midpoints |
| **`pool_present -> False`** | **not defensible — asserts a negative** |

**45.5% of vision-analysed homes have a pool** (Burleigh Waters 55.7%). So of the 1,967
unanalysed, roughly **894 likely have a pool and were valued as though they don't**, taking the
full pool rate (~$75,000) against every comparable that has one. Same defect class as the
zero-bedroom default fixed earlier today: an absent input becoming a confident negative claim.

**Fix — three levels, since the False was re-applied at each:**
1. `extract_features`: `outdoor.get('pool_present', False) if outdoor else False` → `None` when the analysis never ran.
2. `subject_features` / comp features: `.get('pool_present', False)` → `.get('pool_present')`.
3. `calculate_adjustments`: skip the pool adjustment entirely when either side is `None`, matching the guard the continuous features already had.

Verified on 28 Wedgebill (which HAS vision): range unchanged at $1,753,450–$2,231,664 — correct,
the fix must only affect homes where the pool is genuinely unknown.

**New: `scripts/batch_value_offmarket.py`** — computes the book with shared caches, skips homes
valued within 30 days, self-reports via `job_run(cadence_hours=168)` per Rule 7. Smoke test:
200 homes in 0.7 min (5/s), 166 with adjusted comparables (83%), confidence high 112 / medium 54
/ not_available 34. Full book = 12,250 homes, ~40 min.

`scripts/batch_value_offmarket.py` (new)

## [NIGHTLY-DECK-CAP] Two correct changes made the nightly a 6-hour job; capped it — 21:05 AEST

**The interaction, not a bug in either part.** `offmarket_discovery_nightly.py` runs at **00:20
daily** (cron `20 0 * * *`) and historically built almost nothing — the last four runs were
`to_build` = 0, 2, 0, 1, finishing in 0-4s — because staleness keyed off
`enriched_data.last_enriched`, which rarely changes.

Two same-day changes altered that, and both are correct:
1. `[DECK-STALE-AFTER-VALUATION]` — `_needs_build` now also triggers on
   `valuation_data.computed_at`, without which the obvious-comparable card can never appear.
2. `scripts/batch_value_offmarket.py` — writes a fresh valuation to the whole off-market book.

Together the backlog becomes ~10,000 decks. **Measured cost: 2.1s per rebuild** (five real
properties; min 0.5s, max 6.1s) → **~6 hours in one run**, starting 00:20 and holding Cosmos RUs
through the morning crons on a serverless tier with a ~5,000 RU/s burst limit.

**Fix:** `DEFAULT_NIGHTLY_CAP = 3000`, plus **oldest-deck-first ordering** so a capped run drains
the backlog deterministically rather than rebuilding whichever homes happen to sort first. Homes
with no doc at all go to the front — they render nothing today. Decks not reached keep serving
their current content, which is what they would have done anyway. Self-healing: each night takes
the next oldest slice. `--limit` overrides; `--limit 0` disables the cap.

Output now reports both figures so the backlog is visible rather than implied:

```
indexed=14645  have_docs=26297  backlog=2163  to_build=500  (capped at 500; 1,663 deferred)
```

`beat.metrics` gains `backlog`, so the Systems Health board shows the queue draining.

**Verified:** dry run with `--limit 500` correctly defers 1,663; unlimited dry run at the time
showed backlog 2,123 (the batch was still running).

**Batch status at time of writing:** 3,037 of 12,278 valued, **79% of them carrying adjusted
comparables** — matching the 83% smoke-test rate and the 77% §2 coverage measured in the render
sample.
