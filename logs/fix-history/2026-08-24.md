## [ROTATED-SECRET-NOT-DELIVERED] Rotated .env secrets never reach running daemons — REC-ops-004 — 10:01 AEST
**Symptom:** Rotating a secret in `/home/fields/Fields_Orchestrator/.env` did not reach any already-running systemd service. `fields-voice-agent` and `fields-watchdog` were still holding credentials frozen at their 2026-08-06 start; the stale Bright Data key (`05c1f723…`) returned HTTP 401 while the live `.env` key (`e974dc13…`) returned 200. **Root cause:** systemd reads `EnvironmentFile=` once, at unit start. A `.env` edit is invisible to a live daemon until it is restarted. Nothing forced that restart, so rotation depended on a human remembering to bounce every affected service.
**Fix:** Two parts (both approved by Will 2026-08-18 on REC-ops-004).
  1. Immediate: `systemctl restart fields-voice-agent fields-watchdog`; verified voice-agent's held `BRIGHTDATA_API_KEY` now matches the live `.env` key via `/proc/PID/environ`.
  2. Durable (automatic, per Will): `scripts/restart_env_dependent_services.sh` + `fields-env-watch.timer` (every 60s) + `fields-env-watch.service` (oneshot). The script sha256-hashes `.env`, compares to a stored baseline (`logs/.env-watch.hash`), and on change restarts every ACTIVE service whose unit declares this `.env` as `EnvironmentFile` (discovered dynamically, not hardcoded — new services are covered automatically). It only advances the stored hash on a fully clean restart (Rule 7b: never advance a watermark on a failed run), and seeds the baseline without restarting on first observation.
  Chose a hash-diff timer over a systemd `.path` unit: the `.path` inotify watch fired on in-place writes but NOT on cross-dir atomic replace (temp+mv), which is exactly how some rotations write the file — it would have silently missed the case it exists to catch. The timer catches every write pattern deterministically (≤60s latency; rotations are rare).
**Verification:** End-to-end — changed `.env`, timer fired at 10:00:25, detected the hash change, re-delivered to all 17 `.env`-dependent services, all returned active. Unit files copied to `deploy/systemd/` for disaster recovery.

## [SLICE-HOG-REAPER] Generic slice-hog reaper + backup retention boundary — closes SLICE-THRASH-MONGO-LIST — 16:45 AEST
**Symptom:** Follow-up to `[SLICE-THRASH-MONGO-LIST]` above, which was resolved by hand (`kill -9`) and left three items open: no generic reaper, a wide MemoryHigh/MemoryMax throttle band, and `/` at 88%.
**Root cause (why no guard fired):** `resource_guard.py` had exactly two reapers and the runaway fell between them. `reap_orphans()` requires `PPID==1` — the runaway's parent chain (claude → bash → python3) was alive throughout. `reap_runaway_search()` matches `os.path.basename(cmdline[0])` against `RUNAWAY_ARGV0 = {"ugrep","ug","grep",...}` — it was written for the Aug 1/Aug 6 ugrep lockups, and this runaway's argv[0] was `python3`. The guard *detected* the condition correctly (`level=critical … cgroup_thrashing … workbench_unhealthy streak=47`) and Telegrammed for ~70 minutes with no action available to it. An argv[0] allowlist can only ever chase the last incident.
**Fix:**
- **`reap_slice_hog()` (new, process-agnostic).** Kills any single process in the `code-server.service` cgroup over an RSS ceiling — `GUARD_SLICE_HOG_RSS_GB` (default 6.0), dropping to `GUARD_SLICE_HOG_THRASH_RSS_GB` (default 4.0) once `cgroup_pressure()` reports the slice thrashing. Runs every pass, not gated on system-wide `mem_pct` (a cgroup-confined runaway never moves that number). 6GB sits far above both the measured steady-state peak in this slice (~650MB, the extensionHost, across 42 procs) and the worst legitimate `claude` on record (3.8GB, 2026-07-27), yet well under the 9G `MemoryHigh` — so a hog now dies *before* it can push the slice into the throttle band where it starves its siblings.
- **Safety is structural, not a denylist.** Candidates come from `SLICE_CGROUP/cgroup.procs`. Verified on this box: sshd sessions live in `user.slice/user-<uid>.slice/session-N.scope`, and mongod / fields-orchestrator in their own `system.slice` units — none can appear in that file, so the reaper cannot reach them. The slice is flat (no nested cgroups), so one read is total.
- **Structural processes are reported, never killed.** `out/node/entry`, `--type=extensionHost`, `--type=ptyHost` — killing one of those takes down every session to save one, so a hog there raises a distinct alert asking for a human call instead.
- `cgroup_pressure()` moved ahead of the reapers in `main()` so the thrash-lowered ceiling is available; the thrashing alert now also states whether a runaway was killed on the same pass.
- **`mongodb-backup.sh` retention boundary.** `-mtime +N` truncates age to whole 24h units (so it means "≥ N+1 days"). With cron firing at a fixed 02:00 daily, each archive crossed the boundary within *seconds* of the `find` running and landed on the wrong side of that truncation — 5 archives (7.4GB) against a policy of 4, while the log reported "keeping last 3 days". Switched to `-mmin +$(( LOCAL_KEEP_DAYS * 1440 - 60 ))` (2.95 days), unambiguous regardless of cron jitter. Policy/RPO unchanged.
- **Disk.** Deleted the 4 redundant local mongodump archives after verifying each against `gs://fields-mongodb-backups` by **crc32c and byte size**, not size alone (all 4 MATCH). Kept 2026-08-24 as a warm local copy. `/` 88% → 82%, free 12G → 18G. GCS bucket untouched (32 objects).
**Verification (live drill on the VM, `--dry-run`):** at the default ceiling → `level=ok no actions` (no false positives; cgroup `thrashing: False`, page cache recovered 0.0 → 1.22GB, workbench 200). With the ceiling driven to 0.3GB → `slice_hog_structural[NOT killed]` for pid 841 (`out/node/entry`) and pid 1182181 (extensionHost), plus a correctly-selected `reap_slice_hog[rss]` candidate. That exercises cgroup enumeration, RSS math, structural protection and kill-path selection without killing anything. Both files syntax-checked on the VM's own interpreter (`py_compile`, `bash -n`).
