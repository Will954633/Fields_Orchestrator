## [REPORT-LINK-KEY-MISSING-PRODUCERS] Eight /your-home link producers left key-less by the enumeration gate — 07:45 AEST
**Symptom:** Will opened
`/your-home/31-28-castello-circuit-varsity-lakes?utm_source=offmarket_direct_test_v2&utm_medium=organic`
and the V1.5 mini-site would not load; console showed
`/api/v1/property-report?slug=31-28-castello-circuit-varsity-lakes 404`.
The document exists (`state: under_review`, created 2026-08-19 12:21 by the off-market
direct test). Confirmed the gate, not the data: the identical request with a computed
`k=5qjdRguKPqf1S7h8` returns **200**.

**Root cause:** `[REPORT-API-ENUMERATION-GATE]` (2026-08-19 20:30) gated the report
endpoints behind an HMAC link key and updated the producers it knew about — AYH submit,
progress `ready_url`, the mailer QR artwork, the tracking server. **Eight other producers
of `/your-home/<slug>` links were never found**, and each kept emitting a bare path.

Because `mayReadReport` deliberately answers **404, not 403** (a 403 would confirm the slug
exists and restore the enumeration oracle it closes), a key-less link does not present as a
permission problem to whoever opens it. The report simply appears not to exist. That is why
this went unnoticed for a day and why the gate's own live verification could not catch it:
every check in that entry tested the *endpoint's* behaviour with and without a key, and all
of them passed. Nothing tested whether the things that **build** links still built valid ones.

The two that matter most were customer-facing, not internal:
1. **`off-market.$slug.tsx:412`** — the direct-test redirect, built as
   `/your-home/${slug}?utm_source=...` with no `k`. The visitor has **no device token to
   fall back on** either: the stub is created server-side by `analyse-your-home-submit`
   with a server-generated token the browser never sees, so the URL key is their *only*
   proof of access. Every admission after 20:30 on 08-19 would have sent a real organic
   Google visitor to a page saying their report does not exist — the V1.5 arm of a live A/B
   test was a blank page. All 5 round-2 admissions (10:13–14:26 on 08-19) predate the gate,
   so no visitor was actually burned; the next one would have been.
2. **`ayh-lead-fulfil.mjs:60` and `offmarket-notify.mjs:122`** — both EMAIL the recipient
   "your report is ready" with a link that 404s. The second goes to someone who paid **$15**.

The rest were Telegram/email notifications to Will (`property-report-book-review`,
`property-report-message-send`, `square-payment`, `property-plan-submit`), the
`justcall-sms` fallback branch, and the `BuildingPage` error-box escape hatch.

**Fix:**
- **`db.mjs` — `reportPath(slug, hash)` / `reportUrl(slug, hash)`.** The real defect is that
  a correct link required remembering an invariant, so the fix is to make the correct link
  the easy one: one import, one call, key included. Both carry the comment explaining why
  a key-less link reads as "gone" rather than "forbidden".
- Routed all eight producers through it. `tryAdmitDirectTest` now returns `k` alongside
  `slug` (both return paths, including the 10-minute duplicate-visit short-circuit) and the
  loader appends it via `URLSearchParams`, preserving the `no-store` headers untouched.
- `BuildingPage` now renders "try opening the page directly" **only** when the server has
  handed it a key-bearing `ready_url` — the previous bare link would have replaced one
  error with a worse one.
- `HomeRecognitionModal.tsx:141` left alone: its `data.redirect_url` already carries `k`
  and the key-less fallback is unreachable on that branch (`existing && state !== 'stub'`
  always yields a `redirect_url`).

**Verification:** `tsc --noEmit` clean; `node --check` on all 9 functions. Key parity
against the values recorded in yesterday's entry — `21-royal-links-drive-robina` →
`AZLSMkAUjAwQ_Qfs`, byte-identical. Live: the reported slug returns 200 with `k` and 404
without, before and after deploy.

**⚠ Not verified end-to-end:** the direct-test redirect itself cannot be exercised on
demand — it needs a Google referrer, a residential AU IP, and a free admission slot. The
key is now built by the same helper proven above, but the first real admission is still the
first live proof. Worth watching the next Telegram admission notification: its `Mini-site:`

## [MAILER-PRINT-SPEC-BLEED] Pronto print file — 3mm bleed, crops, one 100pp PDF — 11:35 AEST
**Symptom:** Not a defect — John Thwaites (Pronto) replied with his RIP spec and the
artwork we had supplied met none of it: 50 separate A4 PDFs, trim-size only, no bleed,
no marks. Printed as supplied, any cut running 1 mm out shows white on the deep-green
bands that run to all four edges.
**Root cause:** The mailer was authored as an A4 screen document (`@page { size: A4 }`,
`.page` 210×297) and shipped straight to a press. No step in the chain ever asked what
the printer's RIP wanted, so the question only surfaced after John was holding the file.
**Fix:** New `build_pronto_print_pdf.py` — reads `manifest.csv` in row order and lays
every page onto 230×317 mm: trim 210×297, bleed 216×303 (both boxes tagged), crop marks
offset 3 mm / 5 mm long, registration targets mid-edge, all clear of the bleed. One
combined 100-page file, piece n on pages 2n-1 and 2n. Left in RGB — Pronto convert.
The artwork is NOT scaled up to make bleed (that costs 3 mm of design at every edge and
the tightest text on p2 sits 5.6 mm off trim); the outermost 0.5 mm of each edge is
stretched outward instead, which is exact because every edge is flat colour and no photo
reaches one. Uploaded to the Pronto Drive folder; the 19 Aug zip and its READ_ME moved to
`SUPERSEDED_2026-08-19_zip_no_bleed_DO_NOT_PRINT`; new READ_ME answers John's 3 questions.
**Two things the build caught on itself:**
- `show_pdf_page` defaults to `keep_proportion=True`, so the first build scaled each
  0.5 mm bleed strip to fit and centred it, leaving a **white hairline just outside
  trim** — invisible at page zoom, exactly what prints on a 1 mm-off cut. Found by eye
  at 600 dpi, then codified: `bleed_gaps()` compares the colour 2 mm outside trim with
  0.5 mm inside it on all 100 pages and the build refuses on a mismatch (Rule 7b — the
  check was proved against a negative control that reproduces the bug, p98 delta 222).
- QR decode is re-run on the **combined** file, not trusted from the assembler: the
  lay-up is a re-render. 3 of 50 failed at 200/400 dpi and needed a dpi sweep plus a
  crop to the CTA block — a detector limit, not bad artwork, but the script cannot tell
  those apart so it refuses either way. 50/50 verified in the shipped file.
Also verified: 100 pages, order matches manifest row-for-row (address text checked on
every odd page), boxes read back at 230×317 / 216×303 / 210×297, upload size matches
byte-for-byte.
**Files:** 11_House_Mini_Site/_shared/mailer_v2/build_pronto_print_pdf.py (new),
11_House_Mini_Site/_shared/mailer_v2/RUNBOOK_batch_to_pronto.md

## [VAL-FLOOR-SANITY] 28 Merion Court floor_area_sqm=30 escapes the 2026-04-02 guard via a second resolver — 11:45 AEST
**Symptom:** While building the formal valuation report page for 27 Huntingdale Crescent, the schedule of comparable sales rendered "28 Merion Court — 30 m² living area" on a house that sold for $1,810,000, while the adjustment grid on the same page used 233 m² for the same property. Two sections of one document disagreeing about one number.
**Root cause:** Two independent floor-area resolvers exist in `precompute_valuations.py` and only one was fixed on 2026-04-02.
  - `resolve_floor_area()` (:2514-2592) — enforces `MIN_FLOOR_AREA = 40`, correctly rejects the 30 and returns 233. This is the one the April fix hardened. It feeds `adjustment_result.adjustments.floor_area.comp_value`.
  - `basic_features()` (:3193-3197) — a legacy helper with **no sanity gate at all**, which reads `doc.floor_area_sqm` *first* — the exact field `resolve_floor_area` ranks *last* because it is unreliable. It feeds `features.basic.floor_area_sqm`.
  The April entry claimed "the 40sqm sanity check will prevent this class of error for all properties." That was wrong twice over: it guarded one of two code paths, and 40 sqm is a plausible apartment but never a house, so bad scrapes between 40-80 sqm still pass.
  The enrichment layer had already diagnosed this exact property — `floor_plan_analysis.internal_floor_area` carries the note "floor_area_sqm field (30) is a scraped room dimension, not actual floor area." `basic_features` ignores that annotation and takes the 30 verbatim.
**Impact (measured, not assumed):**
  - **Reported valuations are clean.** Line 3903 prefers `comp_bd_inputs` over `basic`; across all three collections there were **0 cases** where an adjustment used the implausible `basic` value. 27 Huntingdale's $1,522,634 is unaffected.
  - **One source property, 4,116 denormalised copies** — 28 Merion Court appears as a comparable inside 4,116 robina subject documents (93.0% of those carrying `recent_sales`).
  - **Public surfaces do display it:** `ValuationEvidence.tsx:627` renders "30m² floor" while :758 on the *same card* says "41.0 m² smaller floor area" off the correct 233; `fact_bundle.py:266` writes a false "{N}m² more/less floor area" claim into off-market deck card 06 prose for 9 robina homes; `generate_property_analysis.py:393` feeds "Floor: 30 sqm" into the LLM prompt behind published property copy.
  - **Separate, larger valuation defect found:** `MIN_FLOOR_AREA = 40` (:2544) is too low for a detached house. **36 valued Houses** carry an *authoritative* floor area under 80 sqm, where the bad scrape passed the gate and **does** reach the valuation (e.g. `18 KIRRALEE DRIVE` 40 sqm, `3 PYMBLE PLACE` 45 sqm).
  - Netlify functions are clean — the only one touching `recent_sales` projects address/price/date only.
**Fix:** **None applied to production.** The report page defends itself: `16_Valuation/report_page/build_report_page.py:126-149` (`attrs_from_adjustments`) sources the schedule from the adjustment lines rather than `features.basic`, so the two sections cannot diverge. The upstream fix — replacing the chain in `basic_features()` with `resolve_floor_area(doc)`, and gating `MIN_FLOOR_AREA` on `property_type` — changes live valuation output and requires a full precompute re-run across three collections. Escalated to Will rather than applied unattended.
**Files:** `16_Valuation/report_page/build_report_page.py` (new — defensive read only). No production file modified, no database write.
**Recurrence:** **Second** — first was 2026-04-02, same property, same field, same value. The class of defect is "a guard added to one of two duplicate code paths, with the entry recording it as fixed for all". Same shape as `[UNIT-NUM-ALIAS-EATS-FLOOR-AREA]` and the design-envelope guard keyed to a value the model could never produce (see `valuation_design_envelope` memory).
