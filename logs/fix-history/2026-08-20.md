# Fix History — 2026-08-20

## [REPORT-LINK-KEY-MISSING-PRODUCERS] Eight /your-home link producers left key-less by the enumeration gate — 07:45 AEST
**Symptom:** Will opened
`/your-home/31-28-castello-circuit-varsity-lakes?utm_source=offmarket_direct_test_v2&utm_medium=organic`
and the V1.5 mini-site would not load; console showed
`/api/v1/property-report?slug=31-28-castello-circuit-varsity-lakes 404`.
The document exists (`state: under_review`, created 2026-08-19 12:21 by the off-market
direct test). Confirmed the gate, not the data: the identical request with a computed
`k=5qjdRguKPqf1S7h8` returns **200**.

**Root cause:** `[REPORT-API-ENUMERATION-GATE]` (2026-08-19 20:30) gated the report
endpoints behind an HMAC link key and updated the producers it knew about — AYH submit,
progress `ready_url`, the mailer QR artwork, the tracking server. **Eight other producers
of `/your-home/<slug>` links were never found**, and each kept emitting a bare path.

Because `mayReadReport` deliberately answers **404, not 403** (a 403 would confirm the slug
exists and restore the enumeration oracle it closes), a key-less link does not present as a
permission problem to whoever opens it. The report simply appears not to exist. That is why
this went unnoticed for a day and why the gate's own live verification could not catch it:
every check in that entry tested the *endpoint's* behaviour with and without a key, and all
of them passed. Nothing tested whether the things that **build** links still built valid ones.

The two that matter most were customer-facing, not internal:
1. **`off-market.$slug.tsx:412`** — the direct-test redirect, built as
   `/your-home/${slug}?utm_source=...` with no `k`. The visitor has **no device token to
   fall back on** either: the stub is created server-side by `analyse-your-home-submit`
   with a server-generated token the browser never sees, so the URL key is their *only*
   proof of access. Every admission after 20:30 on 08-19 would have sent a real organic
   Google visitor to a page saying their report does not exist — the V1.5 arm of a live A/B
   test was a blank page. All 5 round-2 admissions (10:13–14:26 on 08-19) predate the gate,
   so no visitor was actually burned; the next one would have been.
2. **`ayh-lead-fulfil.mjs:60` and `offmarket-notify.mjs:122`** — both EMAIL the recipient
   "your report is ready" with a link that 404s. The second goes to someone who paid **$15**.

The rest were Telegram/email notifications to Will (`property-report-book-review`,
`property-report-message-send`, `square-payment`, `property-plan-submit`), the
`justcall-sms` fallback branch, and the `BuildingPage` error-box escape hatch.

**Fix:**
- **`db.mjs` — `reportPath(slug, hash)` / `reportUrl(slug, hash)`.** The real defect is that
  a correct link required remembering an invariant, so the fix is to make the correct link
  the easy one: one import, one call, key included. Both carry the comment explaining why
  a key-less link reads as "gone" rather than "forbidden".
- Routed all eight producers through it. `tryAdmitDirectTest` now returns `k` alongside
  `slug` (both return paths, including the 10-minute duplicate-visit short-circuit) and the
  loader appends it via `URLSearchParams`, preserving the `no-store` headers untouched.
- `BuildingPage` now renders "try opening the page directly" **only** when the server has
  handed it a key-bearing `ready_url` — the previous bare link would have replaced one
  error with a worse one.
- `HomeRecognitionModal.tsx:141` left alone: its `data.redirect_url` already carries `k`
  and the key-less fallback is unreachable on that branch (`existing && state !== 'stub'`
  always yields a `redirect_url`).

**Verification:** `tsc --noEmit` clean; `node --check` on all 9 functions. Key parity
against the values recorded in yesterday's entry — `21-royal-links-drive-robina` →
`AZLSMkAUjAwQ_Qfs`, byte-identical. Live: the reported slug returns 200 with `k` and 404
without, before and after deploy.

**⚠ Not verified end-to-end:** the direct-test redirect itself cannot be exercised on
demand — it needs a Google referrer, a residential AU IP, and a free admission slot. The
key is now built by the same helper proven above, but the first real admission is still the
first live proof. Worth watching the next Telegram admission notification: its `Mini-site:`
line now carries `k`, so if that link opens, the redirect did too.

## [PRIORITY-CALLS-TAB] Human call outcomes had nowhere to live — 10:58 AEST
**Symptom:** Will rang the two GC seller-intent leads (Tania Callaghan, Kerry Gillespie).
Everything he learned — that Tania didn't answer, the SMS he sent her verbatim, that Kerry
wants a self-serve valuation and explicitly does not want a person involved — existed only
in his phone. The CRM had no field for any of it, and the Live Leads Tracker's "All Leads"
tab is insert-only chronological, so it answers "who came in?" but never "who do I ring
today?". A follow-up agreed on a call was a thing only human memory tracked.
**Root cause:** every write path into crm_contacts is automation inferring from observed
behaviour. There was no path for a fact only Will holds, and therefore no due-date field
for anything to schedule against.
**Fix:**
- New `scripts/log_contact_touch.py` — appends to the existing `communications[]` and
  `notes[]` arrays (shapes matched to what `engagement_activity_to_sheet.py` already reads,
  so touches render in "already sent" for free), and sets `follow_up_at` /
  `follow_up_reason` / `follow_up_channel` / `contact_preference` / `contact_status`.
  Refuses to create a contact that doesn't exist rather than inventing one.
- New `scripts/priority_calls_to_sheet.py` — renders the "Priority" tab, forced to index 0,
  from `crm_contacts.follow_up_at` within 14 days, overdue first. Done column is a real
  checkbox and is harvested back into the CRM (clears `follow_up_at`) BEFORE the rebuild,
  so a tick is a write, not a note that gets wiped on the next run.
- Wired into `nightly_lead_chain.py` as a final step (`needs=["crm_sync"]` only, so the tab
  stays correct on a night enrichment fails). Rule 7 heartbeat `priority_calls_to_sheet`,
  cadence 24h; Rule 7b assertion raises when `follow_up_at` docs exist but zero rows render
  — an empty diary (`pending_total == 0`) is success, a silently empty tab is not.
- Also repaired `name` and `phone` on both contacts by hand from `fb_leads` (see the
  separate field-name defect below — `crm_lead_sync.py` reads `f.get("phone")` where the
  form field is `phone_number`, so no FB lead has ever had a phone in crm_contacts).
**Gotcha:** Sheets `USER_ENTERED` strips the leading `+` from `+61422403596`. Phone is
written with a leading apostrophe to force text, or the number can't be tapped to dial.

scripts/nightly_lead_chain.py
