## [BRAIN1-VERIFY-BOLD-QUOTES-UNCHECKED] Publish gate read ~none of the brief and passed it — 08:05 AEST

**Symptom:** ran `brain1_verify.py` over the first Brain 1 cold-calling brief. It emitted a clean
run with **no findings and no summary line** — which reads as "nothing wrong". It had in fact
checked almost nothing.

**Root cause:** `parse_pairs()` extracted quoted spans only from `"..."` / `“...”`. But
`brain1_deep.py`'s synthesis renders verbatim corpus material in **bold**, not quotation marks. On
the q2 brief that is **88 bold spans of real quoted material against ~26 quoted pairs** — so the
overwhelming majority of the verbatim content, i.e. exactly the text that could be fabricated or
misattributed, was never looked at. Extraction returned **0 pairs**; after the fix, **98**.

**Why this is the more dangerous of today's two verifier defects.** `[BRAIN1-VERIFY-CORPUS-GAP]`
failed *loudly* — it screamed NOT_FOUND at genuine quotes, so it produced visible false alarms.
This one failed *silently and confidently*: a brief could carry a fabricated quote and the gate
would pass it without comment. A gate that cries wolf gets ignored; a gate that says nothing gets
believed. Same class as Rule 7b — a clean exit that asserted no outcome.

**Fix:** `parse_pairs()` now pairs ids against three carriers of verbatim text on the same line —
quotation marks, `**bold**` spans, and `>` blockquotes — deduped per line.
⚠ **Known, accepted noise:** the synthesis also uses bold for its own emphasis and for labels, so
some extracted "quotes" are the author's prose and will report NOT_FOUND falsely. Guards applied
(min 40 chars, skip label-like spans ending in `:`, skip ALL-CAPS headings), but the residue is
real. **This makes reading the failure list mandatory rather than optional — the headline fidelity
percentage on a brain1_deep brief is now a floor, not a score.** That matches the standing warning
that the verifier scores badly on documents that discuss citations.

**Files:** `scripts/samantha/brain1_verify.py`

**Recurrence:** 1st for this defect. 2nd verifier defect found today; both were found by using the
tool rather than trusting it, and neither was visible from its exit code.

**Not done:** the real fix is for `brain1_deep.py` to emit quoted material in quotation marks (or a
machine-readable citation form) so the gate does not have to infer intent from markdown styling.
Extraction heuristics over prose formatting will keep producing both false positives and misses.

## [CALLQUEUE-SUPPRESSION-ESCAPES-BY-TRACK-AND-ADDRESS] A suppressed person could be re-queued — 08:55 AEST

**Symptom:** a person who says "take me off your list" is written `status: do_not_contact`, and the
caller is scripted to tell them it is done. Two paths re-queue them anyway. Found while verifying a
research finding against the code rather than accepting it; nothing has dialled yet, so no one has
actually been re-contacted.

**Root cause:** `queue_id()` is `f"{track}:{address_slug}:{phone}"` and `upsert_rows()`'s guard only
looks up that exact `_id`. Suppression is therefore keyed to a (track, address, phone) triple, but
it is a property of the **person**.
1. **Track change.** Suppressed as `B_intent:12-smith-st:0412…`, reappears as
   `C_openmarket:12-smith-st:0412…` — different `_id`, `existing` is None, re-queued as "queued".
   Track B→C is the planned expansion path (`00_SCOPING.md` §1), not hypothetical.
2. **New address.** `read_call_outcomes.py` sweeps a suppressed number across other addresses, but
   only over docs `queued`/`listed` **at that moment**. A later ID4ME append finding the same
   number at a second property (investor, previous occupant) creates a doc the sweep never saw.

**Why it matters beyond tidiness:** it makes the caller's "I'll get it taken off" false. A promise
of suppression that the system silently reverses is the fact pattern most likely to satisfy the
**"reckless" element of the statutory tort** (Privacy Act Sch 2, commenced 10 Jun 2025) — and
**cl 6(3) disregards the rest of the Act, so the small-business exemption is no shield.** It is
also a DNCR exposure: the person most likely to complain is the one who already asked us to stop.

**Fix:** `upsert_rows()` now preloads every `do_not_contact` phone and skips any row carrying one,
**before** the `_id` lookup — so suppression is enforced by phone across every track and address.
The skip is counted (`skipped_suppressed_phone`), reported in the run's `beat.metrics`, and printed
with a ⛔ line when non-zero, so a suppression never silently removes rows (Rule 7b: no silent caps).
The guard can only ever *prevent* a call, never cause one.

**Files:** `20_Direct_Phone_Calls/scripts/build_call_list.py`

**Recurrence:** 1st.

**Not done:** suppression still lives only on the queue collection. A person-level suppression
record keyed on the number itself (surviving any queue rebuild) is the stronger design, and the
`--needs-id4me` append path should refuse to spend an ID4ME credit on a suppressed number at all.

## [DOM-RECENT-WINDOW-COVERAGE-GAP] The real DOM defect — timeline source stopped at the 12-month cutoff — 14:05 AEST

**Corrects `[DOM-REA-GAP-REOPENED]` above, which mis-stated the defect.** That entry called it a
double-count (245 records over 149 sales). That measurement came from a subagent reconstructing the
pool over a 12-month window using the generator's *filters*; the generator itself queried the two
sources over **disjoint windows**, so they barely overlapped and the true double-count was 6/0/3
records. The 245-vs-149 figure was an artefact of the reconstruction, not of the generator. Flagged
here rather than edited above so the wrong number stays visible.

**The actual root cause.** `calculate_days_on_market_data()` queried
`scraped_data.property_timeline` only for dates **older than 12 months** (`$lt cutoff_12m_str`),
and `listing_status='sold'` only for the **last 12 months**. Timeline records inside the recent
window were silently discarded unless a fallback triggered (`len(recent_results) < 5`, which never
fires on a real suburb). Two consequences:

1. **Recent quarters dropped most of their evidence.** Burleigh Waters 2025-Q3 held **39** timeline
   records with a usable DOM; the published quarter used **13**.
2. **A quarter's pool CHANGED AS IT AGED**, because the 12-month cutoff slides forward monthly. So
   the published series compared quarters that were not measuring the same population — which is
   what manufactured Burleigh's apparent speeding-up (48→54→31→29) that the data does not contain
   (recomputed: 24→30→26→28).

**Fix (applied to the generator; NOT yet deployed — no DB write, no frontend change):**
1. `_dedupe_dom_records()` — collapses the same sale seen by more than one source. Keyed on
   **normalised address first, `_id` second**: address takes precedence because one home can hold
   more than one document (the known, unfixed duplicate-document issue), and keying on `_id` alone
   admits one copy per duplicate doc. Clustered with a **150-day tolerance**, because the same sale
   carries different dates across sources (timeline = contract date, listing_status = our detection
   date, which lags to +126d).
2. **Widened the timeline source to the full window** — the actual fix. Safe only because (1) exists.
3. `_trailing_12m_dom()` — publishes a trailing-12-month median as `trailing_12m`, replacing
   `latest_quarter_median` (n=15–39, bootstrap 95% CI 20–32 days wide) as the headline.
   `latest_quarter_median` is retained for backwards compatibility.
4. Added `basis_note` and `dedupe_stats` to the document so the basis travels with the data.

**Validation — the two sources agree on the same sale.** On sales seen by BOTH sources
(Robina n=115, Varsity n=65, Burleigh n=107) the **median difference is 0.0 days**. Source
preference therefore moves the merged median only 1–2 days, i.e. the choice is not load-bearing.
Independently cross-checks against the agent measurement of the `days_on_market` field

## [V4-ANALYTICS-BLIND-SPOTS] V4 reading telemetry could not attribute a layout change or explain its largest cohort — 09:18 AEST
**Symptom:** Asked whether V4 off-market reader data supports conclusions yet. Three separate blind spots surfaced, none of which threw or looked broken:
1. The 2026-08-13 section reorder is recorded nowhere in the event stream — only in a memory note. Any before/after comparison silently measures the move, not the reader, and there is no way to separate them after the fact.
2. `valuation_method: "none"` is the LARGEST cohort (40 of 95 readers, 24 of 57 exits) and carries no reason. It collapses "unit", "outside the design envelope" and "no usable comps" into one label, so 42% of traffic was unreadable.
3. Dashboard insight 1 ("How far down the page people get") had no `offmarket_arm` filter, pooling ~95 non-V4 `scroll_depth` events into what presents as the V4 retention curve.

**Root cause:** (1) and (2) are missing event properties — the data was never emitted, so no query could recover it. `decline_reason` was in fact already captured, but only on `offmarket_claim_shown`, which is gated on reaching the valuation section and fired 6 times in a week. (3) is an insight misconfiguration: `scroll_depth` deliberately reuses the decks' schema so `organic_journey_build` reads V4 without a special case, and that same sharing means an unfiltered query silently picks up every other page emitting it.

## [SLOT-RESOLVER-ADDRESS-FALLBACK-DEAD] Subject-address lookup never matched anything — 14:40 AEST
**Symptom:** Rebuilding `27-protea-court-robina` with `--force` changed nothing — 11 gate blockers
before, 11 after — and finished in 21s instead of the usual 3-4 min. Log said
`Subject property not found in robina for 27 Protea Court, Robina, QLD 4226`, yet the address IS
in `Gold_Coast.robina` (twice).

**Root cause:** `slot_resolver.py` resolves the subject by `property_id` first, then falls back to
an address regex. The fallback was built as
`re.sub(r"\s+", r"\\s+", re.escape(addr))`. On Python 3.7+ `re.escape()` escapes a space to `"\ "`;
the sub then matches that same space and rewrites it to `\s+`, **leaving the backslash in front** —
producing `\\s+`, which matches a literal backslash character. So the pattern could never match a
real address. **This fallback has never worked**, for any address, since it was written. Every
report that resolved a subject did so via `property_id`; any report without a usable one silently
got NO subject, and a missing subject fails comps, scarcity, competitor matching, personas, hero
photo and aerial simultaneously — presenting as "this property has no data" rather than as a
lookup bug.

Second, smaller fault in the same expression: stripping `QLD 4226` leaves a trailing comma
(`"27 Protea Court, Robina,"`), and `Gold_Coast` stores BOTH `"27 Protea Court, Robina, QLD 4226"`
(sold record) and `"27 Protea Court, Robina QLD 4226"` (cadastral stub) for the same home — so
anchoring on the comma can only ever match one of the two formats.

**Fix:** Build the pattern by escaping each WORD and joining with `\s+`
(`r"\s+".join(re.escape(w) for w in normalised.split())`), which cannot reintroduce the escaped
space, and strip the trailing comma so both stored address formats match. Comment left in place
explaining why the obvious one-liner is wrong, since it reads as correct.

**Blast radius — measured, not assumed:** across all 111 `property_reports`, 106 already resolved
via `property_id`, **3 are recovered by the fix** (`27-protea-court-robina`,
`23-bellbird-avenue-burleigh-waters`, `11-highgate-lane-robina`), 1 has no address/suburb and 1 is
genuinely absent from `Gold_Coast`. So this is a real latent bug with a small current blast radius
— it matters going forward because freshly-minted lead addresses are exactly the case that falls
through to the fallback.

**Honest scope note:** this does NOT explain why only 15 of 337 lead addresses are mailer-ready.
That remains a separate question — 229 lead addresses exist in `Gold_Coast` as cadastral stubs
with `listing_status: None`, i.e. never listed, therefore no Domain photos. Being tested separately
