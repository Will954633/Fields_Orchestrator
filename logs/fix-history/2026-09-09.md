## [ARTICLE-DATE-HYDRATION-418] formatArticleDate had no timeZone → SSR/client date mismatch — 07:20 AEST
**Symptom:** After swapping the seasonality graphic in article `december-listing-paradox` and bumping its `updated_at` to `2026-09-08T21:08Z`, the live page threw React #418 (hydration text mismatch, `args[]=text`). Console went from 0 → 1 msg; page rendered fine but hydration failed.
**Root cause:** `src/services/articleService.ts::formatArticleDate` called `toLocaleDateString('en-AU', …)` with NO `timeZone`. It uses the runtime zone — UTC on the Netlify SSR server, local (AEST, UTC+10) on the client. `21:08Z` = "8 September" in UTC but "9 September" in AEST, so the "Updated <date>" line differed server vs client. Any article with a published/updated time in the UTC 14:00–24:00 window trips it. Not caused by the image swap — the timestamp bump exposed a latent bug.
**Fix:** Added `timeZone: 'Australia/Brisbane'` (Gold Coast zone, no DST) to the options in `formatArticleDate` so server and client always format the same calendar day. Fixes it site-wide (all article cards + article header use this one helper), not just this article. Pushed commit 7e90253 → Netlify auto-deploy; re-verified headless: #418 gone, Console 0.
**Files:** `Feilds_Website/01_Website/src/services/articleService.ts`
**Recurrence:** Nth (date-formatter hydration is a recurring class — see [HOUSE-MINI-SITE-003], [V3-HERO-DATE-HYDRATION], [GFONT-HYDRATION-418], [OFFMARKET-DECK-HYDRATION-418]). This is the first for the shared `formatArticleDate` helper. Standing lesson: EVERY `toLocale*` date call rendered under SSR must pass an explicit `timeZone`.

## [WATER-CLASS-TUPLE-SILENT-CORRUPTION] classify_water_relationship tuple return corrupted all 3 legs of renovation study — 07:45 AEST
**Symptom:** New `16_Valuation/Renovation_Premium/renovation_premium_study.py` first run: matched-pair leg found 0-3 matches out of 70+ treated per suburb; every hedonic p-value exactly 1.0 with CIs [-100%, +Inf]; r²=0.98 in a 136-row regression.

The study stored the tuple as the water-class value: (1) equality matching between treated and comps almost never fired → empty matched-pair leg; (2) `C(water)` in statsmodels exploded into hundreds of unique dummy levels → singular fit, leverage-1 rows, HC3 covariance → p=1.0/infinite CIs and fake r²; (3) `water == WATERFRONT` (tuple vs string) never true → 14 specialist-market waterfront sales silently leaked into the sample. **Fix:** Take `classify_water_relationship(doc)[0]`; switched HC3→HC1 (robust to near-leverage-1 rows in small quarter×class cells). Re-run produced sane fits (r² 0.74-0.75) and 31/32/8 matched pairs per suburb.
