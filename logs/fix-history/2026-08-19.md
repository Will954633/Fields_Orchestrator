# Fix History — 2026-08-19

## [WITHDRAWN-SERIAL-FETCH-BUDGET] Step 113 parallelised fetch — 11:20 AEST
**Symptom:** `detect_withdrawn.py` (step 113) aborted early with "runtime budget exceeded" every night for a week. At ~26s per BrightData Web Unlocker round-trip and 221 live listings, a full pass needs ~95 min against `MAX_RUNTIME_MIN` = 40, so a complete sweep was arithmetically impossible and withdrawn listings sat undetected.
**Root cause:** the main loop fetched one listing at a time. The 26s is pure network wait — no local CPU, no shared state — so the step was ~100% idle by wall clock.
**Fix:** parallelised ONLY the fetch. `worklist` is now processed in chunks of `2 x FETCH_WORKERS`; each chunk's `check_listing_status` calls resolve concurrently via `ThreadPoolExecutor.map` (order-preserving), then the chunk's results are iterated IN ORDER on the main thread where every DB write still happens serially, unchanged. Workers run `_resolve_status()`, which never receives the collection handle and does no DB access, so no write can originate off the main thread. Worker count from `WITHDRAWN_FETCH_WORKERS` (default 4, deliberately conservative; 6-8 is the target). Wall-clock `deadline` is now checked BETWEEN chunks so an abort never strands in-flight paid requests. Per-item `time.sleep(REQUEST_DELAY)` moved to between chunks.
Circuit breaker changed from consecutive-error counting to a ROLLING WINDOW (`>= WITHDRAWN_CIRCUIT_BREAKER` (15) errors in the last `WITHDRAWN_CIRCUIT_WINDOW` (20) results) — with concurrent completion, "consecutive" described nothing real and one healthy result between failures reset the count to zero. `circuit_broken` semantics and the `⚠ COVERAGE BEHIND` line that `main_site_health_check.py` greps are unchanged.
Round-robin interleaving, per-suburb counters, the rotation cursor field (`withdrawn_last_checked_at`) and `check_listing_status` classification logic are all untouched. Added `--limit N` for testing.
**Verification:** `--dry-run --limit 12` completed in **112.8s** (12 checked, 12 active, 0 errors, robina=4/varsity_lakes=4/burleigh_waters=4 — interleaving preserved) vs ~312s serial, ~2.8x.
**Files:** `scripts/detect_withdrawn.py`
**Recurrence:** First

## [AUDIT-UNPROJECTED-OOM] Step 107 dead 13 nights — unprojected find({}) needed ~13 GB — 19:30 AEST
**Symptom:** step 107 (Database Audit & Validation) hit its 600s timeout on all 3 attempts every night from 2026-08-06 to 08-19 — 13 consecutive nights, 1921s of wall clock burned per run. `stdout.log` was 1 byte. Nothing anywhere reported it.
**Root cause:** `audit_collection()` did `properties = list(collection.find({}))` — no projection, every field of every document across 110 collections materialised into a Python list. The audit only ever reads six fields. Measured: ~1,112 KB/doc × 12,104 robina docs ≈ **13.1 GB of Python heap** on a 15 GB VM already using ~6 GB with swap in use, so it swap-thrashed to SIGTERM rather than OOM-killing (no dmesg entry — part of why it was invisible).
It ran fine in 72.6s on 08-05 and failed from 08-06 onward: **document size changed, not count** (+9% docs cannot explain 72s → >600s). `[COMPS-DETAIL-EXPOSED]` on the evening of 08-05 deliberately persisted per-comparable adjustment detail; `valuation_data` is now ~115 KB of a 149 KB average robina doc. A legitimate schema change walked into an unbounded read pattern that was always fragile. Raising the timeout would not have helped — 600s was already ~6x the real work.
**Fix:**
1. Six-field projection + stream the cursor instead of `list()`. **8.6s / 105 MB peak RSS**, verified with `/usr/bin/time -v`.
2. Populated `EXCLUDED_COLLECTIONS`, which was `[]`. Six collections are keyed on something other than suburb (`propradar_sold`, `propradar_coverage_gaps`, `propradar_gap_enriched`, `unit_valuations`, `unit_statutory_comps`, `property_attributes`) and so reported every document as misplaced: **2,731 false positives, zero true ones**. Each verified as genuinely cross-suburb before excluding. Post-fix the audit finds **0 misplaced across 411,165 properties / 104 collections** — so the 416 reported on 08-05 were false positives too, and there was never a real misplacement problem.
3. Rule 7: wrapped the full sweep in `job_run("database_audit", cadence_hours=24)` — it had no heartbeat at all, so it was absent from the Process Registry. A targeted `--collection` run stays unheartbeated (developer action, not the ongoing process).
4. Rule 7b: assert an outcome. `--no-fail` forces exit 0 regardless of findings, so a run that scanned nothing was indistinguishable from a clean audit. Now raises if `collections_scanned == 0 or properties_audited == 0`.
5. Per-collection progress lines, so a future hang is localisable — the entire 110-collection scan printed nothing, which is why the failure could not be placed from logs.
6. Added step 107 to `_STEP_OUTCOME_CHECKS` in `main_site_health_check.py` (two checks: reached its summary at all; misplaced count judged on level, not on non-zero — the [WTA-OPS-020] mistake). Verified both regexes match real step output and return OK.
7. **Latent bug found in the process:** the shared capture-mode consumer does `int(mm.group(1))`, which raises `ValueError` on any comma-formatted number and would have taken the whole health check down. Now strips thousands separators — no-op for the existing bare-`\d+` patterns.
**Why it was invisible for 13 nights:** three independent safety nets and none covered this step — no Rule 7 heartbeat, `--no-fail` inverting Rule 7b, and no row in the step-outcome table.
**Files:** `scripts/database_audit.py`, `scripts/main_site_health_check.py`
**Recurrence:** First for the OOM. The step's failure was logged as `[WATCHDOG] Step 107` on 2026-08-18 without a root cause.
