## [GNAF-XXX-STREET-TYPE] 4,269 property addresses read "THE CRESTWAY XXX" on live public pages — 09:40 AEST
**Symptom:** `https://fieldsestate.com.au/off-market/29-the-crestway-xxx-robina` and the matching
`/property/` page both returned 200 with **"29 The Crestway Xxx, Robina"** in the `<title>` and body.
4,269 documents across **35 Gold Coast collections** carried the junk — `The Esplanade Xxx`,
`The Boulevarde Xxx`, `The Concourse Xxx` — plus 13 with an `Id 21158261 25 Lake Orr Drive` prefix.

**Root cause:** `valuation-tracker/gnaf/sample_addresses.py:128` resolved the street-type code with
`street_types.get(code, code)` — **falling back to the raw code on a lookup miss** — then
concatenated it into the address. **G-NAF uses the code `XXX` to mean "this street has no type"**,
which is exactly right for `The Esplanade`, `The Crestway`, `The Gardenway`. So the one code that
means "print nothing" was the one code printed. An unresolved code is never safe to emit.

**How it was found — not by looking for it.** While characterising why 3,526 dwellings matched no
onthehouse sitemap URL, the "street does not exist in their sitemap" bucket turned out to be
**our** corrupt addresses, not their missing coverage. onthehouse then served as an independent
check: `the-crestway`, `the-gardenway` and `the-links` all exist in their sitemap and the `-xxx`
forms do not, confirming the corrected names before anything was written.

**⚠ FIXING THE PROPERTY DOCUMENT CHANGED NOTHING ON THE PAGE.** The first pass repaired
`Gold_Coast.<suburb>` and the live page was byte-identical, because the address is **denormalised
into four places**. Found by searching for the literal string across every database rather than
assuming the page read the field just fixed:
  * `Gold_Coast.<suburb>` — address / complete_address / street_address (4,269)
  * `Gold_Coast.address_search_index` — **coast-wide, 86,223 docs**; 1,715 corrupt, incl.
    `street_type: "XXX"`, i.e. the parser had stored the junk AS the street type
  * `system_monitor.offmarket_discovery` — what the public deck actually renders (136)
  * `system_monitor.listing_status_cache` (1)

**⚠ SCOPE WAS 27× THE INITIAL FINDING.** It presented as 160 docs in the three target suburbs. The
search index is coast-wide, so repairing only the target suburbs would have left the index clean
and the property records dirty. Every Gold_Coast collection is now scanned.

**Fix:**
1. `scripts/fix_corrupt_addresses.py` — strips the junk from all four collections. Two anchored
   patterns only (`XXX` as a whole word, the id prefix only at string start); a general
   "clean the address" regex is how good addresses get mangled. Refuses any change that would
   empty a field carrying real content, but ALLOWS `street_type: "XXX"` -> `""` because guessing
   a street type for `The Crestway` would be inventing data. **Never touches `url_slug` or `_id`** —
   those are already indexed and renaming them needs 301s (Will's explicit call: text only).
   Original values preserved under `address_fix` for reversal.
2. `valuation-tracker/gnaf/sample_addresses.py` — `XXX` and any unresolved code now emit nothing,
   and the address is joined from the parts that exist (interpolating an empty type left
   `"29 The Crestway , Robina"` — a bug my own first fix introduced and the unit check caught).

**Verified:** 0 corrupt docs remaining in all four collections. `/property/...` renders
`29 The Crestway Robina QLD 4226`. `/off-market/...` still showed the old text until a
cache-buster proved it was a Netlify **Edge cache hit** (age 947s, ttl 2658), not stale data —
`?cb=` returns 0 occurrences. Builder unit-tested on XXX / lowercase xxx / ST / RD / unknown code.

**Files:** scripts/fix_corrupt_addresses.py, valuation-tracker/gnaf/sample_addresses.py
**Recurrence:** First. Lesson pairs with `[ONTHEHOUSE-HOUSES-BACKFILL]`: **a fix you have not
observed at the surface is not a fix.** The DB was clean two collections before the page was.
## [APPRAISAL-AERIAL-SCRATCH-LEAK] Root disk hit 100% (77MB free) from never-deleted aerial scratch — 08:30 AEST
**Symptom:** VM at load 8.0 on 4 vCPU and `/` **100% full with 77MB free** — one write away from a
crash. `artifacts/appraisals_v4` was 25GB, of which `assets/aerial_tmp` alone held **3,686 files /
6.9GB** and was still growing (newest file timestamped during the investigation).

**Root cause:** `_render_boundary_aerial()` in `generate_appraisal_v4.py` renders the Google Static
Maps aerial into `artifacts/appraisals_v4/assets/aerial_tmp/`, then (for `cover=True`) copies the
bytes to the durable shared cache at `/data/blobs/property-images/aerial/<suburb>/<id>/boundary_cover.png`
and returns the **cached** path. The scratch file it just copied *from* was never unlinked — nothing
references it again, and no janitor ever swept the directory. The cache was working correctly (3,653
covers present), so this was pure orphan accumulation at ~2MB per render.

It went unnoticed because it only becomes material at volume: `prewarm_offmarket_covers.py
--limit 100000 --workers 3` has been running since 2026-08-14 pre-building the catchment, turning a
2MB-per-render leak into 6.9GB.

Note the second, smaller path: when `cover=False` the function `return Path(path)` — the scratch file
**is** the live asset there and cannot be unlinked inline. Those leak too, just far more slowly.

**Fix:**
1. `assets/aerial_tmp` swept of files older than 60 min — **3,528 deleted, 6.9GB → 277MB**. The 60-min
   floor deliberately spared in-flight renders (3 concurrent pre-warm workers).
2. `journalctl --vacuum-size=50M` — 40MB.
3. **Permanent, cover path:** unlink the scratch file immediately after the `shutil.copy` to the shared
   cache succeeds. Placed inside the success branch so a failed copy still leaves the bytes on disk.
4. **Permanent, non-cover path:** added `_sweep_aerial_scratch()`, called at the top of `main()`, which
   removes scratch older than 24h. Age-gated rather than unconditional precisely because the non-cover
   branch hands that path back to a caller that is still using it, and 3 workers run concurrently.

Net: 77MB → **6.7GB free**.

**Verification:** measured a clean window starting 08:33:11, after the patch, while the pre-warm kept
running: **5 covers newly cached, 0 new scratch files left behind.** (An earlier window straddling the
edit showed 6 leftovers against 10 covers — those were processes that had loaded the old code before
the edit landed, not a failure of the fix.)

**Files:** `scripts/generate_appraisal_v4.py`

**Recurrence:** First for this specific leak. But root-disk pressure is **not** first — see
`[COVERAGE-AUDIT-009]`, `[BLOB-DISK-HDD-MIGRATION]`, `[SSD-QUOTA-DENIED + AUTORESIZE-WATCHER]`. Those
all concern `/data/blobs`; the autoresize watcher built there does **not** watch `/` , which is why a

### Not fixed — reported to Will, needs a decision

## [RESOURCE-GUARD-THROTTLED-BLIND-ALERT] Disk alerts fired 976 times and told Will nothing useful — 23:45 AEST
**Symptom:** Root disk sat at 92-100% for ~13h (see `[APPRAISAL-AERIAL-SCRATCH-LEAK]` above) and Will's
Telegram carried no usable warning. Investigating "why was there no alert" found the opposite: the alert
had fired ~4 times and was **indistinguishable from routine noise**.

**Root cause — two independent defects, both in `scripts/resource_guard.py`:**

1. **Throttled with no escalation.** `ALERT_COOLDOWN_H = 3` per category, and 93% and 100% produce the
   *identical* message. `disk_high_streak` reached **976 consecutive critical passes** and never raised
   urgency. Over 13h that is ~4 messages, each reading "Auto-cleanup ran … investigate growth".

2. **The cleanup it advertised is structurally incapable of fixing this class of problem.**
   `disk_cleanup()` only touches journald, apt/pip caches, `logs/**` >100MB and run-logs >14d. It has no
   concept of `artifacts/`, scratch or cache dirs, so the 6.9GB in `artifacts/appraisals_v4/assets/aerial_tmp`
   was invisible to it. It ran ~960 times, reclaimed ~0 bytes, and reported a list of actions every time.
   **This is Rule 7b applied to a remediation: it asserted that it ACTED, never that it ACHIEVED anything.**

**Fix:**
1. `disk_cleanup()` now returns `(actions, bytes_freed)`, measured from `shutil.disk_usage("/").free`
   before/after. The routine alert reports actual MB freed and GB remaining instead of "cleanup ran".
2. New `disk_ineffective` alert category: when a CRITICAL pass frees `< CLEANUP_INEFFECTIVE_BYTES`
   (200MB) **and** disk is still critical, send a differently-worded alert on a **1h** cooldown
   (`INEFFECTIVE_COOLDOWN_H`) stating plainly that cleanup is not working, how many consecutive
   critical checks have elapsed, and that it needs a human.
3. `top_growth_dirs()` names the actual culprit — `du -x --max-depth=2` over `/home/fields`, `/var`,
   `/tmp`, with parent dirs suppressed when a listed child is ≥70% of them. ⚠ Called **only** on the
   ineffective-alert path: it takes ~13s of heavy I/O and the guard runs every 90s on a box that is by
   definition already under pressure.
4. `alert_allowed()` takes an optional per-category `cooldown_h`.

**⚠ Defect found and fixed during verification: `--dry-run` was consuming the real alert budget.**
`send_telegram()` returns early when dry, but `mark_alerted()` ran regardless — so a diagnostic run
started a cooldown for a message nobody received. Observed live: a dry run at 23:39:38 silently
suppressed the genuine alert from the real run 67s later. `mark_alerted(..., dry)` is now a no-op on dry
runs, all 7 callsites pass the flag, and the poisoned `disk_ineffective` key was cleared from
`logs/resource_guard_state.json`. **A diagnostic mode that mutates the state it is diagnosing is worse
than no diagnostic mode** — it makes the system quieter precisely when someone is looking at it.

**Verified:** dry run selects the new escalated message at 94%/0MB-freed and leaves `last_alert`
untouched; the rendered alert names `/home/fields/Fields_Orchestrator/artifacts` (19.7G) and
`/home/fields/backups/mongodb` (12.6G) as the top two — exactly the signal that was missing this morning.

**Files:** scripts/resource_guard.py
**Recurrence:** First for the alert path. The underlying pattern — a job reporting success for doing
nothing — is the third instance after `[BUILDER-ENV-EXPORT-GAP]` and `[INDEXING-SILENT-ZERO]`, which is
why CLAUDE.md Rule 7b exists. Rule 7b was written for *jobs*; this is the same failure in a *remediation*,
and the fix is the same: assert the outcome, not the attempt.

## [JUSTCALL-CALL-SYNC] Build JustCall → CRM call + transcript sync — 10:05 AEST
**Symptom:** New build, not a bug. `00_SCOPING.md` §8 specifies calls and transcripts landing in
`system_monitor.call_activity`, and nothing existed to put them there. The JustCall API exposes
**only the last 3 months** of call history, so every day without this job is a day whose call
records acquire a 90-day fuse — once the window passes they are unrecoverable except by emailing
JustCall support.
**Root cause:** n/a (new module).
**Fix:** Two writers into one collection, keyed on the same stable field (`call_sid`) with the same
document shape, so whichever arrives first creates the row and the other fills it in:

1. `20_Direct_Phone_Calls/scripts/justcall_sync.py` — nightly reconciliation. Pages
   `GET /v2.1/calls`, then `GET /v2.1/calls_ai?fetch_transcription=true` (that param **defaults to
   false**; omitting it returns a 200 with no transcript, which is indistinguishable from not being
   entitled). Upserts with `$set` for mutable fields + `$setOnInsert` for `first_seen`. Joins each
   call to `system_monitor.call_queue` on a 9-digit AU phone key that handles `+61`/`0`/spacing
   variance, stamps the queue row `status="called"`, and records an **unmatched call as a value**
   (`queue_match`: matched / no_matching_number / no_queue_collection / no_phone_number) rather than
   as an absent field — Will dialling someone by hand is a legitimate unmatched call, but "every
   call unmatched" must be visible as a number and not as silence. Optional `--download-recordings`
   stores the MP3 under `20_Direct_Phone_Calls/recordings/` (added to `.gitignore` — it is private
   conversation audio under QLD *Invasion of Privacy Act* s45) with its sha256.

   **Rule 7/7b.** Wrapped in `job_run("justcall_sync", cadence_hours=24, …)`; `beat.metrics` carries
   calls_seen / calls_ingested / transcripts_ingested / recordings / unmatched. The zero-output
   assertion uses the server's own `total_count` field, not our own parse — comparing our row count
   against a number we derived from the same parse would prove nothing. It raises when the server
   reports calls and we ingested none, **and also on a partial parse** (parsed 40 of 300 is the same
   failure with a smaller number on it, and would otherwise pass the zero check and then advance the
   watermark over the other 260). The watermark lives in `system_monitor.job_watermarks`, never a
   local file, and is written only on the success path — and it *widens* the next run's window rather
   than being merely a floor, so a failed night is re-attempted instead of being skipped. A watermark
   older than the 90-day retention is clamped and reported as permanent loss instead of silently
   "catching up" over a gap that is already gone.

2. `netlify/functions/justcall-call-webhook.mjs` (written, **deliberately not deployed**) — handles
   `call.completed` and `jc.call_ai_generated`. Verifies the HMAC-SHA256 signature
   (`secret|<url-encoded url>|<event>|<timestamp>`, 15-minute replay window) — an upgrade on
   `justcall-sms.mjs`, which has only a `?k=` shared secret — but **also accepts `?k=` as a
   fallback**, because dynamic signatures are an opt-in per-webhook dashboard setting and an endpoint
   that fails closed on arrival drops call records into the unrecoverable bucket. Which path
   authenticated is logged and stored on the row as `auth_via`, so "signatures are on" is a fact we
   can check rather than a belief; a signature that is present but does not verify logs a warning
   even when the fallback succeeds. `call.completed` fires *before* notes/disposition/AI exist, so
   only fields carrying an actual value enter `$set` — the early event can never overwrite what the
   AI event already established.

**Transcription is stored as an explicit state, never as an absent field** — `pending` / `available`
/ `empty` / `not_entitled` / `no_recording` — because entitlement on our Team plan is unproven
(vendor blog says included, third-party pricing says add-on, developer docs silent). A call with no
recording is marked `no_recording` rather than `pending`, so it cannot sit forever waiting for
something that was never possible.

**Verification.** Both handlers exercised end to end against the live DB with synthetic events, then
every test row deleted and the two collections dropped back to their prior (non-existent) state:
webhook `call.completed` → `no_recording`, then `jc.call_ai_generated` → `available` (no demotion);
bad `?k=` → 403; valid HMAC with no `?k=` at all → 200 via `hmac_signature`; tampered HMAC → 403;
hour-old timestamp → 403. Python side: campaign join matched + unmatched, the 7b zero assertion and
the partial-parse assertion both raised, and the watermark was confirmed **unchanged** after each.
Python and JS phone keys verified to agree on the same inputs — if they diverge the campaign join
silently splits in two. Seeded a real heartbeat (Rule 7 #4) and added the 01:20 cron entry, without
which the job would read STALE on the health board within 36h.

**Transcription entitlement: STILL UNPROVEN, and the probe says so.** `--test-transcription` ran
against the full 90-day window and returned `total_count=0` — **the account has made no calls at
all**, so there is nothing to transcribe and the result proves nothing either way. `/calls_ai`
itself answers 200 (not 401/403) with our credentials, which shows the endpoint is reachable but not
that transcripts would be generated. The probe is written so this cannot be misread: it prints
`VERDICT: INCONCLUSIVE — NO CALLS EXIST TO TEST WITH` and names the next step, because a previous
probe returned 200-with-zero-calls and was nearly taken as evidence of entitlement.
**Blocked on:** recording being switched on for the number (dashboard only, no API) and one real
recorded call. Fallback if it fails is already scoped: `--download-recordings` + Gemini via Vertex.

**Constraints honoured:** GET-only against JustCall, no webhook registered, no call placed, nothing
pushed to GitHub, `justcall-sms.mjs` untouched.

## [CALL-LIST-OCCUPANCY-DATING] Prior occupants excluded from the call list — 10:40 AEST
**Symptom:** `build_call_list.py` turned every ID4ME person on a property document into a
queue row. ID4ME returns everyone it has EVER associated with an address — 12 people at
20 Chantilly Place, Robina, spanning 1997 to 2023, against a property that last sold in
2009. Most are previous occupants. Each one was a DNC wash credit we pay for, and a
stranger asked about a house they sold fifteen years ago. Nothing in the builder dated
them, and nothing capped how many people at one house could be dialled.
**Root cause:** `id4me_people()` flattened people to (person, phone) pairs and never
compared `ID4ME_Source_Date_Latest` to the property's last SALE. The score had no
occupancy term, so a 1997 record outranked nothing.
**Fix:** integrated `occupancy_evidence.assess_occupancy` / `rank_people` / `last_sale`.
Every ID4ME-sourced person (tracks B and C) is now dated BEFORE a row exists:
* `prior_occupant` → no row, counted under the new named exclusion
  `prior_occupant_dated_before_sale` (distinct numbers, i.e. wash credits not spent), so
  it appears in `--stats` and can never be a silent omission. `--include-prior` overrides.
* `current_likely` / `unknown` → row, with the full assessment stored on the doc under
  `occupancy` (verdict, confidence, reasoning, last_sale_date, id4me_record_date,
  record_age_years, our_last_contact_date, assessed_at) — the exact contract
  `call_list_to_sheet.build_row` already reads for the "Occupant?" column (index 8).
* Scoring gained `occupancy_evidence`: current_likely 0.10 + 0.15×confidence (0.175–0.235
  in practice), unknown 0.03, prior −0.25 (reachable only under `--include-prior`).
  Deliberately capped BELOW `record_freshness` (0.30): both terms are driven by the same
  ID4ME date, and `current_likely` is the WEAK direction of an asymmetric inference — a
  signal that cannot confirm must not be the largest term. The strong direction is not a

* `--max-per-address` (default 2) caps ROWS per address, taken in `rank_people` order so
  the cap bites on the weakest candidate. Dialling five people at one house is the

* New `ContactHistory` builds the `our_contacts` argument from OUR OWN records, keyed by
  address_slug. Rule 8: every path confirmed with `scripts/db_fields.py` before querying,

  7,303 of 7,308 are our own precompute and are excluded). 179 of 218 candidate addresses
  have at least one. `system_monitor.call_outcomes` and `call_activity` are BOTH EMPTY
  (0 docs, call_outcomes not even created) — deliberately NOT queried rather than coded
  against guessed field names; wire after the first call round.
* Rule 7b: added an assertion that people read from ID4ME must produce verdicts, and
  made "everything was excluded as a prior occupant" (`all_people_prior_occupants`,
  `occ_prior_rows_suppressed`) reportable and distinct from "we found nothing" — the

## [PODCAST-BRAIN-INGEST] Spotify podcast -> Brain 1 transcription pipeline — 11:20 AEST
**Symptom:** No route existed to get podcast content into Brain 1. Requested for the Bothsides

The proxy works. My probe failed with `407 Invalid Auth` because I passed a session tag containing a

normally — verified, 18,545 words. `youtube_brain_ingest.py` is NOT broken.
This is CLAUDE.md rule 8 applied to an auth failure rather than a query: **a rejection is evidence
about what I typed, not about the credential.** The two management endpoints that looked corroborating
(`status` -> `can_make_requests:false, auth_fail_reason:zone_not_found`; `customer/balance` -> 403)
are both red herrings — `status` reports on the key's default zone and `balance` needs a permission
the key does not carry, and NEITHER reflects whether unlocker traffic flows. Only the proxy does.
Added `scripts/probe_brightdata_auth.py` so this is diagnosed in one command instead of by inference
across three disagreeing endpoints.
**What was genuinely dead:** OpenAI ASR only (`insufficient_quota: credit_balance_exhausted`).
**Why the podcast still uses Vertex and not free YouTube captions:** YouTube auto-captions carry no

## [YT-INGEST-UNASSERTED-ZERO] youtube_brain_ingest could report success having listed, fetched and built nothing — 11:50 AEST
**Symptom:** Another session flagged that `youtube_brain_ingest` recorded `status=success` with

nothing pending". Investigating that claim found the premise wrong and three real defects behind it.
**Root cause:**
1. *The claim itself was wrong on the detail.* Two videos WERE pending (`attempts=1`), so the existing
   `attempted > 0 and transcribed == 0` assertion was reachable. Both transcribed fine on re-run
   (7,147 and 4,183 words) — the earlier `VideoUnplayable` errors were transient.
2. *Nothing scheduled the job.* One heartbeat existed in `job_runs`, ever: 2026-08-08 05:57 UTC, a
   hand-run `discover`-only invocation (metrics carried no `transcribe_*`/`chunk_*` keys — which is
   why it looked like an unfireable assertion; that code path had simply never executed). It
   self-registered `cadence_hours=168` with no crontab line and no timer to keep that promise. It
   would have gone STALE on ~2026-08-18 — correctly, but for "unscheduled", not "captions broke".
3. *`discover` had no assertion at all* (the genuine Rule 7b hole). `yt-dlp` exiting 0 having listed
   nothing — bot check, channel restructure, changed id — is indistinguishable from "no new videos".
   Worse, `channels_listed` is a SUM across channels (250 eXp + 81 BLAC SALT = 331), so one dead
   channel is fully masked by the other still working.
4. *`MAX_ATTEMPTS=3` retirement was silent.* Failed videos keep `status: "pending"` and drop out of
   `{"attempts": {"$lt": 3}}` forever — never retried, never counted, never reported. A sustained
   caption outage raises for 3 runs per video and then goes permanently quiet. This IS the shape of
   gap the original flag described, reached via attempt exhaustion rather than an empty queue.
5. *Found while testing the fix:* `discover` registers scheduled premieres ("Premieres in 2 days").
   They cannot transcribe, burned an attempt per run, and after 3 weekly runs were retired for good —
   even though by then they had long since aired. Silent corpus loss, and the retired stubs pile into
   exactly the given-up count the new alert gates on, so it would have false-tripped over time.
**Fix:**
- `discover`: raise per channel when it lists 0 entries, and emit per-channel counts
  (`listed_exp_realty_us`, `listed_blac_salt_au`) alongside the sum so one channel dropping is
  visible. Also raise when `--library` matches nothing in the config.
- `transcribe`: count `status: "pending", attempts >= MAX_ATTEMPTS` every run as `given_up`, and raise
  once it crosses `max(10, 5% of registered)` — a shape that distinguishes a bulk outage from the few
  genuinely private/removed videos that must not hold the job red forever.
- Premieres are classified `not_yet_released` (`_PREMIERE_RE`) and deferred without spending an
  attempt, bounded at `MAX_DEFERRALS=8` so a cancelled premiere still eventually counts. The existing
  zero-transcribed assertion now compares against `attempted - deferred`, so a queue holding only
  unreleased videos reads as "no work to do" rather than failing. Reset the 2 attempts my own test run
  had charged under the old logic.
- Added the missing weekly cron (Sunday 09:30 AEST, `all`) to match the declared 168h cadence.
- Verified: both discover assertions fire under simulated rc=0-empty and no-match; the give-up gate
  computes 0/335 vs threshold 16 and stays quiet; a real end-to-end run through the exact cron command
