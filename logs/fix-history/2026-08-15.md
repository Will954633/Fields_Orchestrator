# Fix History — 2026-08-15

## [GNAF-XXX-STREET-TYPE] 4,269 property addresses read "THE CRESTWAY XXX" on live public pages — 09:40 AEST
**Symptom:** `https://fieldsestate.com.au/off-market/29-the-crestway-xxx-robina` and the matching
`/property/` page both returned 200 with **"29 The Crestway Xxx, Robina"** in the `<title>` and body.
4,269 documents across **35 Gold Coast collections** carried the junk — `The Esplanade Xxx`,
`The Boulevarde Xxx`, `The Concourse Xxx` — plus 13 with an `Id 21158261 25 Lake Orr Drive` prefix.

**Root cause:** `valuation-tracker/gnaf/sample_addresses.py:128` resolved the street-type code with
`street_types.get(code, code)` — **falling back to the raw code on a lookup miss** — then
concatenated it into the address. **G-NAF uses the code `XXX` to mean "this street has no type"**,
which is exactly right for `The Esplanade`, `The Crestway`, `The Gardenway`. So the one code that
means "print nothing" was the one code printed. An unresolved code is never safe to emit.

**How it was found — not by looking for it.** While characterising why 3,526 dwellings matched no
onthehouse sitemap URL, the "street does not exist in their sitemap" bucket turned out to be
**our** corrupt addresses, not their missing coverage. onthehouse then served as an independent
check: `the-crestway`, `the-gardenway` and `the-links` all exist in their sitemap and the `-xxx`
forms do not, confirming the corrected names before anything was written.

**⚠ FIXING THE PROPERTY DOCUMENT CHANGED NOTHING ON THE PAGE.** The first pass repaired
`Gold_Coast.<suburb>` and the live page was byte-identical, because the address is **denormalised
into four places**. Found by searching for the literal string across every database rather than
assuming the page read the field just fixed:
  * `Gold_Coast.<suburb>` — address / complete_address / street_address (4,269)
  * `Gold_Coast.address_search_index` — **coast-wide, 86,223 docs**; 1,715 corrupt, incl.
    `street_type: "XXX"`, i.e. the parser had stored the junk AS the street type
  * `system_monitor.offmarket_discovery` — what the public deck actually renders (136)
  * `system_monitor.listing_status_cache` (1)

**⚠ SCOPE WAS 27× THE INITIAL FINDING.** It presented as 160 docs in the three target suburbs. The
search index is coast-wide, so repairing only the target suburbs would have left the index clean
and the property records dirty. Every Gold_Coast collection is now scanned.

**Fix:**
1. `scripts/fix_corrupt_addresses.py` — strips the junk from all four collections. Two anchored
   patterns only (`XXX` as a whole word, the id prefix only at string start); a general
   "clean the address" regex is how good addresses get mangled. Refuses any change that would
   empty a field carrying real content, but ALLOWS `street_type: "XXX"` -> `""` because guessing
   a street type for `The Crestway` would be inventing data. **Never touches `url_slug` or `_id`** —
   those are already indexed and renaming them needs 301s (Will's explicit call: text only).
   Original values preserved under `address_fix` for reversal.
2. `valuation-tracker/gnaf/sample_addresses.py` — `XXX` and any unresolved code now emit nothing,
   and the address is joined from the parts that exist (interpolating an empty type left
   `"29 The Crestway , Robina"` — a bug my own first fix introduced and the unit check caught).

**Verified:** 0 corrupt docs remaining in all four collections. `/property/...` renders
`29 The Crestway Robina QLD 4226`. `/off-market/...` still showed the old text until a
cache-buster proved it was a Netlify **Edge cache hit** (age 947s, ttl 2658), not stale data —
`?cb=` returns 0 occurrences. Builder unit-tested on XXX / lowercase xxx / ST / RD / unknown code.

**Files:** scripts/fix_corrupt_addresses.py, valuation-tracker/gnaf/sample_addresses.py
**Recurrence:** First. Lesson pairs with `[ONTHEHOUSE-HOUSES-BACKFILL]`: **a fix you have not
observed at the surface is not a fix.** The DB was clean two collections before the page was.
