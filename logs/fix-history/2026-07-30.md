## [ADDRESS-SEARCH-WHITESPACE] One-word street names never match two-word stored names — 11:40 AEST
**Symptom:** Same seller fired ~40 `address_search` events over 8 min on /analyse-your-home (10:53–11:01 AEST), abandoned twice, never submitted — could not find their own home in the autocomplete. They typed the street as one word ("120 Gleneagles drive, Robina"); it is stored as two words ("120 Glen Eagles Drive").
**Root cause:** `netlify/functions/address-search.mjs` `searchIndex()` tokenizes the query on whitespace and joins tokens with `.*`. "GLENEAGLES" → regex `120.*GLENEAGLES`, which cannot match "120 GLEN EAGLES DRIVE" (a space sits between GLEN and EAGLES). Verified live: "120 Glen Eagles" → 1 result, "120 Gleneagles" → 0 results.
**Fix:** Make each token whitespace-tolerant internally — join a token's characters with `\s*` (tokens are already stripped to [A-Z0-9], so every char is regex-safe): `tokens.map(t => t.split('').join('\\s*')).join('.*')`. So "GLENEAGLES" → `G\s*L\s*E\s*N\s*E\s*A\s*G\s*L\s*E\s*S` matches "GLEN EAGLES". Node unit test: seller's queries now match, "14 Ray"→"14 STINGRAY" regression holds, no false positives. Deployed and confirmed live ("120 Gleneagles Robina" → 1 result). Does NOT fix true typos (e.g. "Gleneages", missing a letter) — that needs fuzzy matching, deferred.
**Files:** netlify/functions/address-search.mjs (34aa663 @ Will954633/Website_Version_Feb_2026).
**Recurrence:** 2nd — prior [ADDRESS-SEARCH-DEBOUNCE] was a different root cause (debounce) in the same search bar.
